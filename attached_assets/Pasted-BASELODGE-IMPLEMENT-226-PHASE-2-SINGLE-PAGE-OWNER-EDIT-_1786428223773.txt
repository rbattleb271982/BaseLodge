BASELODGE — IMPLEMENT #226 PHASE 2
SINGLE-PAGE OWNER EDIT MODE ON TRIP DETAIL

Implement the next phase of the approved #226 architecture.

Phase 1 is complete:
- “Trip Setup” is now “My Setup”
- Pass is participant-level
- Equipment is participant-level
- Lessons is participant-level
- Owner and accepted participants can each edit only their own My Setup values

Now make trip_detail the ONE primary user-facing trip screen for the owner.

Do NOT undo or alter the Phase 1 personal-ownership work.

==================================================
1. FINAL PRODUCT MODEL
==================================================

TRIP-LEVEL — OWNER ONLY
- Location
- Dates
- Visibility
- Planning / Going
- Private note

PERSONAL — CURRENT USER
- Pass
- Equipment
- Lessons

Important:

“My Setup” remains directly editable at all times for both:
- owner
- accepted participant

The owner does NOT need to enter Edit mode to change:
- Pass
- Equipment
- Lessons

Edit mode is only for trip-level information.

==================================================
2. REMOVE NAVIGATION TO SEPARATE EDIT PAGE
==================================================

Current owner behavior:

Edit → /trips/<id>/edit

Change this.

On trip_detail:

The owner’s Edit action should NO LONGER navigate away.

Instead:

Edit

should enter a client-side edit mode on the SAME trip_detail page.

Do not delete:

/trips/<id>/edit
templates/edit_trip.html
edit_trip_form()

Keep them intact as temporary fallback/legacy behavior.

Do not redirect or remove the route yet.

td-edit-mode

Edit

Editing state:

Done

No page navigation.

No query parameter required.

==================================================
13. PRIVATE NOTE SAVE UX
==================================================

Because overall Edit mode uses per-field AJAX:

Do NOT let the owner type a private note and then lose it by tapping Done.

Use one clear save behavior for Private note.

Preferred:

Textarea + explicit:

Save note

button inside the Private note editor.

Behavior:

- button disabled or subdued when unchanged if practical
- POST /api/trip/<id>/notes
- trim whitespace server-side using existing endpoint
- empty value clears note
- 500-char limit enforced
- show lightweight success state
- after successful save, note remains visible while still in Edit mode

Done should NOT silently discard a changed, unsaved note.

If note has unsaved changes and user taps Done:
either:
A. save it first
or
B. warn that note has unsaved changes

Choose the simplest reliable implementation and report which pattern was used.

14. DONE BUTTON
==================================================

Done does NOT perform one giant save.

All fields save individually through their canonical AJAX endpoints.

Done should:

- exit td-edit-mode
- restore Edit label

- preserve already-saved changes on screen

If an AJAX request is currently in flight:
prevent Done from creating an inconsistent UI state if practical.

No full page navigation required.
