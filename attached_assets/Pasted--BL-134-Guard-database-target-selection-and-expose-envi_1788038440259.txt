# BL-134 — Guard database target selection and expose environment identity

This is a CRITICAL database-safety task.

PLAN / INVESTIGATION ONLY.

Do not modify code.
Do not run any migration.
Do not write to any database.
Do not change secrets or environment variables.

## Goal

Make it impossible to mistake these database targets during migration work:

1. Replit PostgreSQL
2. Supabase Development
3. Supabase Production

The system must eventually support:
- explicit migration target selection
- safe environment/database identity diagnostics
- fail-closed migration commands
- no generic fallback that could accidentally select Development or Production

BL-134 is only the safety/targeting layer.

NO migration execution belongs in this task.

- migration scripts and helper scripts

## B. Identify the three environments safely

Determine what non-secret attributes can reliably distinguish:

### Replit PostgreSQL
### Supabase Development
### Supabase Production

Possible identity signals to evaluate:
- hostname
- database name
- Supabase project ref
- configured environment label
- explicit target enum
- server/database metadata queried read-only
- other stable identifiers already available

Do not recommend printing:
- passwords
- full connection strings
- API keys
- tokens
- credentials

The diagnostic should show enough identity for a human to know exactly what target is selected without revealing secrets.

## C. Explicit target-selection design

Recommend a fail-closed target-selection mechanism.

I want an operator to explicitly choose something equivalent to:

- replit
- supabase-development
- supabase-production

Evaluate the best mechanism for this repository, such as:
- a dedicated MIGRATION_TARGET variable
- explicit wrapper commands/scripts
- environment-specific config variables
- another safer existing pattern

The important requirement is:

Development and Production must NEVER be inferred merely because a generic DATABASE_URL happens to contain one of them.

If the target is not explicitly selected, migration commands should refuse to proceed.

## D. Target/URL mismatch protection

Design how to detect and reject cases like:

- MIGRATION_TARGET=supabase-development but URL points to Production
- MIGRATION_TARGET=supabase-production but URL points to Development
- MIGRATION_TARGET=replit but URL points to Supabase
- unknown target
- missing target
- missing target-specific URL
- malformed database URL

The system should fail closed before Alembic performs migration work.

Explain where this check should live.

## E. Diagnostic command

Design a safe diagnostic that an operator can run before migration work.

It should clearly report something like:

Database host: [safe host]
Database name: [safe name]
Environment identity: [safe project/environment identifier]
Migration revision: [if safely/read-only obtainable]
Target verification: PASS

or FAIL with a clear reason.

Determine whether querying current Alembic revision is appropriate and safe here.

No writes.
