# #248 - Friend Discovery: Registered-User Search

## What & Why

Extend the existing Friends page so users can find and connect with other registered BaseLodge members by name.

Today the Search friends field only filters the user's existing friends client-side.

This feature adds:

* Server-side global registered-user search triggered on Enter/Search
* Shared friend-request service logic
* Pair-specific 24-hour request cooldown behavior
* Mutual-friend counts
* Relationship-state-aware search results
* A user-controlled friend-discovery privacy setting

The existing Friends page, `Friend` model, `Invitation` model, accept/decline routes, push notification events (`FRIEND_REQUEST_CREATED` / `FRIEND_REQUEST_ACCEPTED`), and profile-settings patterns should all be reused wherever possible.

---

# Done looks like

* Typing into Search friends continues to filter existing friends client-side
* Pressing Enter/Search with a valid two-component name triggers server-side BaseLodge user search
* Global search replaces the normal friends list while active
* Results show:

  * Name
  * Home state when available
  * Mutual-friend count when greater than zero
  * Relationship action/status
* Possible states:

  * Connect
  * Requested
  * Accept
  * Connected
  * No action during cooldown
* Connect requires confirmation before sending
* Accept acts immediately
* Requested can be tapped to cancel
* Decline, sender cancellation, and unfriend each create a 24-hour pair-specific cooldown
* During cooldown both users can still appear in search, but neither gets a Connect action
* Discoverability setting is added to Profile Settings above Notifications
* Discoverability defaults On for existing and new users
* Existing friends remain searchable even when discoverability is Off
* A discoverability-Off user who has sent the current user a pending request may still appear to that recipient
* A discoverability-Off user should not remain searchable merely because the searching user previously sent them a request
* Opted-out users may still count anonymously toward mutual-friend totals
* Existing friend-request push notification infrastructure is reused unchanged
* Full automated test coverage is planned
* Existing functionality remains intact

# Product behavior

## 1. Existing Friends search while typing

The current Search friends behavior remains intact while the user types.

## 2. Global search trigger

Global search runs only when the user presses Enter/Search.

Minimum eligibility:

* At least 2 characters in the first-name portion
* At least 2 characters in the last-name portion
* At least two name components overall

Examples:

`John`
→ filters current friends only

`John S`
→ filters current friends only

If Enter/Search is pressed before the minimum is met:

**Enter more letters to search BaseLodge.**

`Jo Sm`
→ eligible global search

`John Sm`
→ eligible

`John Smith`
→ eligible

Once global search begins:

* Replace the normal Friends list with a loading state
* Replace loading state with global results
* Clearing the search restores the normal Friends view

If no matches:

**No BaseLodge users found**

# 3. Name matching requirements

Global matching should be:

* Case-insensitive
* Accent/diacritic-insensitive
* Apostrophe-tolerant
* Hyphen-tolerant
* Extra-whitespace tolerant
* Prefix-oriented rather than arbitrary substring matching
* Display should preserve the person's actual stored spelling

Examples:

`john smith`
→ John Smith

`JOHN SMITH`
→ John Smith

`Jose Garcia`
→ José García

`OConnor`
→ O'Connor

`Battle Baxter`
→ Battle-Baxter

`Anne Marie`
→ Anne-Marie

Do not allow arbitrary internal substring behavior like:

`ohn mith`
→ John Smith

Names may contain multiple words.

Support examples such as:

* Mary Ann Smith
* Ana Maria De La Cruz
* John Van Buren
* Anne-Marie Smith

# 7. Connect

**Send friend request to John Smith?**

# 8. Incoming request

If the candidate already sent the current user a pending request:

Show:

**Accept**

Do not show Connect.

Do not allow a reverse pending request to be created.

Accept should happen immediately with no confirmation.

After success:

* Change to Connected
* Recalculate visible mutual counts
* No full page reload

The backend must prevent reverse-request creation independently of the UI.

---

# 9. Outgoing request

If the current user already sent the candidate a pending request:

Show:

**Requested**

Requested is tappable.

On tap:

**Cancel friend request?**

Actions:

* Keep Request
* Cancel Request

Successful cancellation:

* Request becomes cancelled
* Requested disappears
* 24-hour pair cooldown begins
* Person remains visible in search
* No action shown during cooldown

If cancellation fails:

* Keep Requested visible
* Show an error
* Do not update optimistically

---

# 10. 24-hour cooldown

Cooldown applies after:

1. Request declined
2. Sender cancels request
3. Existing friendship is removed

During cooldown:

* Users may still appear in search
* Home state still shows
* Mutual-friend count still shows
* No Connect action
* No cooldown explanation
* No countdown
* No "try again later"

After 24 hours:

* Connect becomes available automatically
* No manual reset required

Cooldown must be enforced server-side.

---

# 11. Declines

If a request is declined:

* Do not notify the requester of the decline
* Begin the 24-hour pair cooldown
* Requested disappears once relationship state is refreshed
* No Connect during cooldown
* Connect returns after cooldown

---

# 12. Cancellation

If a sender cancels:

* Recipient should no longer see the request as pending
* No cancelled-history UI
* Begin 24-hour pair cooldown

---

# 13. Unfriend

When existing friendship is removed:

* Existing symmetric Friend removal behavior remains intact
* Begin 24-hour pair cooldown
* Both users may still find one another in search
* No Connect until cooldown expires
* Either user may reconnect after 24 hours

---

* Pending Invitations

* Cancelled Invitations
* Removed friendships

A user who turned discoverability Off may still count anonymously if they are a confirmed friend of both users.

Do not expose mutual-friend names.

Avoid N+1 queries.

Plan a batched mutual-count query/helper.

# REQUIRED PLAN CORRECTIONS

The earlier draft plan contained five issues that must be corrected in this revised plan.

These are mandatory.

---

## Correction 1 — cooldown must be pair-specific

Do **not** store a general cooldown on `User`.

A field such as:

`User.friend_request_cooldown_until`

is incorrect because a cooldown is between two specific people.

Example:

Richard cancels a request to John.

That should mean:

**Richard ↔ John are blocked from re-requesting each other for 24 hours.**

It must NOT stop:

* Richard → Sarah
* Richard → Michael
* John → Emily

Determine the cleanest pair-specific architecture.

Investigate whether the pair cooldown should be stored:

* on the relevant `Invitation`
* in a dedicated pair-level relationship/cooldown structure
* or another existing relationship-level mechanism

The plan must specify:

* Exact storage location
* Exact fields
* How both A→B and B→A checks resolve the same pair-level cooldown
* How decline creates it
* How cancellation creates it
* How unfriend creates it
* How the friend-request service checks it
* How global search determines `cooldown_active`
* How expiration works automatically

Prefer the smallest safe design.

Do not introduce a user-wide cooldown.

---

## Correction 2 — fix discoverability exception direction

The search eligibility logic must reflect the exact product decision.

A discoverability-Off user can still appear when:

### Existing friend

The searching user is already connected to them.

### Incoming request to the searching user

The discoverability-Off candidate has themselves sent a pending request to the searching user.

Example:

John has discovery Off.

John → Richard is pending.

Richard searches John.

John may appear with:

**Accept**

However:

Richard → John is pending.

John then turns discovery Off.

John must disappear from Richard's non-friend search.

Therefore do **not** use a condition equivalent to:

`discoverable OR has_outgoing_request_from_me OR existing_friend`

Instead plan the equivalent of:

`discoverable OR existing_friend OR candidate_sent_pending_request_to_current_user`

Be precise about sender/receiver direction.

Include automated test cases specifically proving both directions.

---

## Correction 3 — multi-word names need a concrete split strategy

The existing database has separate:

* `first_name`
* `last_name`

Global search must support:

* Mary Ann Smith
* Ana Maria De La Cruz
* John Van Buren
* Anne-Marie Smith
* Battle-Baxter
* O'Connor

Do not assume:

`first token = first_name`

and

`everything else = last_name`

For a multi-token query, plan how to evaluate plausible split points against the stored first and last name fields.

Example:

`Mary Ann Sm`

Potential interpretation:

`first_name = Mary Ann`

`last_name prefix = Sm`

Likewise:

`Ana Maria De La`

must be evaluated sensibly against stored first/last values.

The plan should specify:

* How query tokens are normalized
* How possible first/last split points are generated
* How those split points are compared against normalized stored first_name / last_name
* How match quality is scored
* How incorrect combinatorial explosion is avoided
* How this behaves with hyphenated/apostrophe names

Do not make the parsing brittle.

---

## Correction 4 — normalization must have a real database/query strategy

Do not simply say:

"Create a Python `normalize_name()` helper and apply it to stored names at query time."

A Python helper cannot automatically execute against all stored PostgreSQL rows inside a normal SQL query.

Do not plan to load the entire User table into Python and normalize every user in memory.

The revised plan must specify a technically valid search strategy for:

* Lowercase/case-insensitive comparison
* Accent/diacritic-insensitive matching
* Apostrophe normalization
* Hyphen normalization
* Whitespace normalization
* Prefix matching

Evaluate the current BaseLodge/PostgreSQL setup and recommend the smallest safe option.

Possible approaches may include:

* PostgreSQL `unaccent` if already available/appropriate
* SQL expressions using `lower`, `replace`, etc.
* A normalized searchable column
* Functional index
* Another PostgreSQL-native solution

Do not introduce a new database extension casually without determining whether it is appropriate for BaseLodge's deployment environment.

If a migration or normalized field is warranted, include it explicitly in the plan.

Explain:

* Query shape
* Index strategy
* Performance at current BaseLodge scale
* How displayed names retain their stored spelling
* How tests validate normalization behavior

---

## Correction 5 — do not pre-decide Invitation upsert behavior

The earlier plan assumed the existing Invitation should simply be updated/upserted after cooldown.

Do not lock in that design before verifying actual database semantics.

First plan explicit tests for the existing constraint:

`UNIQUE(sender_id, receiver_id, trip_id)`

where friend requests use:

`trip_id = NULL`

Determine how BaseLodge's actual PostgreSQL configuration behaves for:

* pending A→B
* declined A→B
* cancelled A→B
* another A→B insert
* reverse B→A insert
* accepted/removal/reconnect

Then decide whether the best history-preserving strategy is:

* reuse/reset an existing Invitation
* create a new Invitation
* adjust the constraint
* or another minimal relationship-history mechanism

Regardless of the storage choice, the final architecture must guarantee:

* No duplicate active requests
* No simultaneous A→B and B→A pending requests
* Re-request allowed after 24-hour cooldown
* Historical resolved records handled intentionally
* Push notification fires only for a legitimate new request
* Cooldown cannot be bypassed

The plan must explain the chosen approach and why.
