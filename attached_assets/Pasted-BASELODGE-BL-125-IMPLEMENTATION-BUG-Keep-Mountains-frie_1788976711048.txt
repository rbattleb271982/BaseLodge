==================================================
BL-125 OBJECTIVE
==================================================

Fix stale friend-derived counts in the authenticated Mountains experience without changing existing count semantics.

The investigation established three stale layers:

1. process-local `_mountains_cache` containing personalized `/api/mountains-data`
2. browser reuse from `Cache-Control: private, max-age=300`
3. frontend/bfcache reuse of retained `RESORTS` state

The smallest safe fix is:

- stop caching the complete personalized Mountains response;
- preserve caching of stable resort reference data;
- compute existing `friend_count` live on each API request using the existing bulk query;
- make the personalized response non-storable;
- stop relying on stale ETag/304 behavior;
- fetch Mountains data fresh on every page load/pageshow, including bfcache restoration;
- preserve all existing product semantics.

==================================================
DO NOT CHANGE COUNT SEMANTICS
==================================================

Mountains list `friend_count` must continue to mean:

- reciprocal friends only
- count distinct friend trip OWNERS
- public trips only
- active or legacy NULL lifecycle only
- resort_id required
- past/current/future all count
- trip_status irrelevant
- participant RSVP irrelevant
- participant-specific dates irrelevant
- one friend counts once per resort
- completed/cancelled excluded
