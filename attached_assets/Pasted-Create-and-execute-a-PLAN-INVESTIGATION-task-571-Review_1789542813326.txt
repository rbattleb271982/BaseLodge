This is an evidence-based product architecture review of how BaseLodge currently communicates notifications, requests, invitations, pending actions, unread state, and other user-attention items across the application.

The goal is to determine whether BaseLodge currently has a coherent distinction between:

1. Something the user should KNOW

5. Something that belongs contextually on another screen
6. Something that belongs in notification history

## 4. Distinguish notification state from actionable state

For every event determine whether BaseLodge currently treats it as:

### Informational
Example conceptual model:
“Richard accepted your friend request.”

No action is required.

### Actionable
Example conceptual model:
“Sarah invited you to Aspen.”

The user must respond.

### Contextual state
Example conceptual model:
A pending invitation is visible on the relevant Trip because that is where the underlying relationship exists.

### Historical
Example conceptual model:
An event remains useful as a record after its actionable state is resolved.

### Ephemeral feedback
Example conceptual model:
“Equipment updated.”

Useful immediately, but not necessarily appropriate as persistent notification history.

These are analytical categories only. Do not change product behavior.

## 13. Classify duplication

Every repeated attention item should be classified as:

### A. Useful contextual repetition
The same underlying state appropriately appears in multiple contexts.

### B. Redundant duplication
The same item is presented multiple times without additional user value.

### C. Inconsistent duplication
Multiple surfaces represent the same state differently or become inconsistent.

### D. Necessary action persistence
The same unresolved action remains visible in multiple appropriate places because the user still needs to act.

### E. Historical + contextual coexistence
Notifications retain the historical event while another surface owns current state.

Do not classify repetition as bad solely because it exists.

## 14. Identify missing connections

Only identify missing connections supported by observed product behavior.

Examples of the TYPE of issue to investigate, not predetermined findings:

- An actionable invitation exists but is difficult to discover.
- A resolved action still looks actionable in Notifications.
- A badge represents unread notifications while the user interprets it as pending actions.
- Home surfaces one request type but not another equivalent type.
- Notification deep links do not take the user to the useful resolution context.
- Failure leaves the user uncertain whether an action succeeded.

Ground every finding in evidence.
