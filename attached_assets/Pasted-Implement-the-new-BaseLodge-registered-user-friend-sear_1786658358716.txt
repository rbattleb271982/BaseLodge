Implement the new BaseLodge **registered-user friend search and friend discovery privacy setting** based on the investigation already completed and the product decisions below.

Use the existing architecture wherever possible. The investigation found that BaseLodge already has the Friends page, confirmed `Friend` relationships, pending `Invitation` records, request acceptance/decline flows, push notification events, and profile settings patterns that can be reused.

This is now an **implementation task**, not another investigation.

Do not commit, push, publish, or deploy anything.

At the end, provide a detailed implementation report and test results.

# 1. Core product behavior

BaseLodge already has a **Search friends** field on `/friends`.

We want that same field to support two distinct behaviors.

### While typing

Typing into the field should continue to filter the user's **existing friends only**, using the current client-side behavior.

Do not run a BaseLodge-wide user search automatically as the user types.

### When Enter/Search is pressed

If the entered name meets the minimum requirements, pressing Enter/Search should run a server-side search across eligible BaseLodge users.

When global search starts:

* Replace the current Friends list with a loading state.
* When results arrive, replace the loading state with global search results.
* Do not leave the normal friend list visible above the global results.
* Clearing the search should return the user to the normal Friends view.

If there are no results, display:

**No BaseLodge users found**

# 2. Global-search eligibility

A global BaseLodge search requires:

* At least 2 characters in the first-name portion
* At least 2 characters in the last-name portion
* At least two name components overall

Examples:

`John`
→ filters current friends only

`John S`
→ filters current friends only

If Enter/Search is pressed, show:

**Enter more letters to search BaseLodge.**

`Jo Sm`
→ valid global search

`John Sm`
→ valid global search

`John Smith`
→ valid global search

Do not require BaseLodge to somehow know that the user has finished typing the person's complete first name. A real person's first name could actually be "Jo."

# 3. Name matching behavior

Global search should be forgiving about formatting but should still match names from the beginning rather than arbitrary substrings.

### Required behavior

* Case-insensitive
* Accent/diacritic-insensitive
* Hyphen tolerant
* Apostrophe tolerant
* Extra spaces normalized
* Preserve the person's actual stored spelling when displaying the result

Examples:

`john smith` → matches **John Smith**

`JOHN SMITH` → matches **John Smith**

`Jose Garcia` → matches **José García**

`OConnor` → matches **O'Connor**

`Battle Baxter` → matches **Battle-Baxter**

`Anne Marie` → can match **Anne-Marie**

### Prefix behavior

Name components must match from the beginning.

For example:

`Jo Sm` can match a name beginning with those components.

Do not make arbitrary internal substring matching such as:

`ohn mith` → John Smith

### Multi-word names

Support multi-word first names and surnames, including examples such as:

* Mary Ann Smith
* Ana Maria De La Cruz
* John Van Buren
* Jean-Luc Martin
* Battle-Baxter

Do not implement a brittle rule that assumes every name is exactly two words.

Create a reusable normalization/matching helper so this logic is testable.

# 4. Global result format

In global-search mode, **everyone uses the same minimal result format**, including existing friends.

Do not use the richer normal friend card in global search.

Format:

**John Smith · Colorado**              **Connect**
4 mutual friends

Existing friend:

**John Smith · Colorado**              **Connected**
4 mutual friends

Outgoing request:

**John Smith · Colorado**              **Requested**
4 mutual friends

Incoming request:

**John Smith · Colorado**              **Accept**
4 mutual friends

During cooldown:

**John Smith · Colorado**
4 mutual friends

There is no action on the right during cooldown.

### Home state

If `home_state` exists:

**John Smith · Colorado**

If it does not exist:

**John Smith**

Do not show a dangling separator.

Users without a home state should still appear in search.

### Mutual friends

* 1 → **1 mutual friend**
* 2+ → **X mutual friends**
* 0 → show no mutual-friends text

However, keep the result rows a consistent fixed height even when there are zero mutual friends.

Mutual count is display-only.

Do not make it clickable.

Do not expose the identities of mutual friends.

# 5. Search-result ranking

Rank results primarily by **best name match**.

For equivalently strong name matches, rank by **number of mutual friends descending**.

Do not automatically rank existing friends above non-friends.

Do not implement 3rd-degree or 4th-degree graph ranking at this time.

Mutual friends are enough for version 1.

The results should be scrollable.

Use a reasonable backend safety limit based on the current architecture so a search cannot return an unlimited database dump, but do not artificially restrict the UX to only 5 or 10 visible matches.

# 6. Existing friends in global search

Existing friends should appear if they match the global search.

They use the same minimal global-result row and show:

**Connected**

`Connected` is a non-clickable status.

# 7. Connect behavior

For a non-friend with no active request and no cooldown:

Show:

**Connect**

When the user taps Connect, do **not** send immediately.

Show confirmation including the person's name.

If state exists:

**Send friend request to John Smith in Colorado?**

If no state exists:

**Send friend request to John Smith?**

Actions:

* Cancel
* Send Request

Only send after confirmation.

After the request succeeds:

* Change **Connect** → **Requested** immediately in place.
* Do not show a success toast.

If sending fails:

* Leave the button as **Connect**
* Show a brief error such as:

**Couldn't send friend request. Try again.**

# 8. Shared friend-request backend logic

The investigation found that the current friend-request route is email-based even though the search flow should operate by user ID.

Do **not** duplicate the business logic into two separate implementations.

Extract/refactor the core "create friend request" behavior into a shared helper/service that handles:

* Self-request prevention
* Existing friendship detection
* Existing outgoing request detection
* Existing incoming request detection
* Cooldown enforcement
* Invitation creation/update
* Notification emission
* Validation
* Transaction handling

Then:

* The existing email-based request flow can reuse it.
* The new user-ID-based search flow can reuse it.

The two entry points should not be allowed to drift apart.

# 9. Incoming pending requests

If the candidate has already sent the current user a pending friend request:

Show:

**Accept**

Do not show Connect.

Do not allow BaseLodge to create a reverse request.

This fixes an issue found during the investigation where opposite-direction pending requests can currently coexist.

The backend must prevent that state, not merely the UI.

### Accept behavior

Tapping **Accept** should accept immediately.

No confirmation dialog.

Reuse the existing acceptance logic.

After success:

* Change the result immediately to **Connected**
* Recalculate visible mutual-friend counts because the newly created friendship may change counts for other displayed users

Do not require a full page reload.

# 10. Outgoing pending requests

If the current user already sent a request:

Show:

**Requested**

Requested should be clickable.

When tapped, ask for confirmation:

**Cancel friend request?**

Actions:

* Keep Request
* Cancel Request

If cancelled successfully:

* Remove the Requested status
* Start the 24-hour cooldown
* Leave the person visible in search
* Show no action on the right during cooldown

If cancellation fails:

* Keep showing **Requested**
* Show a brief error
* Do not pretend the request was cancelled

Create/reuse the appropriate authenticated backend endpoint for cancelling an outgoing pending request.

Only the sender can cancel their request.

# 11. 24-hour request cooldown

Implement a **24-hour cooldown** following any of these events:

1. Recipient declines a request
2. Sender cancels their outgoing request
3. Two users remove an existing friendship

During the 24-hour cooldown:

* Both users may still appear in eligible search results
* Normal identifying information remains visible
* Mutual-friend counts remain visible
* There is **no Connect action**
* Do not show "try again later"
* Do not display remaining cooldown time
* Do not explain the cooldown in the UI

After 24 hours:

* Connect becomes available automatically the next time the user searches
* No manual reset is required

### Push-notification protection

This cooldown is important because friend requests generate push notifications.

Enforce the cooldown on the backend.

Do not rely on hiding the button in the UI.

A user must not be able to bypass the cooldown by manually calling the endpoint.

# 12. Re-request behavior

The investigation raised a question around the `Invitation` unique constraint and whether declined/cancelled records could prevent later re-requests.

Before changing that database behavior:

1. Verify the actual current behavior with tests against the database semantics used by BaseLodge.
2. Do not assume that a nullable `trip_id` behaves a certain way under the unique constraint.
3. Implement the new 24-hour re-request rule deliberately.

After the cooldown, the same pair must be able to connect again.

Use the cleanest architecture based on the current `Invitation` model:

* reuse/update an existing resolved Invitation where appropriate, or
* create a new Invitation if the database model safely permits it

Preserve history if practical.

Do not introduce unnecessary complexity.

# 13. Declines

If someone declines a friend request:

* Do not notify the requester that they were declined.
* Remove the outgoing **Requested** state when the requester next receives fresh relationship state.
* Start the 24-hour cooldown.
* During cooldown the person may still appear in search, but with no Connect action.
* After cooldown, Connect becomes available again.

# 14. Cancellation

If the sender cancels their request before it is accepted:

* The request should disappear immediately from the recipient's pending requests the next time that state is refreshed.
* Do not display cancelled-request history in the Friends UI.
* Start the 24-hour cooldown.

# 15. Removing an existing friendship

Existing unfriend behavior should continue removing the confirmed friendship in both directions.

After friendship removal:

* Apply a 24-hour cooldown between those users.
* They may still find one another in search.
* Neither has a Connect action until the cooldown expires.
* Mutual count remains visible normally.

After 24 hours, either user can send a new request.

# 16. Mutual-friend calculation

Use only confirmed `Friend` relationships.

Do not count:

* Pending requests
* Declined invitations
* Cancelled invitations
* Removed friendships

A person who has opted out of friend discovery may still count anonymously as a mutual friend if they are genuinely a confirmed friend of both people.

For example:

Sarah has `discoverable_in_friend_search = False`.

Richard and John are both confirmed friends with Sarah.

John may still display:

**1 mutual friend**

Do not reveal that Sarah is the mutual.

### Performance

Do not create an N+1 query for every result.

Use a batched query/helper to calculate mutual counts for the candidate set efficiently.

After a friendship is accepted from the search results, recalculate the visible mutual counts immediately.

# 17. Friend Discovery privacy setting

Add a new setting to Profile Settings directly **above Notifications**.

Create a small section titled:

**Friend Discovery**

Setting:

**Show me in friend search**

Description:

**Allow other BaseLodge members to find you by name. Turning this off does not affect your existing friends.**

Use the existing Profile Settings save behavior.

Do not create a special instant-save mechanism.

The setting saves when the user saves the rest of Profile Settings.

### Default

Default to **On** for:

* Existing users
* New users

Use a safe migration/default strategy.

### When turned Off

Once the profile save succeeds:

* The user immediately stops appearing in non-friend global searches.
* Existing friends can still find them when searching.
* Existing friendships remain completely unaffected.
* The user can still search for other people.
* The user can still send friend requests.
* Incoming/outgoing Invitation records are not deleted.
* Their confirmed friendships may still anonymously contribute to other people's mutual counts.

### Special pending-request rules

If a user with discovery Off sends someone a friend request:

* They may still appear to that recipient in search while that incoming request is pending because they intentionally initiated contact.

If someone already sent a request **to** a user who subsequently turns discovery Off:

* That user should disappear from the requester's non-friend global search.
* The underlying pending request still exists.

If they turn discovery back On while the request remains pending:

* They should reappear showing **Requested**.

# 18. Global-search visibility rules

Exclude:

* Current user
* Users who have opted out of search, except where the incoming-request exception above applies
* Any users the existing architecture already considers invalid/ineligible

Do not invent account-state systems that do not exist.

The investigation found no current blocking system and no dedicated deleted/suspended flags.

Do not add blocking as part of this feature.

Make the search architecture easy to extend with blocked-user exclusions later.

# 19. Data exposed for non-friend/global search

Return only the data needed by the UI:

* User ID
* First name
* Last name
* Home state
* Mutual friend count
* Relationship state
* Cooldown/action availability as necessary

Do not expose:

* Email
* Phone
* Trips
* Upcoming trip count
* Passes
* Skill level
* Rider type
* Equipment
* Wish lists
* Auth-provider data
* Notification preferences
* Other private user attributes

Even though some richer fields are visible to confirmed friends, global search should remain minimal.

# 20. Search privacy and abuse protections

Global user search must:

* Require authentication
* Require the minimum name input described above
* Require explicit Enter/Search rather than firing on every keystroke
* Have a reasonable server-side result cap
* Be rate-limited
* Validate input length
* Prevent user enumeration as reasonably as possible
* Return only explicitly selected response fields

Do not add pagination that allows someone to trivially scrape the entire user base.

Use a rate limit appropriate for legitimate interactive search without making normal use frustrating.

# 21. Search loading/error handling

When Enter/Search triggers global search:

1. Immediately switch from the current friends list to a loading state.
2. Fetch global results.
3. Replace loading state with results.

If there are no results:

**No BaseLodge users found**

If the request itself fails:

Show an appropriate short error state and allow the user to retry.

Prevent stale-response bugs.

Example:

* User searches one name
* Quickly changes query and searches another
* The older/slower request must not overwrite the newer results

Use cancellation, request IDs, or another safe approach.

# 22. No separate search section label

Do not add:

* People on BaseLodge
* Search BaseLodge
* Discover People

There should be **no separate section heading** for global results in this version.

The results themselves are sufficient.

# 23. Invite behavior remains separate

Do not change the existing **Invite** functionality.

The investigation confirmed that Invite is for onboarding people who are not yet on BaseLodge, while this new flow connects users who already have accounts.

Keep those systems conceptually separate.

# 24. Existing notifications

Reuse the existing friend-request notification architecture.

The investigation found:

* `FRIEND_REQUEST_CREATED`
* `FRIEND_REQUEST_ACCEPTED`

are already implemented and wired to push delivery.

Do not create duplicate event constants or notification specs.

The shared create-request helper should emit the existing `FRIEND_REQUEST_CREATED` event.

Existing acceptance behavior should continue using `FRIEND_REQUEST_ACCEPTED`.

Verify notification dedupe behavior alongside the new 24-hour cooldown.

Use the existing Friends page visual language.

Primary line:

**X mutual friend(s)**
