1. ADD A REPOSITORY-OWNED HISTORY CONTRACT

Create a focused architecture/documentation file in the most appropriate existing repository documentation location.

Do not invent a new documentation structure if the repo already has an established architecture/docs convention.

The document must define the BaseLodge history-event contract covering:

EVENT IDENTITY
- immutable database-generated event ID
- semantic subject keys identify a stream, not an event
- no external/client idempotency key by default
- legitimate repeated lifecycle transitions receive new event identities

SUBJECTS
- explicit privacy/lifecycle subjects
- required subject FKs where appropriate
- canonical ordering for unordered pairs
- deletion semantics for every subject

ACTORS
- authenticated actor supplied for user-driven transitions
- nullable actor for defined system actions and anonymization
- actor and subject are distinct concepts
- actor never implies authorization or visibility

SOURCES
- finite, domain-specific source vocabulary
- source describes trusted product path
- prohibit arbitrary reason/metadata/request-payload capture unless separately approved

TIMESTAMPS
- server/database-generated timezone-aware timestamps
- deterministic ordering by timestamp then event ID
- caller-supplied historical timestamps allowed only for separately approved import/backfill

APPEND-ONLY / CORRECTIONS
- ordinary product code does not rewrite historical business fields
- correction requires a defined compensating event or separately reviewed maintenance
- privacy deletion and actor anonymization are explicit exceptions
- privacy erasure must not fabricate product transitions

CURRENT STATE VS HISTORY
- every domain explicitly defines authoritative current-state truth
- history does not automatically become authorization, visibility, eligibility, or current-state truth
- reconstruction only where recording is complete
- unknown-before-cutover semantics are mandatory

BACKFILL
- default is no backfill
- backfill requires reliable event-level evidence, provenance, deterministic idempotency, privacy handling, and rollback validation
- current-state rows, dates, notifications, analytics, or surviving relationships alone are insufficient evidence

DUPLICATE PREVENTION / CONCURRENCY
- lock authoritative state deterministically
- refresh under lock
- compare current state to requested transition
- emit at most one event for an actual state change
- current-state mutation and history write share one transaction
- constraints validate shape/vocabulary, not legitimate repeated lifecycles

RETENTION / PRIVACY
- define deletion subjects per stream
- erase/anonymize history when required by privacy deletion
- actor-only deletion nulls actor on surviving events
- ordinary cancellation/removal is different from account/privacy erasure
- avoid copied PII

INDEXING / QUERY PATTERNS
- indexes follow demonstrated query patterns
- baseline subject key + event time
- event ID is ordering tie-breaker
- only add actor/event-type/secondary indexes when demonstrated
- state-at-time queries preserve unknown-before-cutover semantics

AUDITABILITY
- bounded event types
- bounded sources
- explicit actor provenance
- immutable timestamps
- avoid PII copies
