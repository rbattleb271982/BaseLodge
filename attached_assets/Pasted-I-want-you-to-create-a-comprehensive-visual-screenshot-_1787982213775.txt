## OBJECTIVE

Create a well-organized, representative screenshot library showing what BaseLodge looks like today, with particular emphasis on the mobile experience.

The screenshots should give an external product designer enough visual context to understand the current BaseLodge product and evaluate its design without needing access to the codebase.

## ABSOLUTELY NO APPLICATION CHANGES

Do not change:

* application code
* HTML/templates

* functionality

* seed data

## WHAT TO CAPTURE

Focus exclusively on the CONSUMER-FACING BaseLodge product.

Do not capture Admin or internal analytics/operations tools.

Capture representative examples of the major BaseLodge experiences, including:

### Primary product

* Home/feed
* Trips
* Trip creation
* Trip detail
* Trip planning
* Mountains
* Mountain detail
* Friends/social
* Friend profiles
* Profile
* Settings
* Notifications
* Invite/connect experiences
* Trip ideas/availability/wishlist/overlap experiences where visually distinct

### Authentication and onboarding

Capture representative visually distinct screens for:

* Login
* Signup
* Password recovery/reset
* Onboarding
* Identity/profile setup
* Location setup
* Pass selection
* Relevant invite landing experiences

### Important states

For major product areas, capture alternate states only when they create a materially different visual experience.

Examples include:

* populated vs. empty
* owner vs. participant
* public vs. private
* modal or bottom-sheet open
* different tabs
* important creation/editing flows
* meaningful confirmation states
* materially different social states

Do NOT create screenshots of every possible functional permutation.

This is not QA documentation.

If two states look essentially the same from a design perspective, one representative screenshot is enough.

## PRIORITIZE MOBILE

BaseLodge is primarily a mobile product.

The screenshot library should therefore provide especially strong coverage at a realistic narrow mobile/iPhone viewport, including the complete visible viewport and relevant safe-area/navigation treatment.

Also capture representative desktop versions of major screens so the external reviewer can understand responsive behavior.

You do not need a desktop duplicate of every minor mobile state when it adds no meaningful visual information.

## SCREENSHOT QUALITY

Screenshots should:

* accurately represent the current running BaseLodge product
* use realistic existing development/test data where available
* show complete UI without browser debugging overlays
* avoid obviously broken intermediate loading states unless that loading state itself is intentionally being documented
* capture the full page when useful
* capture the viewport when that better represents the actual mobile experience
* preserve the current app exactly as it exists

Do not modify data merely to manufacture a screenshot state.

If a requested state cannot safely be reached using existing data, document that rather than changing data.
