# BL-162 — Progressively Load Mountain Detail Social Intelligence

Use BUILD mode.

This is a performance improvement to the existing Mountain Detail experience.

Do not redesign Mountain Detail.
Do not change the approved visual system.
Do not change social eligibility, privacy, trip visibility, counts, ordering, or user-facing semantics.

## Goal

Mountain Detail currently blocks the initial page response on secondary social intelligence even though the core mountain/pass content can render independently.

Improve perceived Mountain Detail performance by rendering the core mountain experience first and progressively loading appropriate secondary social intelligence afterward.

The current task identifies these secondary areas:

- Going
- Interested
- Availability
- Been Here
- Want to Go
- related friend/social intelligence
- qualifying trips/participants where applicable

The implementation must preserve the exact existing product behavior and privacy rules.

## Important context

Notion BL-162 states:

- Representative current profile: approximately 13 SQL statements
- Approximately 24.8 KB HTML
- Approximately 7 ms warm in-memory
- Expected impact: High for large social graphs, Medium at current scale
- Dependencies: BL-133 and BL-146

First verify those dependencies/current architecture rather than assuming their historical state.

B. SECONDARY / CANDIDATE FOR PROGRESSIVE LOAD

Core content must remain immediately available.

# 3. Design the smallest progressive-loading boundary

Based on the audit, choose the smallest architecture that materially reduces blocking work.

Prefer grouping related secondary intelligence into a small number of bounded requests rather than creating many tiny endpoints.

Avoid:

- one endpoint per row
- one request per friend
- one request per trip
- N+1 behavior
- excessive browser waterfalls
- duplicated eligibility/privacy logic
- duplicated templates
- client-side reconstruction of server-owned business rules

Where practical, reuse existing services and server-rendered partials.

The initial Mountain Detail request should no longer calculate secondary intelligence that has been moved behind progressive loading.

Simply hiding already-rendered content with JavaScript does NOT satisfy BL-162.

# 6. Query and scaling requirements

The progressive implementation must remain bounded.

Specifically verify:

- no per-friend queries
- no per-trip queries
- no per-participant hydration
- no new N+1 behavior
- initial Mountain Detail query count decreases when secondary intelligence is deferred
- progressive request query count remains bounded as social graph size increases

Add or update query-budget coverage where appropriate.

Report before/after statement counts separately for:

A. initial Mountain Detail request
B. progressive social request(s)
C. total page hydration

The goal is primarily to reduce blocking initial work, not merely move an inefficient query pattern to another endpoint.

# 7. Progressive-load behavior

Implement robust browser behavior.

Verify:

- secondary intelligence loads after the core page
- each section renders once
- repeated visibility/page lifecycle events do not create duplicate content
- browser back/forward cache behavior remains sane
- refresh works
- authentication failures are handled safely
- failed secondary requests do not break the core Mountain Detail page
- no infinite retry behavior
- no duplicate analytics events caused solely by hydration
- no console errors

Because BaseLodge uses Capacitor, consider both normal browser visibility and Capacitor-style lifecycle behavior where existing infrastructure supports it.

Do not add native-only dependencies or require a new iOS/Android build unless absolutely necessary. This task should remain web-layer compatible.
