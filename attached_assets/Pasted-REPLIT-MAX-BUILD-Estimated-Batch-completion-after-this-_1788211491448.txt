==================================================
PRIMARY GOAL
==================================================

Eliminate participant-scaling database queries and avoidable repeated queries on authenticated Trip Detail without changing:

- UI
- content
- authorization
- privacy
- RSVP behavior
- planning behavior
- overlap behavior
- lodging/stay behavior
- resort behavior
- terminal-trip behavior

Measured baseline shows organizer Trip Detail growing approximately as:

19 + N

because participant User records are lazily loaded.

The implementation must make query behavior effectively constant as visible participant count grows.

==================================================
CANONICAL MEASURED BASELINE
==================================================

Warmed organizer requests:

- 1 Going participant: 20 queries
- 5 Going participants: 24 queries
- 20 Going participants: 39 queries

Other measured scenarios:

- Active participant, 5 participants: 22
- Terminal trip, 2 participants: 21
- Overnight/stay trip, 2 participants: 21

Do not mix cold startup/auth/cache queries into cardinality assertions.

==================================================
ROSTER PRIVACY FIRST
==================================================

Preserve BL-133 exactly.

For non-organizers:
query only Going and Interested participant rows.

For organizers:
query Going, Interested, Pending, and Declined.

Never include Removed in the user-facing roster query.

Important:
filter participant rows in SQL BEFORE eager-loading participant User records.

Do not load unauthorized identities and hide them later.

==================================================
BATCH PARTICIPANT USERS
==================================================

Replace participant-user lazy loading with bounded eager loading.

Preferred approach:

- privacy-filter participant rows first
- use selectinload for participant User relationships

Do not use a large joined eager-load that multiplies rows.

The participant query should remain narrow and auditable.

==================================================
REUSE PARTICIPANT DATA
==================================================

Reuse the already-loaded participant rows for:

- roster grouping
- group signals
- organizer participant context

Do not re-query the participant collection for group signals.

Do not re-query the organizer participant row if it is already present.

A narrow compatibility fallback is acceptable only if the expected organizer row is genuinely absent.

==================================================
PLANNING PREVIEW AUTHORS
==================================================

The planning preview is capped at three posts.

Batch-load authors for that limited preview.

Do not eager-load the full planning collection.

Target behavior:

1 versus 3 distinct preview authors should add no more than one additional query.

Do not weaken services/visibility.py or duplicate its authorization logic.

Do not load unrelated users.
