BL-78 — Preserve RSVP status transitions

PLAN / INVESTIGATION ONLY.

Do not modify code, tests, database state, migrations, configuration, dependencies, or data.
Do not commit anything.
Do not access or modify Production.
Do not run migrations against Development or Production.

GOAL

BaseLodge currently retains the latest RSVP state. BL-78 should preserve meaningful RSVP status transitions over time while keeping the existing current RSVP state as the operational source used by the product.

Notion requirements:

- Record meaningful RSVP status transitions with timestamps and trip/user references.
- Current RSVP remains the operational source used by Trip Detail.
- Transition history is internal.
- Do not create a user-facing activity log.
- Respect account deletion/privacy requirements.

USER DATA SAFETY GATE

This extends persisted RSVP user data.

Before implementation we need:
- migration/compatibility review;
- rollback considerations;
- duplicate-event prevention;
- tests;
- verification against existing RSVP records.

Dependency:
Build on the existing RSVP foundation and invitee-response work.

IMPORTANT CURRENT BASELODGE CONTEXT

BL-34 and subsequent Trip Detail RSVP work already established the current RSVP behavior. Preserve it.

BL-70 introduced a season-specific pass-history architecture, but its Development/Production migration and backfill are currently DEFERRED.

Do not depend on the BL-70 migration.
Do not resume BL-70.
Do not attempt to solve BL-70's backup/migration issue as part of BL-78.

There is also one known unrelated migration test failure caused by a guarded PostgreSQL migration being exercised against SQLite. Do not fix or expand scope into that issue.

INVESTIGATE THE CURRENT RSVP ARCHITECTURE

1. Identify every model/table currently involved in trip participation, invitations, attendance, and RSVP state.

For each relevant model report:
- table/model name;
- primary key;
- user reference;
- trip reference;
- current status/state fields;
- timestamps currently available;
- uniqueness constraints;
- foreign-key/cascade behavior.

2. Identify the canonical current RSVP state.

Determine:
- which field/model Trip Detail treats as authoritative;
- all valid current RSVP statuses;
- any legacy statuses still supported;
- how organizer participation differs from invited/guest participation;
- whether attendance dates or other participant metadata are coupled to RSVP status.

Do not assume the status vocabulary. Derive it from the current code and tests.

3. Trace EVERY RSVP mutation path.

Search the repository for every place RSVP/participant status can change, including:
- invite acceptance;
- interested/maybe-style responses if applicable;
- going responses;
- declines;
- organizer actions;
- participant removal;
- reinvitation;
- API routes;
- web forms;
- native-facing endpoints;
- admin/internal paths;
- trip creation paths that establish an initial participant state.

For each mutation path report:
- endpoint/function;
- old state;
- possible new state;
- where commit occurs;
- whether notifications/analytics/messaging are triggered;
- whether repeated/idempotent requests are possible.

4. Build the actual RSVP transition matrix.

Based strictly on current BaseLodge behavior, enumerate meaningful transitions such as:

old_status -> new_status

Distinguish:
- initial creation from a true transition;
- same-state writes/retries;
- removals;
- declines;
- legacy-state normalization;
- organizer states if applicable.

Recommend which events BL-78 should record and which should NOT create history rows.

5. Investigate existing history/event patterns.

Search for existing BaseLodge models/tables that already preserve transitions or append-only events.

Determine whether BL-78 should:
A. use an existing generic event/history architecture;
B. use a dedicated RSVP transition table;
C. wait for another planned foundation task.

BL-140 exists separately to define broader append-only history/event conventions.

Assess explicitly whether BL-78 can safely proceed before BL-140 without creating architecture we will immediately need to replace.

Do NOT expand BL-78 into BL-140.

6. Propose the minimum safe BL-78 data model.

If a dedicated table is appropriate, propose fields and constraints.

At minimum evaluate whether it needs:
- id
- trip_id
- user_id
- previous_status
- new_status
- changed_at
- actor_user_id
- source/action
- idempotency/deduplication identifier

Do not assume all are necessary.

Explain the purpose and privacy implications of every proposed persisted field.

7. Duplicate-event prevention.

Determine how history can be recorded exactly once when:
- the same request is retried;
- the requested RSVP already equals the current state;
- transaction retries occur;
- multiple code paths converge on the same state-changing helper;
- concurrent requests occur.

Recommend the narrowest reliable strategy compatible with the existing architecture.

8. Transaction integrity.

Determine how the current-state mutation and transition-history insert can occur atomically.

We must not allow:
- current RSVP changes without corresponding required history;
- history claiming a transition that failed to become current state.

Identify the appropriate transaction boundary.

9. Existing-record/backfill strategy.

BL-78 must preserve transitions going forward.

Investigate whether existing RSVP records contain enough historical information to reconstruct prior transitions.

Do NOT invent historical events.

Recommend whether migration should:
- create no history for existing records;
- create a clearly identified baseline/current-state event;
- or use another defensible approach.

Explain the tradeoff.

10. Privacy and account deletion.

Trace current user/account deletion behavior for RSVP/participant records.

Determine what should happen to BL-78 history when:
- a user deletes their account;
- a trip is deleted;
- a participant is removed from a trip.

The Notion requirement explicitly says to respect account deletion/privacy requirements.

Recommend foreign keys/cascade/anonymization behavior consistent with current BaseLodge policy.

11. Migration safety.

Assess:
- PostgreSQL migration requirements;
- SQLite test compatibility;
- downgrade/rollback behavior;
- indexes/constraints;
- whether migration is additive;
- whether deployment can safely occur before application code or must be coordinated.

Do NOT create the migration yet.

12. Consumer impact.

Confirm that:
- Trip Detail continues reading the current RSVP source;
- no existing UI needs to read history;
- no native iOS/Android change is required;
- no new user-facing activity log is introduced.

Identify any analytics/admin/internal future use, but do not implement it.

13. Testing strategy.

Specify tests required for:
- each meaningful transition;
- same-state writes;
- retries/idempotency;
- transaction rollback;
- concurrent/duplicate protection if relevant;
- account deletion;
- trip deletion;
- existing RSVP compatibility;
- migration upgrade/downgrade;
- current Trip Detail behavior remaining unchanged.

14. Scope/dependency assessment.

Explicitly answer:

- Can BL-78 be implemented independently of BL-70 rollout?
- Should BL-78 proceed before BL-140?
- Does BL-78 require a native app build?
- Does BL-78 require any user-facing UI change?
- Does BL-78 require Production access during implementation?
- Is a backfill actually necessary?
