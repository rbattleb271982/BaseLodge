# Investigate Locked Trip Detail Design Requirements

## What & Why

Perform a read-only engineering investigation against the actual BaseLodge application source to verify the remaining data, state, permission, and interaction assumptions behind the now-locked Trip Detail redesign.

The visual design is already approved.

Do NOT redesign Trip Detail.
Do NOT propose alternative layouts.
Do NOT implement anything.

The purpose of this investigation is to determine exactly which parts of the approved target design are already supported by BaseLodge, which require small presentation changes, which require new backend/data logic, and which should be deferred before implementation begins.

Use the current application code, models, routes, services, templates, tests, and fixtures as the source of truth.

## Critical constraint

The following visual architecture is LOCKED and is not under review:

- Hybrid trip header
- Trip / People / You structure
- Trip opens by default
- Trip Planning is first under Trip
- Two planning items shown by default
- This Mountain section
- People sentence headline
- Participation graphic
- Pass distribution graphic
- Join requests inside People
- Compact grouped participant roster
- Expandable participant status groups
- Invite action in the group header
- You begins with profile-derived Riding + Pass
- You includes trip-specific Status, Availability, Equipment, and Lessons
- Availability is visual
- Equipment and Lessons are directly selectable
- You can show an unanswered-item badge
- Cancel Trip requires confirmation
- Leave Trip requires confirmation
- No Stay section
- No profile photos, avatar circles, profile bubbles, or initials avatars
- No photography
- Past trips retain mountain identity
- Dates are informational, not independently tappable

Do not challenge or replace these decisions.

The task is to verify what is required to build them safely.

# Questions to answer

## 1. This Mountain data support

The approved design shows three rows:

### Other upcoming trips
Example:
`2 friends have Northstar trips planned`

Verify:

- whether BaseLodge can currently query a user's friends who have trips at the same mountain
- whether those trips can be filtered to upcoming only
- whether the current user can see only trips permitted by privacy rules
- whether an accurate unique-friend count can be derived
- whether a destination/list surface already exists for this relation
- whether this requires any schema change

Document exact models, relationships, service/query logic, routes, templates, and relevant tests.

### Friends who have visited
Example:
`6 friends have skied Northstar`

Verify:

- whether BaseLodge currently stores mountain visit/history information per user
- what exactly counts as "visited" or "skied"
- whether it is derived from past trips, an explicit visited-mountain field, history records, or something else
- whether friend-level visited data is already exposed anywhere
- whether a unique-friend count can be produced under current privacy rules
- whether this can be implemented with existing data
- whether the wording "have skied Northstar" is actually supported by the data or whether only "visited" is defensible

Do not assume visited == skied unless the data model proves it.

### Friends with this mountain on their wishlist
Example:
`4 friends want to ski Northstar`

Verify:

- where wishlist data is stored
- whether friend wishlists are visible to the current user
- whether a unique-friend count can be derived
- whether this is already queried anywhere
- whether the current `On N friend(s)' wishlist` logic can be reused
- whether a destination/list route exists or would need to be created
- whether any migration is needed

For all three rows, classify each as:

- SUPPORTED NOW
- SUPPORTED WITH SMALL QUERY/PRESENTATION WORK
- REQUIRES NEW BACKEND LOGIC
- REQUIRES SCHEMA/DATA MODEL CHANGE
- SHOULD NOT BE BUILT FROM CURRENT DATA

## 2. Trip Planning

The locked design shows:

- 2 most recent planning items
- category
- title
- author
- date
- `All ideas`
- `Share an idea or link`

Verify:

- exact model backing Trip Planning
- exact model/field backing category
- supported current category values
- whether `Lodging`, `Travel`, `Terrain`, `Gear`, etc. exist or which are real
- whether title and link are separate fields
- author relationship
- created/published timestamp
- current ordering
- whether the two most recent items can be queried deterministically
- whether there is already a full-list route
- whether "ideas" and "posts" are the same persisted object or different concepts

- who may read planning
- who may create planning content

Explicitly verify the approved permission rule:

- random non-participant friend: NO Trip Planning access

- Going / Interested / Organizer: READ + CONTRIBUTE

If current behavior differs, document the delta precisely.

- Organizing
- Going
- Interested

- whether Not going persists a declined status or removes participation

## 4. People counts and graphics

The People design requires:

- total associated people
- Going count
- Interested count
- Invited count

Verify:

- which participation states count toward "people on this trip"
- whether organizer is included in Going, separate, or both
- how to avoid double-counting organizer
- whether declined/removed/cancelled people are excluded
- whether invited users have profile/pass data available
- whether all associated users can be joined efficiently in one query

For the pass distribution:

- identify the canonical pass field/model
- enumerate actual current pass values
- verify whether users can have multiple passes
- verify how "No pass" is represented
- determine whether the approved graphic can be computed without a migration
- identify edge cases such as multiple passes or missing values

Do NOT introduce pass compatibility logic.

The approved design only needs group distribution.

## 9. You — availability

This is critical.

The target design compares the trip's actual dates to the current user's stored availability.

It needs to support:

- all trip days available
- partial availability
- no availability entered
- Add availability
- Update availability

Verify:

- exact availability model
- whether availability is season-scoped
- representation of ranges vs individual days
- timezone/date semantics
- whether partial-day or full-day concepts exist
- how overlap with a trip date range should be computed
- whether trip start/end dates are inclusive
- whether a trip date span of Jan 15–18 means 4 calendar days for this purpose
- whether availability is currently editable from another context
- whether the existing availability editor can be reused from Trip Detail
- whether inline modification requires a new route/component/API

Important:

Availability is allowed on You because it is the current user's own availability.

Do NOT expose other users' raw availability.

## 12. You attention badge

when trip-specific questions are unanswered.

For now, only:

- Equipment
- Lessons

should count.

Availability does NOT count toward the badge.

Verify:

# Scope classification

For every target requirement above, classify implementation as:

### A — Presentation only
Existing data + existing actions. Mostly template/UI changes.

### B — Small backend/query extension
Existing schema supports it, but query/service/API work is needed.

### C — New state/behavior logic
Requires new authorization, transition, or business logic.

### D — Schema/migration required
Existing data model cannot support the approved behavior honestly.

### E — Unsupported / should defer
Current data cannot justify the feature or the requirement is unsafe.
