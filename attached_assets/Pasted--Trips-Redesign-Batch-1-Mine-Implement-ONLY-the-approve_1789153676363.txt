2. MONTH GROUPING
==================================================

Mine is ALWAYS grouped chronologically by month.

No threshold.

Use:

JANUARY
FEBRUARY
MARCH

etc.

Within a month, row dates should omit the repeated month when possible:

12–15
20–21

For cross-month trips, keep the range understandable:

24–Mar 1

Sort deterministically by trip start date and existing stable tie-breaker behavior.

==================================================
3. MINE PROJECTION
==================================================

Build one bounded, explicit Mine display projection.

Include:

- organizer-owned active/upcoming trips
- participant Going trips
- participant Interested trips
- pending invitations

Exclude from the active upcoming ledger:

- Declined
- Removed
- cancelled/terminal trips
- inappropriate historical rows

Avoid duplicate trips where the viewer is represented through more than one relationship.

Do not use the current `active_guest_count` label semantics blindly.

The readiness audit established that current Trips counts are inconsistent with Trip Detail/Home.

Use explicit viewer relationship and explicit deduplicated people sets.

==================================================
4. ROW ANATOMY
==================================================

Use the approved two-row mountain-led treatment.

Example:

Indy Basin, CO                         ORGANIZING
Jan 12–15 · +7 others

Stowe, VT                                  GOING
Feb 4–8 · +3 others

Alta, UT                              INTERESTED
Jan 15–18 · 2 going

Rules:

- mountain/location is primary
- relationship/status appears once only
- date is secondary
- people/context appears on the same secondary line
- do not display `ORGANIZING` twice
- do not add status eyebrows above the row
- no cards
- no avatar circles
- use flat ledger hairlines
- preserve the BaseLodge scale/rule system established in Trip Detail

==================================================
5. STATUS SEMANTICS
==================================================

Do NOT map trip-level `PLANNING` to Interested.

Readiness audit established:

- Planning = trip-level state
- Interested = participant RSVP

Viewer relationship presentation should come from actual role/RSVP semantics:

- owner → ORGANIZING
- participant Going → GOING
- participant Interested → INTERESTED
- pending invitation → invitation treatment, not a duplicate INVITED status label

Trip-level Planning may still exist in backend data but should not masquerade as a person-level relationship.

Do not change the underlying trip state model.

==================================================
6. `+N OTHERS`
==================================================

Use a deduplicated qualifying-person projection.

Do not reuse raw row counts.

For a viewer who is represented by the row relationship:

- exclude the viewer from the `others` count
- count qualifying other people exactly once
- suppress the suffix when there are zero others

Grammar:

+1 other
+N others

Do not derive this from:

- trip count
- date count
- Friends’ grouped_count
- pending join requests
- raw participant rows without deduplication

For Interested rows, preserve meaning accurately.

If viewer is Interested and two people are Going:

INTERESTED · 2 going

Do not convert that to `+N others` unless the count is actually describing the viewer’s same participation group.

==================================================
7. INVITATIONS INLINE
==================================================

Pending invitations appear chronologically within Mine.

Use the approved I1 treatment.

Example:

Whistler, BC                            Jan 25–29
Dana invited you · 5 going      Decline    Accept

Rules:

- invitation stays in the two-row ledger footprint
- subtle waiting-for-answer treatment may use the established blush/accent system
- do not create a separate invitations inbox
- do not create a large attention block
- do not add an `INVITED` label if `Dana invited you` already communicates it
- Accept and Decline are equal, explicit actions

==================================================
8. INVITATION ACTION BEHAVIOR
==================================================

Reuse the existing canonical route:

POST `/trips/<trip_id>/respond`

Do not create a second RSVP write path.

Decline:

- directly submit canonical `declined`
- preserve all current side effects, history, notifications, and transition rules

Accept:

We explicitly decided that Accept does NOT automatically mean Going.

Tapping Accept opens a small choice:

Going
Interested

Choosing one submits the existing canonical response.

Do not introduce a new RSVP state.

Preserve:

- CSRF
- authorization
- transition history
- existing activity/messaging side effects
- duplicate-trip reconciliation behavior
- terminal mutation protections

After successful response:

- refresh/recompute the Mine projection
- remove the pending invitation treatment
- place the accepted trip into its normal month/relationship position
- update any counts/context affected

A full page reload is acceptable if needed for safety, but prefer the smallest existing bounded refresh pattern if already supported.
