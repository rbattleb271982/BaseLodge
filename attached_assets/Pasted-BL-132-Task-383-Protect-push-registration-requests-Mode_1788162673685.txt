Implement approved Task #383 exactly as investigated.

Objective:
Enforce BaseLodge’s existing server-side CSRF contract on push-token registration and the native diagnostic beacon without changing the current browser/native session architecture.

Approved scope:

1. Protect push-token registration
At the start of /api/push/register-token:
- Require the existing BaseLodge CSRF validation.
- Validation must occur before token parsing, insertion, refresh, reactivation, or deactivation side effects.
- Missing or invalid CSRF must return the existing appropriate 403 behavior.
- Preserve the existing session-authentication requirement.

2. Protect the native diagnostic beacon
At the start of /api/push/beacon:
- Require the same existing CSRF validation.
- Reject missing or invalid CSRF before diagnostic logging occurs.
- Preserve current bounded diagnostic behavior.

3. Preserve browser/native architecture
Do not change:
- Flask session authentication
- browser cookie behavior
- iOS WebView architecture
- Android WebView architecture
- capacitor.config.json
- the existing patched window.fetch CSRF-token behavior
- static/js/bl-native.js unless implementation proves the investigation wrong

Both native platforms already load the BaseLodge web origin and should continue using the same session-bound CSRF mechanism as the browser.

4. Preserve existing push behavior
Do not change:
- APNs token handling
- FCM token handling
- same-user/platform token refresh/deactivation behavior
- push preference semantics
- browser push preferences
- account deletion behavior
- OneSignal/provider delivery
- broadcast behavior
- push-tap routing

5. Add regressions covering:
- authenticated registration + valid CSRF succeeds
- authenticated registration + missing CSRF returns 403 with no token side effects
- authenticated registration + invalid CSRF returns 403 with no token side effects
- unauthenticated registration remains blocked
- iOS/APNs registration still succeeds with valid CSRF
- Android/FCM registration still succeeds with valid CSRF
- existing refresh/deactivation semantics remain unchanged
- diagnostic beacon + valid CSRF succeeds
- diagnostic beacon + missing CSRF is rejected before logging
