# BL-121 — Restrict trip invites to eligible confirmed friends

Work on BaseLodge task BL-121.

This is a CRITICAL authorization/privacy bug.

Start with investigation and planning only. Do not modify code yet.

## Problem

`POST /api/trip/create` currently accepts arbitrary account IDs as invitees.

That allows an authenticated user to create:
- a pending trip participant record
- and an invite notification

for someone who is not actually eligible to be invited under BaseLodge's current friendship rules.

A prior QA audit reproduced a successful 200 response and pending participant for two users with no friendship.

## Required behavior

Every supplied `friend_id` must be validated server-side before any participant or notification side effect occurs.

Invitees must:
- exist
- be eligible confirmed friends under BaseLodge's CURRENT invitation rules
- not be the trip creator themselves

These must be rejected safely:
- non-friends
- self-invites
- nonexistent user IDs
- malformed IDs
- any user who does not satisfy the current confirmed-friend eligibility rules

Rejected invitees must not produce:
- a participant row
- a notification
- any other invite side effect

## Important scope constraint

Do not invent a new friendship policy.

First determine exactly what BaseLodge currently means by an eligible confirmed friend for trip invitations.

Inspect:
- friendship models and statuses
- friend request / confirmation flows
- existing helpers used elsewhere to determine confirmed friends
- current trip invitation UI filtering
- trip create endpoint behavior
- notification creation
- transaction boundaries / rollback behavior
- any existing tests around trip creation and invites
