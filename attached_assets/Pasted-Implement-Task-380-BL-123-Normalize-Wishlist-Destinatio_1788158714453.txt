GOAL

Make wishlist behavior consistent across BaseLodge so a wishlist functions as an ordered set of:

- valid resort IDs
- active resorts only
- non-region resorts only
- maximum 15 unique resorts

Preserve existing authentication, ownership, privacy, navigation, recommendation ranking, and dismissal behavior.

No schema migration or one-time cleanup is required.

1. ESTABLISH ONE CANONICAL WISHLIST CONTRACT

Create one shared normalization/validation path rather than duplicating rules across routes.

The canonical behavior must be:

- accept integer IDs
- accept numeric-string representations of integer IDs where current clients may send them
- reject booleans
- reject null
- reject floats
- reject malformed strings
- reject invalid containers
- stable first-seen deduplication
- preserve submission/append order
- validate IDs in one bounded bulk resort query
- require Resort.is_active == True
- require Resort.is_region == False
- reject nonexistent resorts
- enforce maximum only after normalization, dedupe, and eligibility validation

Maximum:

15 unique valid resorts.

Do not change the capacity.

2. BULK SAVE — /settings/wish-list/save

Apply the canonical contract.

Required behavior:

- normalize submitted IDs
- deduplicate before counting
- preserve first-seen order
- validate the complete unique set
- reject malformed IDs atomically
- reject nonexistent IDs atomically
- reject inactive resorts atomically
- reject region records atomically
- do not partially save a valid subset
- allow exactly 15 valid unique resorts
- reject >15 valid unique resorts
- leave existing stored wishlist unchanged on rejection

Example:

Input:
[12, "12", 15, 19]

Canonical result:
[12, 15, 19]

Input:
15 valid unique resorts + duplicate values

Result:
successful save of the 15 unique resorts.

Input:
15 valid resorts + invalid region ID

Result:
reject entire request; storage unchanged.

Preserve surrounding route response/error conventions as closely as possible while returning a clear client error.

3. INSTANT ADD — /api/wishlist/add

Make add idempotent.

Required order of operations:

- normalize requested ID
- determine whether the normalized ID is already canonically present
- if already present:
  - return successful no-op
  - do not fail because user is already at capacity

If it is a new ID:

- validate it exists
- require active resort
- require non-region resort
- count canonical unique eligible wishlist entries
- allow addition if current unique count <15
- reject if this would create a 16th unique resort

A duplicate add while already at 15 must succeed as a no-op.

Do not reorder existing wishlist entries.

Append a genuinely new resort to the end.

4. REMOVE — /api/wishlist/remove

Preserve ordered-set semantics.

Normalize the requested resort ID safely.

When removing:

- remove ALL legacy occurrences of the normalized ID
- preserve order of all remaining entries
- do not remove unrelated malformed legacy entries merely because this endpoint was called unless canonical storage rewrite naturally requires it

Correct the existing obsolete capacity/`at_limit` behavior from 3 to 15.

Ensure returned limit state is consistent with the canonical 15-resort rule.

5. CANONICAL MODEL READS

Update the canonical wishlist-facing model behavior so user-facing reads do not trust raw JSON blindly.

At minimum audit/update:

- get_wishlist_resorts()

- any directly related canonical helper

Desired behavior:

- malformed entries ignored
- nonexistent resorts ignored
- inactive resorts ignored
- regions ignored
- duplicates ignored
- valid resorts returned once
- stable stored first-seen order preserved where the method represents the user’s wishlist order

Use bounded bulk lookup.

Be careful not to turn a simple model property into hidden N+1 behavior across friend collections.

If a specific high-volume consumer needs its own set-based query instead of calling a model helper repeatedly, implement that consumer defensively rather than introducing N+1.

12. ORDERING

Wishlist ordering is:

stable first-seen order.

Examples:

[4, "2", 4, 7, "2"]

becomes:

[4, 2, 7]

A duplicate add preserves the existing order.

A new add appends to the end.

A removal preserves relative order of everything left.

Do not alphabetically or numerically sort the wishlist.

13. ERROR SEMANTICS

- return clear 400-class client error consistent with existing route behavior
- storage unchanged

Single add:

- malformed input => clear 400
- nonexistent/ineligible destination => use the existing surrounding API convention for unavailable/not-found destinations
- capacity violation => existing capacity error convention
- duplicate => successful no-op
