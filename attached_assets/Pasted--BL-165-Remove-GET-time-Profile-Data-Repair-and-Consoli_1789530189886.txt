# BL-165 — Remove GET-time Profile Data Repair and Consolidate Aggregates

Use BUILD mode.

This is a bounded Profile performance/read-semantics refactor.

Before implementing, inspect the current code and Git history for BL-165-equivalent behavior. If the complete requirement is already implemented, do not duplicate it: verify it, report the evidence, and stop. Otherwise proceed directly with the implementation below.

## Goal

Profile GET/read paths must be read-only.

Current/historical Profile behavior can repair equipment `is_primary` state and commit while serving a GET. Remove that read-time mutation while preserving the equipment-primary invariant and legacy-data safety.

Also inspect Profile's secondary wishlist, trip, and Ski Day aggregates and consolidate or defer them only where doing so produces a concrete bounded improvement.

Do not redesign Profile.

## 1. Audit current Profile behavior

Trace:

- Profile route(s)
- equipment loading
- `is_primary` repair/normalization
- any `db.session.commit()`, flush, update, insert, or delete reachable from Profile GET
- equipment create/edit/delete flows
- primary-equipment selection flows
- wishlist aggregates
- trip aggregates
- Ski Day aggregates
- query counts
- templates/partials consuming these values

Establish the current query/transaction baseline before changing code.

Explicitly determine whether BL-165 has already been partially or fully implemented.

## 2. Make Profile GET read-only

Profile GET must not:

- repair `is_primary`
- commit
- flush mutations
- update equipment
- insert/delete rows
- silently normalize legacy records

Loading Profile should not change persistent application state.

Add regression protection that proves repeated Profile GET requests leave relevant database state unchanged.

## 3. Preserve equipment-primary invariants

Move/enforce primary-equipment invariants at the appropriate mutation boundary.

Inspect all canonical equipment write paths, including as applicable:

- create
- edit
- delete
- mark primary
- replacement of a primary item

Preserve existing product semantics.

Do not invent a new equipment state model.

If legacy malformed data still needs repair support, preserve it through an explicit safe maintenance/write path rather than Profile GET.

Do not perform a migration or bulk data repair unless evidence proves one is required.

## 4. Aggregate performance

Inspect Profile's wishlist, trip, and Ski Day aggregates.

Only consolidate/defer them where there is a measurable or structurally clear benefit.

Avoid:

- N+1 queries
- per-row hydration
- duplicate aggregate queries
- unnecessary new endpoints
- client-side reconstruction of server business rules

Do not turn BL-165 into a Profile redesign or broad performance rewrite.

Report before/after Profile query counts and identify exactly what changed.

## 5. Preserve behavior

The Profile page must continue to display the same user-facing information and actions.

Do not change:

- Profile layout/design
- equipment semantics
- primary-equipment meaning
- wishlist semantics
- trip visibility
- Ski Day semantics
- privacy rules
- authorization
- navigation
- analytics semantics

This is a read-semantics/performance task, not a product redesign.
