────────────────────────────────────────────
PURPOSE
────────────────────────────────────────────

Conduct an evidence-based product architecture review of how BaseLodge communicates:

- Notifications
- Requests
- Invitations
- Pending actions
- Unread state
- Badges
- User-attention items
- Informational events
- Historical events
- Contextual state
- Ephemeral feedback

The review must distinguish:

1. Something the user should KNOW
2. Something the user needs to DO
3. Something that has changed state
4. Something that should remain visible until resolved
5. Something that belongs contextually on another screen
6. Something that belongs in notification history
7. Something that is merely immediate/ephemeral feedback

Do not assume:

- Notifications should become an inbox.
- Notifications should become an action center.
- Home should become an action center.
- Friends should own all social actions.
- Trip Detail should own all trip actions.
- A new screen is needed.
- Every repeated presentation is bad.
- Read and resolved mean the same thing.

Map the current product first.

────────────────────────────────────────────
LOCKED PRODUCT BOUNDARIES
────────────────────────────────────────────

Do not reopen these decisions.

HOME

Home is about what is happening now in BaseLodge.

It must not become Profile or a generic configuration surface.

PROFILE

Profile is the user + their personal BaseLodge configuration.

It must not become another Home/dashboard.

AVAILABILITY

Availability is the canonical functional concept.

Open to Ski is a first-person presentation of Availability.

Trips remain separate.

Raw Availability remains private.

TRIP DETAIL

Trip Detail retains the established:

Trip / People / You

architecture.

Current server-owned permissions, lifecycle semantics, RSVP semantics, invitation semantics, participant semantics, planning permissions, and privacy rules remain authoritative.

This review may identify how attention state interacts with those surfaces.

It must not redesign those already-locked architectures.

16. CLASSIFY DUPLICATION
────────────────────────────────────────────

Classify repeated attention items as:

A. USEFUL CONTEXTUAL REPETITION

Same canonical state appropriately appears in multiple contexts.

B. REDUNDANT DUPLICATION

Same item appears multiple times without additional user value.

C. INCONSISTENT DUPLICATION

Multiple surfaces represent the same state differently or become inconsistent.

D. NECESSARY ACTION PERSISTENCE

Same unresolved action remains visible in multiple appropriate locations because the user still needs to act.

E. HISTORICAL + CONTEXTUAL COEXISTENCE

Notifications retain the historical event while another surface owns current state.

Do not label repetition a defect simply because it exists.
