- previous_status: nullable only for approved initial guest-state establishment
- new_status: required
- changed_at: server-generated UTC timestamp
- actor_user_id: nullable, ON DELETE SET NULL
- source: required and restricted to a bounded internal vocabulary

Use portable string status columns with database constraints.

- pending
- interested
- going

- removed

- accepted

3. Add the focused non-committing RSVP transition writer/helper.

The helper must:

- operate inside the caller's existing transaction
- lock in the approved order: trip first, then participant
- read authoritative participant status after locking
- compare canonical current state to requested target
- no-op on same-state submissions
- preserve existing validation/authorization behavior
- apply existing status-coupled attendance-date cleanup
- update current participant status
- add exactly one matching transition row
- never call commit itself

Current-state mutation and history insertion must commit or roll back together.

4. Preserve concurrency and retry safety.

For PostgreSQL:
- serialize competing mutations against the current participant relationship
- preserve consistent trip -> participant lock order

For SQLite/tests:
- use existing transaction conventions
- do not invent PostgreSQL row-lock behavior
- do not create a generalized locking framework

Do not add client idempotency keys.

Expected behavior:

same target retry:
Going -> Going
= no new transition

legitimate reversal:
Interested -> Going -> Interested
= two real transition rows

For concurrent first-time participant creation, preserve the existing unique `(trip_id, user_id)` constraint and safely recover/re-read after uniqueness races where required.
