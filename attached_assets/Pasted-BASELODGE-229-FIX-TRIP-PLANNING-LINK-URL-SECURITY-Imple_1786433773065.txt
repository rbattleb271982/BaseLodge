BASELODGE — #229 FIX TRIP PLANNING LINK URL SECURITY

Implement ONLY the Trip Planning link_url security fix identified in Audit #228.

This is a tightly scoped security fix.

DO NOT:
- change Trip Planning permissions
- change post categories
- change post body behavior
- change notifications
- change database schema
- change CSRF behavior
- change any unrelated routes
- refactor Trip Planning broadly

==================================================
BACKGROUND
==================================================

SkiTripPlanningPost.link_url is optional.

Product requirement is:

Only http:// or https:// links are valid.

Current issue:

- create/edit accepts arbitrary strings
- backend does not enforce protocol
- template renders link_url in an <a href="...">
- therefore a stored javascript: URL or another unsafe scheme could become clickable

Fix this at BOTH:
1. server-side write validation
2. rendering layer

Server-side validation is the source of truth.

==================================================
1. FIND ALL WRITES TO link_url
==================================================

Identify every route/function that creates or updates:

SkiTripPlanningPost.link_url

Expected paths include:

POST /api/trip/<id>/planning-posts

PATCH /api/trip/<trip_id>/planning-posts/<post_id>

Confirm all write paths before changing anything.

==================================================
2. SERVER-SIDE URL VALIDATION
==================================================

For any non-empty link_url:

Allow ONLY URLs whose parsed scheme is:

http
https

Case-insensitive.

Reject:

javascript:
data:
file:
vbscript:
ftp:
mailto:
relative paths
protocol-relative URLs such as //example.com
plain strings with no scheme

Examples:

https://example.com     → valid
http://example.com      → valid
HTTPS://example.com     → valid

javascript:alert(1)     → reject
data:text/html,...      → reject
//example.com           → reject
example.com             → reject
/foo                    → reject

Do not validate using a simple startswith("http") check.

Use a proper URL parser available in the Python standard library.

Also trim leading/trailing whitespace before validation/storage.

Empty/whitespace-only:
store as NULL / no link according to the existing model behavior.

==================================================
3. CREATE ENDPOINT
==================================================

Update the Trip Planning post CREATE endpoint.

If link_url is invalid:

- return HTTP 400
- return a clear JSON error
- do not create the post
- do not send notifications
- do not partially commit anything

Suggested user-facing message:

"Link must start with http:// or https://"

Preserve existing:
- body validation
- 500-character rule
- category validation
- membership permissions
- notification behavior for valid posts

==================================================
4. EDIT / PATCH ENDPOINT
==================================================

Apply the identical validation to editing an existing planning post.

If a user attempts to change the link to an unsafe URL:

- return HTTP 400
- preserve the existing post
- no partial update
- no notification

Do not allow PATCH to bypass validation that CREATE enforces.

==================================================
5. DEFENSE-IN-DEPTH RENDERING
==================================================

Do NOT assume all existing database rows are safe simply because new writes are validated.

The template must never produce a clickable anchor for a URL unless it is confirmed to have an http or https scheme.

Implement a small server/template-safe check using the project's normal patterns.

For an existing unsafe link_url:

DO NOT render it as:

<a href="unsafe-value">

Instead either:

A. render the value as non-clickable escaped text

or

B. omit the link

Prefer B if that better matches the current UI.

Do not mutate existing database rows as part of this task.

This protects users immediately even if historical unsafe values already exist.

==================================================
6. FRONTEND VALIDATION
==================================================

In the New Post and Edit Post UI:

Use appropriate URL input semantics if not already present:

type="url"

But do NOT rely on browser validation as the security control.

If the backend returns the invalid-link 400:

- keep the form/sheet open
- show the error to the user
- do not clear their post body/category
- allow them to correct the URL

Do not create a generic page failure.

==================================================
7. EXTERNAL LINK SAFETY
==================================================

For valid external links rendered in planning posts, confirm the existing anchor behavior.

If links open in a new tab/window with:

target="_blank"

ensure they also use:

rel="noopener noreferrer"

If no target="_blank" is used, do not introduce it merely for this task.
