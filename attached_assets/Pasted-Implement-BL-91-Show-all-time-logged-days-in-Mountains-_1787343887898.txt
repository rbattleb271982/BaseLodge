Implement BL-91 — Show all-time logged days in Mountains Visited using the now-complete canonical SkiDay foundation.
This is an implementation task.
Goal
In the existing Mountains Visited experience, show the signed-in user’s all-time number of confirmed/logged Ski Days at each mountain.
These totals must come only from persisted SkiDay records.
Do not infer counts from:
trip date ranges
trip ownership
Going / Interested RSVPs
Mountains Visited membership itself
legacy mountains_visited
Required counting logic
For each resort in Mountains Visited, calculate:
COUNT(SkiDay.id) for the current user grouped by resort_id.
The existing unique constraint on:
user_id + resort_id + ski_date
means each record represents one trustworthy logged day.
Display
Keep the existing Mountains Visited UI and add a quiet secondary count beneath or alongside each mountain name.
Examples:
Vail · 8 logged days
Jackson Hole · 1 logged day
Use correct singular/plural:
1 logged day
N logged days
Use the phrase logged day(s) rather than implying this is necessarily the user’s complete lifetime skiing history.
Mountains with zero Ski Days
Existing manually or historically added Mountains Visited entries remain valid even when they have no SkiDay records.
For those mountains:
keep the mountain in Mountains Visited
do not invent a count
either omit the logged-day line or use the smallest existing empty treatment if BL-91 already specifies one
Prefer omitting the count rather than displaying 0 logged days unless the current task explicitly requires zero.
Own and friend views
Review the existing BL-91 task before implementation and follow its defined visibility.
If the task explicitly calls for the logged-day count on both the signed-in user and confirmed-friend Mountains Visited views, reuse the same aggregate logic safely.
If BL-91 is scoped to own Profile only, do not expand friend visibility.
Do not expose raw SkiDay dates, source, trip IDs, or correction history to friends.
Architecture
Reuse the existing:
/mountains-visited
templates/mountains_visited.html
current resort-list data
canonical SkiDay model
Favor one efficient aggregate query rather than querying Ski Days once per mountain.
Avoid N+1 queries.
A result map such as:
resort_id -> logged_day_count
is appropriate.
BL-89 / BL-99 compatibility
Preserve the behavior already implemented:
BL-89 adds confirmed Ski Day resorts to Mountains Visited.
BL-99 can add, edit, move, or delete Ski Days.
Moving a Ski Day can add a new Mountains Visited resort without removing the old one.
Deleting a Ski Day does not remove the mountain from Mountains Visited.
Therefore BL-91 should simply render the current aggregate of active SkiDay records.
If BL-99 deletes a Ski Day, the displayed logged-day total should decrease naturally on the next render.
Do not change
SkiDay schema
SkiDay uniqueness rules
BL-89 synchronization behavior
BL-99 correction behavior
manual Mountains Visited add/remove behavior
legacy Mountains Visited semantics
BL-39 Been Here behavior
trip or RSVP semantics
Do not create a new API unless the current Mountains Visited architecture genuinely requires one.

Run focused SkiDay/Mountains Visited tests and the full regression suite.
Confirm no native iOS, Android, Capacitor, or app-store changes.
