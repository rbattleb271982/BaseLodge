# Mountains Visited + Wishlist Mountains — Resort Selector Redesign
# PLANNING / INVESTIGATION ONLY

We want to redesign the BaseLodge resort-selection experience for both:

1. Mountains Visited
2. Wishlist Mountains

The goal is to make adding resorts much easier than manually typing resort names while creating a consistent, reusable BaseLodge experience.

IMPORTANT:
This is a PLANNING / INVESTIGATION task only.

Do NOT modify any code, templates, CSS, JavaScript, routes, models, database records, or files.

Do NOT commit, publish, push, restart the app, or change Secrets.

Do NOT run migrations or make any database writes.

---

# 1. CURRENT PROBLEM

The current Mountains Visited experience requires the user to manually enter a mountain/resort name.

We believe there should be a much easier way to select resorts from the existing BaseLodge resort database.

The same problem should be addressed for Wishlist Mountains.

We want both experiences to use the same underlying resort-selection experience rather than having two unrelated ways to find and add resorts.

---

# 2. TARGET EXPERIENCE

The proposed resort browser should use this hierarchy:

Country → State/Province/Region → Resort

## Geographic ordering

### United States

The United States must ALWAYS appear first.

Within the United States:

State → Resort

Both should be alphabetical.

Example:

United States

  California

    Bear Valley
    Heavenly
    Mammoth Mountain
    Palisades Tahoe
    ...

  Colorado

    Arapahoe Basin
    Aspen Mountain
    Beaver Creek
    Breckenridge
    Copper Mountain
    Keystone
    Loveland
    Vail
    ...

  Utah

    Alta
    Brighton
    Snowbird
    Solitude
    ...

### Other countries

After United States, all other countries should appear alphabetically.

For example:

Austria
Canada
Chile
France
Italy
Japan
Norway
Switzerland
...

Within each country:

State/Province/Region → Resort

Both levels should be alphabetical.

Use whatever geographic subdivision already exists in the BaseLodge resort data. Do NOT assume every country literally has "states."

---

# 3. COLLAPSIBLE HIERARCHY

The resort browser should not display the entire database expanded at once.

Countries should be collapsible.

States/provinces/regions should also be collapsible.

The intended interaction is:

United States
  ↓
Colorado
  ↓
Resort list

The user can drill down to the resort they want.

Do not invent unnecessarily complicated expansion behavior.

If the existing data makes it possible, groups containing selected resorts may be surfaced intelligently, but this should remain secondary to the basic Country → State/Region → Resort hierarchy.

---

# 4. RESORT SELECTION

Each resort should have a clear selection control, such as a checkbox.

For Mountains Visited:

Checked = user has visited the resort.
Unchecked = user has not visited the resort.

Existing visited resorts must appear checked automatically.

For Wishlist Mountains:

Checked = resort is on the user's wishlist.
Unchecked = resort is not on the user's wishlist.

Existing wishlist resorts must appear checked automatically.

The user should be able to add/remove the resort by changing the selection.

If the existing architecture safely supports immediate persistence without a full page reload, investigate that as the preferred experience.

However, do NOT change the underlying data model simply to support this UI.

---

# 5. VISITED AND WISHLIST MUST REMAIN SEPARATE

This is extremely important.

Visited and Wishlist are two different user states.

A resort can be:

- visited only
- wishlist only
- both visited and wishlist
- neither

Do NOT merge these concepts.

Do NOT change the underlying database representation merely to make the UI look unified.

The goal is a shared selection EXPERIENCE, not a merged data model.

---

# 6. SEARCH

The resort browser should also provide a search field near the top.

Suggested placeholder:

"Search mountains"

The user should be able to search the existing BaseLodge resort database by resort name without drilling through the geographic hierarchy.

For example:

Typing:

Whistler

should quickly surface:

Whistler Blackcomb

The search should use the existing resort data.

Do NOT create a manually maintained list of resorts.

Investigate whether BaseLodge already has a resort/mountain search or autocomplete experience elsewhere that can be reused.

---

# 7. COUNTS

Investigate showing useful counts at the country/state/region level.

For example:

United States · 8 visited

Colorado · 8 visited

For Wishlist, the equivalent could be:

United States · 12 wishlisted

Colorado · 4 wishlisted

The counts should reflect the appropriate state:

- Mountains Visited → number of visited resorts
- Wishlist Mountains → number of wishlisted resorts

Do not mix the two counts.

Determine the cleanest way to present these counts without making the hierarchy visually heavy.

---

# 8. BOTH FEATURES SHOULD FEEL CONSISTENT

Mountains Visited and Wishlist Mountains should use the same resort-selection pattern wherever practical:

- same Country → State/Province/Region → Resort hierarchy
- same alphabetical ordering
- same search experience
- same accordion behavior
- same checkbox/selection treatment
- same mobile tap-target standards
- same BaseLodge visual language

However, the pages should retain their own context.

For example, when the user is on Mountains Visited, the interaction should clearly mean:

"Add/remove this resort from Mountains Visited."

When the user is on Wishlist Mountains, it should clearly mean:

"Add/remove this resort from Wishlist."

Do not make the user wonder which state they are modifying.
