BASELODGE — SIMPLIFY TRIP DETAIL + ADD COLLABORATIVE TRIP PLANNING BOARD

Implement the approved V1 architecture for trip planning.

This task includes:
1. Simplifying the existing trip detail sections.
2. Moving Lessons into Trip setup.
3. Removing Transportation and Accommodations from the visible structured UI.
4. Moving the existing Notes field into Edit Trip as a private owner-only note.
5. Adding a new collaborative Trip Planning board.
6. Adding text-only authorship with simple date labels.
7. Preserving existing data and behavior where possible.

Do NOT add comments, reactions, profile avatars, or rich social features in V1.

==================================================
1. FINAL INFORMATION ARCHITECTURE
==================================================

The trip detail page should become:

TRIP HEADER
- Location
- Dates
- Visibility
- Planning / Going
- Existing Edit trip action

TRIP SETUP
- Pass
- Equipment
- Lessons

PEOPLE
- Existing participant / going / invited content

TRIP PLANNING
- New card that opens the collaborative planning board

TRIP ACTIONS
- Existing Invite friends action

Do not keep a separate “Trip details” section containing Transportation / Accommodations / Notes.

==================================================
2. TRIP SETUP
==================================================

Keep:

- Pass
- Equipment

Move:

- Lessons

into the same Trip setup card/section.

Lessons remains PERSONAL / PARTICIPANT-LEVEL.

Each accepted participant should manage their own lesson status.

Do not turn Lessons into a trip-owner field.

Do not expand Lessons into lesson dates, times, instructor details, etc.

V1 only needs the existing structured lesson status/toggle behavior.

==================================================
3. HIDE TRANSPORTATION + ACCOMMODATIONS FROM MAIN UI
==================================================

Remove Transportation and Accommodations from the visible trip detail interface.

IMPORTANT:
- Do NOT delete their database columns.
- Do NOT delete their endpoints.
- Do NOT migrate or destroy historical values.
- Do NOT remove backend logic yet.
- Do NOT auto-convert old values into Trip Planning posts in this task.

This should be a UI deprecation only for now.

The reason:
Transportation and accommodations will now be discussed/shared through the Trip Planning board.

Preserve all existing stored data for a later cleanup/migration task.

==================================================
4. PRIVATE OWNER NOTE
==================================================

The existing SkiTrip.notes field should NO LONGER appear as a shared Notes row on trip_detail.

Move it into the existing Edit Trip experience:

/trips/<id>/edit

Label it:

Private note

or:

Owner note

Preferred copy:

PRIVATE NOTE
Only you can see this.

Provide a textarea up to the existing 500-character limit.

This note is:
- visible only to the trip owner
- editable only by the trip owner
- NOT visible to accepted participants
- NOT visible to invited participants
- NOT visible to public/friend viewers
- NOT part of Trip Planning

Reuse the existing SkiTrip.notes field.

Do not create another notes column.

Update the existing Edit Trip form/backend safely so Private note can be saved alongside the existing editable fields.

Do not expose the note through participant-facing templates or JSON responses unnecessarily.

==================================================
5. NEW TRIP PLANNING CARD ON TRIP DETAIL
==================================================

Add a new section BELOW PEOPLE:

TRIP PLANNING

Inside it, add one card:

Plan this trip together

Supporting text:

Share ideas, links, accommodations, activities and plans with everyone going.

Show a post count if available:

3 posts

or:

No posts yet

The card should be tappable and open a separate dedicated Trip Planning screen.

Do NOT use a modal/interstitial for the full board.

Use a dedicated page so the feature can grow later.

==================================================
6. TRIP PLANNING ACCESS
==================================================

Trip Planning is PRIVATE to actual trip members.

Can access:
- Trip owner
- Accepted participants

Cannot access:
- Pending invited participants
- Declined participants
- Removed participants
- Friends who can merely see the trip
- Public viewers
- Logged-in users who are not accepted participants

Do not grant access based only on is_public.

The Trip Planning card should not appear to users who cannot access the board.

==================================================
7. TRIP PLANNING DATA MODEL
==================================================

Create a new model/table for planning posts.

Use a name consistent with the codebase, such as:

SkiTripPlanningPost

or another clear equivalent.

Minimum fields:

id
trip_id
user_id
category
body
link_url
created_at
updated_at

Recommended relationships:
- trip → SkiTrip
- author → User

Requirements:
- body required
- link optional
- category required
- created_at required
- updated_at optional or automatically maintained

Do NOT denormalize the author name unless the existing architecture strongly requires it.

Resolve the current author name from the related User.

Use the project’s existing startup migration pattern.

Migration must be:
- idempotent
- safe on repeated startup
- narrowly scoped
- consistent with existing migration style

==================================================

NO PROFILE BUBBLES.

NO INITIALS CIRCLES.

13. CREATE POST PERMISSIONS
==================================================

Who can create:
- owner
- accepted participant

Who cannot:
- invited/pending
- declined
- removed

==================================================
14. EDIT / DELETE PERMISSIONS
==================================================

Author:
- may edit their own post
- may delete their own post

Trip owner:
- may delete ANY post
- should NOT edit another participant’s post

This distinction matters.

Owner can moderate but cannot rewrite someone else’s content.

Server-side authorization required.

==================================================
16. NOTIFICATIONS
==================================================

When a new Trip Planning post is created:

Notify all OTHER accepted participants on the trip, including the owner if the author is someone else.

Do not notify the author of their own post.

Pending invitees should not receive the notification.

Use the existing BaseLodge notification/push infrastructure.

Create a specific notification type only if that matches the current pattern.

Suggested meaning:

“Taylor added a new planning post for Vail.”

or equivalent.

Do NOT add notifications for:
- editing a post
- deleting a post

in V1.
