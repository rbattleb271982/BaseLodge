3. DEFINE THE BASELODGE HISTORY CONTRACT

Propose a concrete contract covering:

EVENT IDENTITY
- database primary key
- whether any domain needs an external/client idempotency key
- whether event identity should ever be reused across retries

SUBJECT
- what identifies the user/entity whose history is being recorded
- single-subject vs pair/multi-subject histories
- canonicalization requirements for unordered pairs

ACTOR
- when actor_user_id is required
- when actor may be NULL
- actor deletion/anonymization behavior
- distinction between actor and subject

SOURCE
- bounded source vocabulary
- whether source values are domain-specific
- whether free-form source/reason/metadata is allowed

TIMESTAMP
- server-generated vs caller-provided
- timezone requirements
- ordering/tie-break semantics
- whether historical timestamps may ever be supplied during legitimate imports/backfills

APPEND-ONLY / CORRECTIONS
- whether rows may be updated after creation
- correction strategy when an event was wrong
- whether delete/rewrite is ever allowed operationally
- how privacy deletion differs from historical correction

CURRENT STATE VS HISTORY
- clarify that history does not automatically become authorization/current-state truth
- define when a domain's current table remains canonical
- define when historical reconstruction is allowed
- tri-state unknown semantics where recording did not exist historically

BACKFILL
- default backfill policy
- standards for allowing a backfill
- provenance requirements
- rules against fabricating historical events from insufficient present-state data

DUPLICATE PREVENTION / CONCURRENCY
- service-level state comparison
- database constraints
- deterministic locking
- transaction boundaries
- whether idempotency keys are normally necessary

RETENTION / PRIVACY
- subject deletion
- actor-only deletion
- anonymization
- cascades
- rules for historical records involving multiple users
- distinction between ordinary product transitions and privacy erasure

INDEXING / QUERY PATTERNS
- required pair/entity + occurred_at indexes
- ordering conventions
- expected future "state at T" queries
- avoid indexes with no demonstrated query need

AUDITABILITY
- bounded event types
- bounded sources
- actor provenance
- immutable timestamps
- no PII copies unless strictly required

TEST INVARIANTS
Define the minimum tests every future history stream must include.

At minimum consider:
- real transition creates one event
- duplicate/no-op creates none
- rollback leaves neither state nor event changed
- reconnection/repeated lifecycle creates new legitimate events
- privacy deletion
- actor anonymization
- no synthetic backfill
- migration upgrade/downgrade
- concurrency on PostgreSQL where relevant
- current authorization/product behavior remains independent from historical rows
