The purpose of this plan is to map the approved presentation onto the current BaseLodge implementation and produce the safest, smallest implementation plan.

## Approved Trip Detail architecture

Trip Detail is organized into three primary sections:

### 1. TRIP

The top of Trip Detail should contain:

- Hybrid mountain/date header using the approved BaseLodge presentation
- Trip Planning immediately below the header
- Two newest planning items shown directly
- All Ideas action
- Share an idea/link action

The historical standalone Stay presentation should not remain as a separate primary block in this presentation.

Determine where existing stay/lodging information belongs under the approved architecture without deleting underlying functionality or data.

### 2. PEOPLE

People contains the existing participant/social functionality presented coherently together:

- Participation summary / existing approved graphic where applicable
- Join requests
- Invite action
- Going
- Interested
- Invited

Reuse existing participation state, permissions, invitation behavior, and server-owned logic.

Do not invent new participant statuses.

### 3. YOU

You contains the current user's trip-specific information:

- Riding
- Ability
- Pass
- RSVP / participation status
- User availability relative to the trip dates
- Equipment
- Lessons

Reuse existing BaseLodge data and semantics.

Do not create new schema or duplicate Profile data.

## Lifecycle presentation

The approved foundation must also account for:

### Organizer
- Cancel Trip
- Existing authorization preserved
- Appropriate confirmation before destructive action

### Participant
- Leave Trip
- Existing authorization preserved
- Appropriate confirmation before destructive action

### Past/cancelled trips
- Appropriate read-only presentation
- No actions that should no longer be available
- Historical information remains understandable

Do not change trip lifecycle semantics.
