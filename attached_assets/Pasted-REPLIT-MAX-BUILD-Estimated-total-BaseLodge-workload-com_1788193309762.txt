APPROVED PRODUCT / DATA DESIGN

1. SkiTrip remains the only canonical trip record.

2. Add:
- nullable lifecycle_state with bounded values:
  - active
  - completed
  - cancelled
- nullable timezone-aware terminal_at

Semantics:
- NULL = pre-cutover lifecycle unknown
- NULL is operationally treated as active unless explicitly transitioned
- new trips start active
- lifecycle state is separate from existing planning/going intent

3. Completion:
- explicit organizer action only
- allowed only after the trip's complete date range has ended
- never generated automatically from date passage
- persisted as completed
- terminal/read-only in BL-80
- no reopen or correction flow in BL-80

4. Cancellation:
- both existing user-facing trip delete flows become cancellation transitions
- retain the canonical SkiTrip
- retain final participant rows
- retain dates
- retain RSVP transition history
- retain planning content, notes, stay/accommodation data, and canonical metadata
- invalidate/remove live invitations, invite tokens, and live opportunity/social artifacts
- terminal/read-only
- no reopening in BL-80

5. Privacy/account deletion remains physical deletion.

6. Controlled maintenance/test cleanup may remain physical deletion where appropriate.

7. Historical Trip Detail access:
- organizer: allowed
- retained participant with active RSVP state: allowed
- pending: denied
- declined: denied
- removed: denied
- unrelated: denied
- current friend only: denied
- former friend only: denied
- public status alone does not grant historical Trip Detail access

8. History events:
Add private domain-specific SkiTripLifecycleEvent with:
- trip subject
- event_type: completed / cancelled
- nullable actor_user_id
- bounded source vocabulary
- timezone-aware server-generated occurred_at
- trip FK CASCADE
- actor FK SET NULL
- trip/time index
- actor/time index

History never grants authorization.

9. No lifecycle-state or event backfill.

Existing dates, notifications, analytics, invitations, logs, or deleted-row absence must not be used to fabricate lifecycle history.

==================================================
LIFECYCLE SERVICE
==================================================

Create one narrow transaction-neutral trip lifecycle service.

Follow the BL-78 / BL-79 pattern where appropriate.

Responsibilities:

- lock the canonical SkiTrip row using PostgreSQL row locking
- refresh lifecycle/current state under the lock
- verify organizer authorization
- verify transition eligibility
- set lifecycle_state
- set terminal_at
- append exactly one lifecycle event
- flush without committing
- return a clear result to the caller

Caller retains commit/rollback ownership.

Do not send notifications from inside the service before commit.

COMPLETION RULES

Completion requires:
- authenticated organizer
- trip not already terminal
- complete valid date range
- end date has passed according to the existing canonical date semantics

Completion must fail for:
- missing dates
- incomplete date range
- future/current trip
- non-organizer
- cancelled trip

Same completed retry:
- no new event
- deterministic no-op response

Completed → cancelled:
- conflict

CANCELLATION RULES

Cancellation requires:
- authenticated organizer
- non-terminal active/legacy trip

Same cancelled retry:
- no new event
- no duplicate notification

Cancelled → completed:
- conflict

Legacy NULL lifecycle trips may be explicitly cancelled.
