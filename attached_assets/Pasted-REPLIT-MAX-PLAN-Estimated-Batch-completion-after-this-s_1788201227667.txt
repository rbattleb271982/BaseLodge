TASK: BL-133 — Define and enforce authenticated-user visibility policy

This is the first task in the new Core Product Systems batch.

INVESTIGATE AND DESIGN ONLY.
Do not implement yet.

==================================================
GOAL
==================================================

Establish a clear, centralized policy for what authenticated BaseLodge users are allowed to see about other users, trips, friendships, wishlist/pass information, availability, and related social data.

The goal is NOT to redesign BaseLodge permissions.

The goal is to:

1. discover the actual visibility rules currently implemented,
2. identify inconsistencies or accidental exposure,
3. define the canonical policy,
4. determine the smallest safe architecture for enforcing it consistently,
5. prepare an implementation plan.

Privacy and authorization behavior must be based on server-side rules, not merely whether the UI happens to display something.

==================================================
1. FIND THE CANONICAL BL-133 REQUIREMENTS
==================================================

Locate BL-133 in the existing task/backlog documentation if available.

Use its exact requirements as authoritative.

Also inspect related privacy/auth/social tasks and existing tests where they clarify intended behavior.

Do not silently expand BL-133 into unrelated authentication/session/CSRF work.

In particular, keep separate unless directly required:

- BL-168 auth/session lifecycle
- BL-169 CSRF contract
- BL-170 rate limits
- broader security-hardening work

==================================================
2. INVENTORY USER-VISIBLE SOCIAL DATA
==================================================

Map every authenticated surface where one user can receive information about another user.

At minimum inspect:

- Friends
- Friend Profile
- Home
- Ideas
- Mountains
- Mountain friend/social context
- My Trips
- Trip Detail
- trip rosters
- invitations
- wishlist overlap
- season-pass overlap
- availability/open dates
- friend-created trips
- friend-attended trips
- interested/going status
- notifications
- messaging-related user/trip context
- relevant JSON/API endpoints

Include server-rendered pages and API responses.

Do not assume a hidden UI element means the underlying endpoint is protected.

==================================================
3. MAP RELATIONSHIP STATES
==================================================

Identify all relationship states that can affect visibility.

Examples may include:

- self
- direct friend
- pending incoming request
- pending outgoing request
- declined
- removed/former friend
- unrelated authenticated user
- trip organizer
- active trip participant
- pending invitee
- declined invitee

- public-trip viewer
- private-trip viewer

Use actual repository states and terminology.

Do not invent states that do not exist.

==================================================
4. MAP DATA CATEGORIES
==================================================

For each relevant relationship state, determine current access to:

- basic profile information
- email or other identifying information
- friendship status
- wishlist

- mountain social context
- messaging eligibility/context

Identify anything sensitive or unexpectedly exposed.

==================================================
5. PUBLIC VS PRIVATE TRIP POLICY
==================================================

Audit exactly what "public" and "private" mean today.

Determine:

- who can discover a public trip
- who can open its Trip Detail
- who can see its organizer
- who can see participants
- who can see RSVP/attendance information
- what friends can see
- what unrelated authenticated users can see
- what happens after completion/cancellation
- whether changing public ↔ private changes visibility correctly

Do not change BL-80 historical authorization semantics unless a genuine conflict is found.

==================================================
6. FRIENDSHIP POLICY
==================================================

Determine exactly when a user becomes authorized to see friend-only information.

Specifically inspect whether any friend-only data leaks through:

- pending requests
- declined requests
- removed friendships
- stale one-sided Friend rows
- historical friendship events
- query joins that merely detect any relationship row

BL-79 history must NOT grant authorization.

Current authoritative friendship state must remain the source of truth.

==================================================
7. WISHLIST / PASS / AVAILABILITY POLICY
==================================================

Determine the intended and current visibility of:

- wishlist mountains
- season passes
- availability/open dates

Pay particular attention to whether these are:

- private
- direct-friend-visible
- exposed only as overlap/context
- visible through Ideas but not directly
- visible to unrelated users through mountain/trip surfaces

BL-87 wishlist history must NOT grant visibility or authorization.

BL-70 remains deferred and must NOT be migrated as part of this task.

==================================================
8. IDEAS AND DERIVED INFORMATION
==================================================

Audit whether Ideas can indirectly reveal information a viewer could not otherwise access.

Examples:

- another user's private availability
- private wishlist membership
- private trip participation
- former-friend information
- non-friend information

Distinguish between:

A. displaying raw underlying data
B. displaying a permitted derived insight

Recommend explicit rules for derived information.

Do not redesign the Ideas ranking algorithm unless authorization requires a narrowly scoped change.

==================================================
9. AUTHORIZATION ARCHITECTURE
==================================================

Identify how visibility is enforced today.

Determine whether authorization logic is:

- centralized helpers/services
- duplicated route checks
- embedded query filters
- template-only conditions
- API-specific checks
- combinations of the above

Identify duplicated or conflicting rules.

Recommend the smallest maintainable architecture.

Prefer explicit domain-specific policy helpers over:

- one giant generic authorization framework
- scattered route-specific conditionals
- template-only enforcement

But conform to existing repository architecture where sensible.

==================================================
10. QUERY-LEVEL VS RESPONSE-LEVEL ENFORCEMENT
==================================================

For each important surface, determine whether unauthorized records should be:

- excluded at query time
- rejected by authorization before retrieval
- filtered before serialization
- hidden only in presentation

Prefer preventing unauthorized data from being loaded/serialized where practical.

Identify any current cases where sensitive information is fetched and merely hidden in the template.

==================================================
11. API / DIRECT-URL TESTING
==================================================

Treat direct URL/API access as authoritative security behavior.

Plan tests where users manually request resources they should not see.

Include:

- unrelated user
- pending friend
- former friend
- declined friend
- unauthorized private-trip viewer
- removed participant
- declined invitee
- historical edge cases

UI navigation is not sufficient authorization testing.

==================================================
12. HISTORY IS NOT AUTHORIZATION
==================================================

Explicitly verify that none of the new historical systems can accidentally grant current access:

- BL-78 RSVP transition history
- BL-79 friendship history
- BL-80 trip lifecycle history
- BL-87 wishlist history

History may support future analysis.

History must not answer:

"Can this user see this resource right now?"

==================================================

- privacy erasure

Do not broaden into a general FK/account-deletion repair task.

Document unrelated defects separately.
