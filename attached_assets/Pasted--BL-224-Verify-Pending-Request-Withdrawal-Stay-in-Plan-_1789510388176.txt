# BL-224 — Verify Pending Request Withdrawal

Stay in Plan.

This is a verification/audit task first. Do NOT assume BL-224 still requires implementation.

We recently implemented and tested substantial pending friend-request withdrawal behavior while fixing the Suggested Friends lifecycle, including the Charles → Eric scenario.

Before making ANY code changes, audit the current implementation against the existing Notion requirements for:

BL-224 — Pending Request Withdrawal

## Goal

Determine whether the CURRENT codebase already fully satisfies BL-224.

Do not recreate functionality that already exists.

## Specifically trace

Audit the complete outgoing friend-request lifecycle:

1. User sends a friend request.
2. The request becomes pending.
3. The sender sees the correct pending/requested state.
4. The sender can withdraw the pending request.
5. Withdrawal uses the canonical supported endpoint/path.
6. The underlying pending invitation/request is correctly removed or transitioned according to the existing architecture.
7. Any originating Suggested Friends recommendation remains intact when appropriate.
8. Reloading the relevant surface produces the correct state.
9. The recipient no longer has an actionable incoming request after withdrawal.
10. Repeated/stale withdrawal is handled safely.
11. Authorization prevents another user from withdrawing someone else's request.
12. Existing friendship, suggestion, invitation, privacy, and notification semantics are preserved.

Pay particular attention to the already-tested Suggested Friends lifecycle:

Richard suggests Eric to Charles
→ Charles sends Eric a request
→ Eric remains represented correctly in Suggested Friends
→ Charles sees Requested
→ Charles can withdraw
→ the FriendSuggestion itself remains intact
→ the UI reflects Request withdrawn / the correct post-withdrawal state
