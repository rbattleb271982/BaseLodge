Implement BL-187 — HOME — Stabilize shared Home data assembly.

This is BUILD.

Use the approved Task #374 plan as the implementation contract.
Do not create another planning task.
Do not expand scope beyond BL-187.

Primary goal:
Create one consistent, read-only Home summary contract from data the Home route already loads, and remove the redundant Home-only trip recount without changing product semantics, visibility, ordering, presentation, or authorization behavior.

Approved implementation direction:

1. Add the smallest side-effect-free Home summary assembler
- Build it from already-resolved Home values only.
- It must not issue database queries.
- It should return a structure equivalent to:

home_summary = {
  "about_you": {
    "user": authenticated User,
    "display_rider_type": existing computed display value,
    "skill_level": existing profile value,
    "pass_type": existing stored pass value,
    "rider_disciplines": existing Home discipline list,
    "gear_by_discipline": existing selected EquipmentSetup map,
    "is_renting": existing rental-state result
  },
  "activity": {
    "upcoming_trip_count": len(all_upcoming),
    "mountains_visited_count": User.visited_resorts_count,
    "wishlist_count": current Home wishlist count
  },
  "friends_passes": {
    "friend_count": len(existing direct-friend IDs),
    "counts": existing Epic/Ikon/Other result,
    "other_pass_slugs_url": existing canonical filter URL
  },
  "next_trip": {
    "trip": existing next_trip with current effective attendance attributes,
    "is_owner": current-user ownership boolean
  } or null
}

Use existing canonical values exactly as they are currently resolved.

2. Remove the redundant Home trip recount
- Home already has authoritative deduplicated `all_upcoming`.
- Derive Home’s trip statistic from `len(all_upcoming)`.
- Do not call the query-backed global upcoming-trip count helper from Home.
- Do not delete or change that global helper; preserve it for non-Home callers.
- Do not introduce replacement queries.

3. Preserve current trip semantics exactly
Keep:
- owned upcoming/in-progress trips
- active Interested/Going participant trips
- effective attendance date handling for guests
- exclusion of pending, declined, and removed participation
- owner/participant deduplication by trip ID
- current private-trip access behavior
- current next-trip selection/order

Do not broaden visibility or reinterpret eligibility.

4. Preserve Friends’ Passes semantics exactly
Reuse the existing helper unchanged.

Keep:
- Epic / Ikon / Other buckets
- all three buckets present
- each direct friend counted once per bucket
- a friend may count in multiple buckets
- Other = canonical supported non-Epic/non-Ikon pass
- No Pass, blank, and unknown values excluded
- count equivalence with existing Friends filters

Do not redesign Friends’ Passes UI.

5. Preserve all other Home semantics
Do not change:
- identity/profile behavior
- rider type logic
- skill logic
- gear selection logic
- rental-state logic
- pass normalization
- wishlist counting semantics
- mountains visited semantics
- direct-friend semantics
- Ideas matching/ranking/retrieval
- Happening eligibility/order/retrieval
- availability behavior
- RSVP/action eligibility
- caching
- authorization policy
- Profile BL-165 behavior

BL-133 remains authoritative for authorization/visibility.
BL-176 and BL-177 remain authoritative for Ideas/Happening performance work.
BL-146 remains authoritative if caching is introduced later.

6. Keep presentation unchanged
- Continue passing the existing flat template arguments.
- Also pass `home_summary`.
- Do not modify Home visual design or interactions.
- Do not implement BL-188, BL-190, BL-191, BL-192, BL-193, or BL-194.
- Templates and partials should remain unchanged unless a purely test-related inert context issue requires the smallest possible adjustment.
