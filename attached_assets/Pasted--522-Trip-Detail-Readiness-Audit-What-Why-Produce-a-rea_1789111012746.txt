# #522 - Trip Detail Readiness Audit

## What & Why

Produce a read-only engineering investigation of the approved, locked Trip Detail redesign against the current BaseLodge source.

The goal is to determine which target features:

- are already supported safely by existing data and actions
- need presentation-only work
- need small query/service additions
- require new behavior or state logic
- require schema/model changes
- should be deferred before implementation begins

The approved Trip Detail design is LOCKED.

Do not redesign it.
Do not propose alternative layouts.
Do not implement anything.

## Locked target architecture

The following requirements are fixed and should be treated as implementation requirements, not design questions:

- Hybrid trip header
- `Trip | People | You` structure
- Trip opens by default
- Trip Planning is first under Trip
- Two planning items shown by default
- This Mountain section
- People sentence headline
- Participation graphic
- Pass distribution graphic
- Join requests inside People
- Compact grouped participant roster
- Expandable participant groups
- Invite action in the group header
- You begins with profile-derived Riding + Ability + Pass
- You includes Status, Availability, Equipment, and Lessons
- Availability has a compact visual treatment
- Equipment and Lessons are directly selectable
- You can show an unanswered-item badge
- Cancel Trip requires confirmation
- Leave Trip requires confirmation
- No Stay section in the target Trip Detail
- No profile photos, profile bubbles, avatar circles, or initials avatars
- No photography
- Past trips retain mountain identity
- Dates are informational and do not have an independent chevron/action

## Product decisions already locked

### Trip lifecycle

Do not introduce a Planning → Confirmed lifecycle.

Target presentation distinguishes:

Trip timing:
- Upcoming
- Past

Viewer relationship:
- Organizing
- Going
- Interested
- Invited

### Trip Planning

Default Trip tab shows:

- 2 most recent planning items
- category
- title
- author
- date
- `All ideas`
- `Share an idea or link`

### This Mountain

Target design explores:

- Other upcoming friend trips at this mountain
- Friends who have visited/skied this mountain
- Friends with this mountain on their wishlist

These must only be built if current data supports them honestly.

### People

People includes:

- sentence-style group summary
- Participation graphic
- Pass distribution graphic
- join requests
- grouped participant roster
- Invite action

Pass distribution includes everyone associated with the trip:

- Going
- Interested
- Invited

Use `No pass`.

Do not add pass compatibility or buddy passes.

### You

`FROM YOUR PROFILE`

- Riding
- Ability
- Pass

`FOR THIS TRIP`

- Status
- Availability
- Equipment
- Lessons

Availability is the current user's own availability only.

Never expose another user's raw availability.

### You attention badge

Only unanswered trip-specific questions count.

For now:

- Equipment
- Lessons

Availability does not count.

### Non-participant friend

A friend viewing a friend-visible trip who is not:

- organizer
- Going
- Interested
- Invited

may see:

- mountain
- location
- dates
- nights
- trip context/visibility
- number of people

They do NOT see:

- participant identities
- Trip Planning
- You content
- join requests
- organizer controls

They may:

- mark Interested
- Request to Join

### Invited user

An invited user who has not responded:

- may READ Trip Planning
- may NOT create planning content yet

After choosing Going or Interested:

- may contribute to Trip Planning

### Cancel Trip

- organizer only
- bottom/near bottom of Trip
- requires confirmation
- `Keep trip`
- `Cancel trip`

### Leave Trip

- participant only
- separate from Going ↔ Interested
- quiet destructive action
- requires confirmation

### Stay

The current canonical Stay block is removed from the target Trip Detail design.

Do not treat lodging as a required Trip Detail object.

Lodging may still appear as Trip Planning content.

## Investigation questions

### 1. This Mountain — upcoming friend trips

Verify:

- whether BaseLodge can query a user's friends who have trips at the same mountain
- whether those can be filtered to upcoming trips
- whether privacy/visibility rules are respected
- whether an accurate unique-friend count can be derived
- whether an existing destination/list surface already exists
- whether this requires any schema change

Cite exact models, fields, functions, routes, services, templates, and tests.

### 2. This Mountain — visited/skied

Verify:

- whether BaseLodge stores visited-mountain history
- whether "visited" and "skied" are actually equivalent in the data model
- whether visit history comes from explicit fields, completed trips, history rows, or another source
- whether friend visit history is already queryable
- whether a unique-friend count can be derived safely
- whether the phrase `have skied Northstar` is defensible

Do not equate visited with skied unless code/data proves it.

### 3. This Mountain — wishlist

Verify:

- wishlist model/storage
- whether friend wishlists are visible
- whether a unique-friend count can be derived
- whether existing wishlist-count logic can be reused
- whether an existing destination/list surface exists
- whether any migration is required

For each This Mountain row classify as:

- SUPPORTED NOW
- SUPPORTED WITH SMALL QUERY/PRESENTATION WORK
- REQUIRES NEW BACKEND LOGIC
- REQUIRES SCHEMA/DATA MODEL CHANGE
- SHOULD NOT BE BUILT FROM CURRENT DATA

### 4. Trip Planning

Verify:

- exact model backing Trip Planning
- exact category field/model
- real supported category values
- whether title/link are separate fields
- author relationship
- timestamp field
- current ordering
- whether the 2 most recent items can be queried deterministically
- existing full-list route
- whether `ideas`, `posts`, and Trip Planning are the same persisted object
- whether Trip Planning shares any model with Home Ideas
- read permissions
- contribute permissions

Explicitly test target permissions:

- non-participant friend: NO access
- invited user: READ only
- Going / Interested / Organizer: READ + CONTRIBUTE

If current behavior differs, document the exact delta.

### 5. Participation states

Map current backend states to:

- Organizing
- Going
- Interested
- Invited

Verify:

- what current `Planning` actually represents
- whether `Pending` and `Invited` are the same concept
- whether organizer is a role, status, field, or derived state
- Going ↔ Interested transitions
- what `Not going` does
- whether declined state persists
- whether Leave Trip exists
- whether Leave Trip and Not going use the same transition
- whether users can rejoin
- any cooldown/history restrictions

Do not change vocabulary in code.

### 6. People counts

Verify:

- which states count toward total associated people
- whether organizer is included in Going or separate
- how organizer double-counting is prevented
- whether declined/removed/cancelled records are excluded
- whether counts can be computed efficiently

### 7. Pass distribution

Verify:

- canonical pass field/model
- all actual pass values
- whether users may have multiple passes
- how `No pass` is represented
- whether invited users have pass/profile data available
- whether pass distribution can be computed across all associated people without migration
- edge cases around missing/multiple values

Do NOT add mountain-access compatibility.

Only verify group distribution.

### 8. Participant roster

Target roster needs:

- grouped statuses
- compact rows
- name
- riding type
- ability
- pass
- tap person → Friend Profile
- expandable status groups

Verify:

- exact source of riding type
- exact source of ability
- exact source of pass
- profile-level vs trip-level source
- visibility/privacy rules
- Friend Profile route
- whether all participants are navigable
- current ordering
- organizer ordering
- stable sorting within groups

Verify whether the frontend can safely render a capped preview and expand in place without a new API.

Do NOT select the final preview cap yet.

## Implementation classifications

Every locked target feature must be classified:

### A — Presentation only
Existing data + existing actions.

### B — Small backend/query extension
Existing schema supports it, but query/service/API work is required.

### C — New state/behavior logic
Requires new transition, permission, or business logic.

### D — Schema/migration required
Current model cannot represent the target honestly.

### E — Unsupported / defer
Current data cannot justify it safely or it should not be in the first implementation.
