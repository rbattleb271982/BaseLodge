GOAL

Add private, append-only history for meaningful direct-connection formation and removal while keeping live Friend rows as the ONLY current friendship and authorization truth.

Historical connection data must never grant access, affect visibility, or create a public “Former Friends” concept.

APPROVED CURRENT ARCHITECTURE

- A confirmed connection is normally represented by two reciprocal directed Friend rows.
- Invitation is request/workflow state only.
- Friend rows remain the sole current truth for:
  - profiles
  - trip access
  - invitation eligibility
  - friend counts
  - overlaps
  - recommendations
  - messaging eligibility
  - Home / Ideas / Happening
  - all other current visibility/authorization

BL-79 history is supplemental and private only.

1. ADD PRIVATE CONNECTION EVENT MODEL

Create a focused domain-specific append-only table for connection lifecycle events.

Recommended fields:

- id
- user_a_id
- user_b_id
- event_type
- occurred_at
- actor_user_id
- source

Subject pair rules:

- canonical ordering only
- user_a_id < user_b_id
- no self-pairs
- one event represents the relationship pair, not one direction

Event types:

- formed
- removed

Use bounded internal source values derived from real product mutation paths.

Do NOT add:

- request/invitation references
- live Friend row foreign keys
- previous-event references
- free-form metadata
- reason text
- public serializers
- public relationships/backrefs
- an is_friend convenience property
- client idempotency identifiers

Use a timezone-aware server timestamp.

Add only appropriate canonical-pair/time indexes.

2. PRIVACY / FK BEHAVIOR

Both relationship subjects are privacy owners of the history.

Deleting either subject account must erase identifiable connection-history rows involving that subject.

If a user appears only as actor on another surviving pair:
- retain the pair event
- set actor_user_id to NULL

Do not copy names, emails, tokens, request payloads, or other PII into the history table.

4. CENTRALIZE CONNECTION TRANSITIONS

Implement a non-committing domain service/helper.

The service should:

- accept the two subject users
- canonicalize the pair
- lock both User rows in ascending ID order
- refresh/read both directed Friend rows after locking
- determine current pair state
- mutate reciprocal Friend rows as needed
- append at most one lifecycle event
- flush but do NOT commit

The caller retains the existing transaction/commit boundary.

Friend mutation and history insertion must commit or roll back together.

5. FORMATION SEMANTICS

A real new mutual connection should create exactly one:

formed

event.

Approved product formation paths include:

- accepting a registered-user friend request
- accepting a reusable friend invite token
- onboarding/login continuation from that token if applicable
- QR/direct connection confirmation
- legacy GroupTrip invitation acceptance that creates a connection
- shared-upcoming-GroupTrip connection flow

Do NOT create formation history from:

- seed setup
- tests
- startup repair
- maintenance/admin data creation
- duplicate accept/connect actions
- already-connected state
- request send
- request decline
- request cancellation

Preserve current route responses and side effects.

6. REMOVAL SEMANTICS

Both canonical unfriend paths must use the transition service:

- API unfriend
- web/form unfriend

When a live connection exists and is removed, create exactly one:

removed

event.

Preserve existing behavior including:

- reciprocal Friend deletion
- invitation cleanup
- invite-token expiry
- cooldown behavior
- notifications
- activities
- analytics
- route responses

Repeated removal when already disconnected must create no history.

Account deletion is NOT an ordinary removed event.
It is privacy erasure only.

7. RECONNECTION

Reconnection after a legitimate prior removal must create a new formed event.

Example:

formed
removed
formed
removed

Each interval is real and must remain distinguishable.

Do not restore or mutate prior event rows.

History is append-only.

8. ONE-SIDED FRIEND DRIFT

This is an explicit safety requirement.

Because reciprocity is not database-enforced, one-sided Friend rows may exist.

Formation behavior:

- if one directed Friend row already exists and the other is missing, repair reciprocity conservatively
- do NOT fabricate a second formed event merely because the missing reciprocal row is repaired
- preserve existing product semantics

Removal behavior:

- if either side exists and the product action removes the relationship, remove any existing reciprocal rows
- record exactly one removed event

Do not silently redesign the live social graph.

If a drift scenario cannot be handled safely without broader architecture changes, STOP and report.

9. CONCURRENCY / IDEMPOTENCY

Use deterministic locking:

- lock both subject User rows in ascending ID order
- then inspect/refresh both Friend rows

This should prevent:

- duplicate formed events from concurrent accepts
- duplicate removed events from concurrent unfriend attempts
- A/B versus B/A direction duplicates

Same-state retries are no-ops.

Do not add client idempotency keys.

Real PostgreSQL concurrency tests are required.

SQLite tests should verify logic but must not pretend to validate PostgreSQL row locking.

10. ATOMICITY

Do not permit:

- Friend rows committed without matching required history
- history committed without corresponding live mutation
- one side of reciprocal relationship committed while the other fails

The connection mutation and event insert belong to the same transaction.

The transition service must never commit internally.
