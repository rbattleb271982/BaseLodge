# BL-120 — Prevent private trips from leaking into Mountains friend counts

Work on BaseLodge task BL-120.

This is a CRITICAL privacy bug.

Start with investigation and planning only. Do not modify code yet.

## Problem

Private trips currently contribute to friend counts returned by `/api/mountains-data`, which can expose destination-level intent to viewers who are not authorized to see those trips.

A prior QA audit reproduced `friend_count` changing from 0 to 1 after a friend created a private trip and the relevant cache was refreshed.

## Required behavior

1. `/api/mountains-data` must exclude private trips from friend counts unless the current viewer is otherwise authorized to see the trip.

2. Mountain friend counts must use the same trip-visibility rules as Mountain Detail.

3. Preserve all existing correct behavior for:
   - direct-friend requirements
   - trip dates
   - attendance / participation statuses
   - public trips
   - trips the viewer is legitimately authorized to see

4. Do not solve this with a UI-only filter. Unauthorized private-trip data must not enter the count in the first place.

5. Regression tests must prove that a private trip does not change Mountain friend counts for an unauthorized viewer.

## Safety / scope

Expected scope is narrow.

Do NOT:
- change database schema
- create migrations
- redesign Mountains
- change unrelated trip visibility rules
- alter public-trip behavior
- change friend eligibility semantics
- change attendance semantics
- refactor unrelated code
- implement caching changes unless strictly necessary to correct this bug

BL-133 will later define the broader canonical authorization/visibility policy. BL-120 should fix the concrete current privacy leak without expanding into that larger task.

There is also a separate task for stale Mountains friend-count caching. Do not absorb cache-freshness work into BL-120 unless the cache itself is directly responsible for leaking unauthorized private-trip data.

## Investigation

Inspect the current implementation, especially:

- `/api/mountains-data`
- the query/helper that calculates friend counts
- Mountain Detail's existing trip-visibility logic
- relevant trip, participant, friend, and visibility helpers/models
- any cache layer involved in the Mountains response

Determine exactly why a private trip is counted in one path but hidden in the other.
