APPROVED PRODUCT CONTRACT
--------------------------------------------------

Complete BL-174 on top of the EXISTING bounded Friends paging system.

The backend already provides:

- GET /api/friends/page
- server-side search across the full authorized reciprocal-friend set
- signed viewer/filter-scoped keyset cursors
- stable ordering
- server-enforced page size of 20
- partial-HTML JSON response
- reciprocal-friend authorization boundary
- bounded hydration
- privacy-filtered trip counts
- existing explicit Load more behavior

Do NOT rewrite that architecture unless tests reveal a concrete correctness defect.

Approved UX:

1. Initial Friends page renders only the existing bounded first page.
2. Automatically load the next page as the user approaches the bottom.
3. Keep the visible Load more control as a keyboard/accessibility/WebView fallback.
4. Search and filters remain server-side across the FULL authorized friend set.
5. Search/filter changes reset paging state.
6. Stale responses must never overwrite newer search/filter results.
7. Repeated observer/button triggers must never duplicate requests or rendered cards.
8. Loading, retry, empty-result, and final-page states must be clear.
9. Preserve current stable ordering:
   - case-insensitive first name ASC
   - case-insensitive last name ASC
   - Friend.id ASC unique tie-breaker
10. Re-authorize every page request so friendship changes cannot leak revoked users.
11. Keep per-page query/hydration cost bounded.
12. Preserve current Friends visuals except for minimal progressive loading/status behavior.
13. No friend ranking, recommendations, social intelligence, global discovery changes, analytics, blocking redesign, or speculative prefetching.

--------------------------------------------------
STEP 2 — HARDEN CLIENT REQUEST GENERATIONS
--------------------------------------------------

Inspect the existing Friends paging JavaScript in templates/friends.html.

Implement an explicit request-generation mechanism in addition to AbortController.

Requirements:

- Every search/filter scope has a generation identifier or equivalent monotonic request-state guard.
- Changing search/filter state:
  - starts a new generation
  - resets cursor
  - resets rendered paging state
  - resets end-of-list state
- Only responses belonging to the CURRENT generation may mutate the Friends directory.
- An old response completing after a newer request must be ignored.
- AbortController may remain, but correctness must NOT rely on abort completing successfully.
- Incremental requests for the same generation must have an in-flight guard.
- Observer and button activation must share the same load-next-page path.
- Only one incremental request may run at a time.
- Duplicate triggers must not append duplicate Friends cards.
- Preserve existing friend-ID deduplication as a second safety layer.

Do not build a generalized networking framework.

Keep this local to Friends paging.

--------------------------------------------------
STEP 3 — ADD PROGRESSIVE AUTOMATIC LOADING
--------------------------------------------------

Add an end-of-list sentinel or similarly minimal DOM target.

Use IntersectionObserver when available.

Behavior:

- Observe a marker near the bottom of the loaded Friends directory.
- When it approaches the viewport and:
  - has_more is true
  - a next cursor exists
  - no incremental request is active
  - current search/filter generation is valid
  then trigger the SAME existing next-page request used by Load more.

Use an appropriate rootMargin so loading begins shortly before the user reaches the end.

Do not introduce aggressive speculative prefetch.

This must be user-scroll-driven progressive loading.

Fallback requirements:

- If IntersectionObserver is unavailable, Friends remains fully usable with the visible Load more button.
- Keep Load more keyboard accessible.
- Keep it usable in mobile WebViews.
- Do not remove the button merely because automatic loading exists.

At the final page:

- stop observing or otherwise prevent further loads
- ensure no repeated network requests
- hide/disable the Load more control appropriately
- expose a minimal accessible completion/end state if consistent with current UI

--------------------------------------------------
STEP 4 — COMPLETE UI STATES
--------------------------------------------------

Implement or harden minimal states for:

INITIAL LOAD:
- loading state should be accessible
- if initial API-driven reload fails, allow retry

INCREMENTAL LOAD:
- keep already loaded Friends visible
- do not clear successful rows on next-page failure
- expose retry through the existing control

SEARCH/FILTER FAILURE:

- allow retry
- stale/superseded responses must not alter the UI

EMPTY SEARCH/FILTER RESULT:

FINAL PAGE:
- no additional requests
- clear loading state
- clear observer behavior
- clear Load more availability appropriately

ACCESSIBILITY:
- preserve semantic button behavior
- use current aria-busy/status patterns if available
- do not shift keyboard focus unexpectedly when rows auto-append
- status updates should not become noisy on every observer event

Preserve BaseLodge’s existing visual language.

No redesign.
