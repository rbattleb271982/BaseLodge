LOCKED MENTAL MODEL

NOTIFICATIONS
= What happened?

HOME → NEEDS YOU
= What do I still need to deal with?

FRIENDS / TRIP DETAIL / OTHER CONTEXTUAL DESTINATION
= Where the underlying relationship, trip, or workflow actually lives.

RED BADGE
= Something new I have not seen.

Red badges do NOT mean unresolved work.

SEEN and RESOLVED are separate concepts.

Never collapse them.

NOTIFICATIONS

Notifications owns recent relevant activity.

Examples:

- friend request received/sent where current messaging supports it
- trip invitation received
- join request approved
- trip dates changed
- friend request accepted
- other meaningful existing trip/planning/social activity

Notifications should feel socially warm and alive because the activity involves real people, trips, and ski context.

Do not use artificial urgency.

Do not turn Notifications into an inbox or action center.

NO RESOLUTION ACTIONS IN NOTIFICATIONS

Notifications must not directly own:

- Accept / Decline friend request
- Going / Interested / Decline
- Approve / Reject join request
- equivalent canonical workflow mutations

If the current implementation allows friend requests to be accepted directly from Notifications, remove that behavior.

Notifications may deep-link to the appropriate owning context.

NOTIFICATION BADGE

The red Notifications badge represents:

UNSEEN NOTIFICATION ACTIVITY ONLY.

Opening Notifications should mark the currently relevant presented unseen notification activity as seen and clear the corresponding badge.

Opening Notifications must NOT resolve underlying actions.

Example:

Trip invitation is unseen + unresolved.

User opens Notifications.

Result:

seen = yes
resolved = no

Notification badge clears.

Invitation may still exist in Notifications while unresolved.
Needs You still contains it.
Trip Detail still owns the underlying decision.

ACTIONABLE NOTIFICATION RESOLUTION

If a notification exists specifically because an underlying action remains unresolved, then after confirmed resolution:

- remove it from Needs You
- remove the corresponding actionable notification

Do not preserve it as permanent history.

Example:

Michael invites Richard to Aspen.

Before response:
Notifications → invitation
Needs You → invitation
Trip Detail → invitation state

Richard responds Going.

After confirmed success:
Notifications → original invitation gone
Needs You → invitation gone
Trip Detail → Richard is Going

Trip Detail remains canonical truth.

LATER EVENTS

Resolution of an old notification must NOT suppress future activity.

Example:

Aspen invitation resolved.

Later organizer changes Aspen dates.

That date change is a NEW notification event.

Do not revive or mutate the old invitation notification to represent the change.

NEEDS YOU

Needs You owns unresolved attention.

It is independent of seen/unseen notification state.

An item can therefore be:

- unseen + unresolved
- seen + unresolved
- resolved and absent

Do not use badge state as workflow state.

NEEDS YOU ACTION RULE

Use context-sensitive resolution.

SIMPLE / LOW-CONTEXT ACTION

May resolve inline from Needs You when the user has enough information to make the decision safely.

Example:

Straightforward friend request:
Accept
Decline

CONTEXT-DEPENDENT ACTION

Navigate to the owning contextual surface before resolution.

Examples:

Trip decisions where dates, roster, participants, trip details, or other meaningful context should reasonably be reviewed.

Do not recreate Trip Detail or Friends inside Home.

FAILED NEEDS YOU ACTIONS

If an inline mutation fails:

- do not remove the item
- do not imply success
- restore/retain unresolved state
- show an explicit error
- provide Retry where appropriate
- prevent duplicate mutation/double submission
- reconcile against authoritative server state

Example:

Sarah wants to connect

Couldn't accept request. Try again.

Retry

The item disappears only after:

- confirmed successful mutation, OR
- authoritative state says it is no longer pending

FRIENDS BADGE

Friends red badge represents:

NEW / UNSEEN FRIEND-REQUEST ACTIVITY.

It does NOT equal the number of unresolved requests.

Example:

Three requests arrive.

Friends badge = 3.

User opens Friends.

Friends badge = cleared.

The user does nothing.

All three requests remain pending in Friends.
They may remain in Needs You.
The red badge stays cleared because the activity has now been seen.

Opening Friends must mark the relevant unseen request activity seen without resolving the requests.

BADGE SEMANTICS

Across BaseLodge:

RED BADGE = new activity I have not seen.

Never:

RED BADGE = work I have not completed.

INFORMATIONAL NOTIFICATION RETENTION

Notifications is recent relevant activity, not a permanent archive.

Purely informational notifications should automatically age out.

Before implementation:

Inspect current notification model/data behavior and existing conventions.

Determine whether a sensible bounded retention policy can be implemented safely with existing state.

Choose the smallest sensible policy consistent with current architecture.

If selecting the retention duration creates meaningful product/data consequences or requires destructive migration/data behavior:

STOP and report the proposed retention period and consequences before implementing it.

Age-out must NEVER alter canonical:

- Trip state
- friendship state
- invitations
- planning state
- participants
- RSVP state
- Availability
- other product truth

DEEP LINKS

Notifications should deep-link to the meaningful owning destination where one exists.

Examples:

Trip dates changed
→ Trip Detail

Trip invitation
→ Trip Detail

Join-request activity
→ relevant Trip/context

Friend activity
→ appropriate Friends/profile context supported by current architecture

Do not deep-link to arbitrary generic pages.

CROSS-SURFACE RECONCILIATION

This is critical.

Resolution from ANY valid owning surface must reconcile:

- Notifications
- Needs You
- Friends
- Trips
- Trip Detail
- relevant badges

Do not leave stale contradictory UI.

Examples:

Friend request accepted from Needs You:
Friends updates.
Needs You item disappears.
Corresponding actionable Notification disappears.
Badges remain based on unseen semantics, not pending count.

Trip invitation resolved from Trip Detail:
Needs You item disappears.
Actionable notification disappears.
Trip Detail reflects canonical RSVP state.

Seen state must remain independent.
