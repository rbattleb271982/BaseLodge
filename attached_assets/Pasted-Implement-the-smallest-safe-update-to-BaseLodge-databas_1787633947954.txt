Implement the smallest safe update to BaseLodge database identity protection so different Supabase projects using the same shared regional pooler can be distinguished without weakening production protection.
Context
The new dedicated Supabase development project exists and is healthy.
Its project-specific direct URL passes identity checks but is unreachable from Replit because the endpoint is IPv6-only.
The Supabase Session Pooler is IPv4-compatible, but both BaseLodge Dev and BaseLodge Prod use the same credential-safe endpoint shape:
postgresql://aws-0-us-east-2.pooler.supabase.com:5432/postgres
Supabase distinguishes projects in shared pooler connections through the username/project reference, e.g.:
postgres.<project-reference>
BaseLodge’s existing database identity logic intentionally excludes the username, so Dev and Prod currently collide.
Goal
Safely distinguish Supabase project identity when using shared Supabase pooler URLs while continuing to:
exclude passwords;
avoid logging full usernames or connection strings;
fail closed;
reject production from development/test/bootstrap/import/user-creation operations;
preserve existing behavior for non-Supabase database URLs.
Preferred design
Do not generally start treating arbitrary database usernames as identity.
For recognized Supabase shared pooler hosts only:
Parse the Supabase project reference from the expected pooler username format.
Treat that project reference as a non-secret database identity component.
Never include the database password.
Never print the full connection URL.
Never print arbitrary usernames.
Diagnostics may report only the credential-safe endpoint and, if appropriate, a redacted/hash representation of the project reference.
Determine the cleanest compatibility design for the existing:
BASELODGE_PRODUCTION_DATABASE_IDENTITY_HASH
Prefer avoiding a risky silent reinterpretation of the existing production hash.
If a new explicit non-secret protection value such as:
BASELODGE_PRODUCTION_SUPABASE_PROJECT_REF
or a hashed equivalent is safer, implement that rather than weakening the current guard.
Required behavior
Prove all of these:
Production Supabase pooler URL is recognized as production.
New BaseLodge Dev pooler URL is recognized as distinct from production.
Two URLs using different roles for the same Supabase project are still treated as the same protected project where appropriate.
A malformed or missing project reference fails closed when using a shared Supabase pooler.
Password changes do not affect identity.
Non-Supabase URLs retain current identity behavior.
Existing Replit development DB remains distinguishable.
Tests
Add focused tests for:
same pooler host + same project ref + different password
same pooler host + same project ref + alternate role
same pooler host + different project refs
malformed pooler username
direct Supabase hostname behavior
production rejection in development
bootstrap/import/development-user guard behavior
Run the full isolated regression suite after focused tests.
Critical safety boundaries
During this task:
do not connect to or modify the new Supabase Dev database;
do not modify production data/schema;
do not run bootstrap/migrations/imports;
do not switch BASELODGE_DEVELOPMENT_DATABASE_URL;
do not change DATABASE_URL;
do not remove the Replit-managed DB;
do not publish/redeploy;
do not restart production;
do not touch push/OneSignal/APNs;
do not resume BL-77.
If a new non-secret production project-reference guard value is required, do not guess it. Derive it credential-safely from the configured production URL without printing credentials, then tell me exactly what secret/value must be added or updated before we retry the Dev pooler.
Return
Report:
identity-design change
files changed
compatibility behavior
focused test results
full regression results
whether a new environment/secret value is required
exact next step for using the BaseLodge Dev Session Pooler
confirmation production and both development databases were untouched
commit hash/message if committed
End with:
SUPABASE POOLER IDENTITY GUARD READY — SAFE TO CONFIGURE DEV POOLER
or
SUPABASE POOLER IDENTITY GUARD BLOCKED: [reason]
