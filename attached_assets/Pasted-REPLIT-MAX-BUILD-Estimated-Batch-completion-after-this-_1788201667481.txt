==================================================
PRIMARY GOAL
==================================================

Enforce one consistent server-side visibility policy across authenticated BaseLodge social surfaces.

The most important defect to close is:

HIGH SEVERITY:
Many friend-only reads currently authorize using a single directed Friend row.

A stale one-sided Friend row must NOT authorize:

- detailed profile data
- wishlist
- visited mountains
- season pass
- riding/equipment data
- availability context
- public friend trips
- friend APIs
- derived social data

Canonical friend authorization requires CURRENT RECIPROCAL FRIENDSHIP.

Pending, declined, former, historical, and one-sided relationships grant no friend-only access.

==================================================
CANONICAL FRIENDSHIP POLICY
==================================================

A confirmed friend relationship exists only when BOTH current Friend rows exist:

viewer → target
target → viewer

History is irrelevant to current authorization.

Do NOT consult:

- BL-78 RSVP history
- BL-79 friendship history
- BL-80 lifecycle history
- BL-87 wishlist history

to determine current access.

FriendConnectionEvent and other history tables are audit/history only.

==================================================
IMPLEMENTATION ARCHITECTURE
==================================================

Create the smallest maintainable set of domain-specific visibility helpers.

At minimum centralize:

1. reciprocal current friendship
2. trip-view capability/policy
3. social field/view-model disclosure where needed

Do NOT create:

- a generic permissions framework
- a generalized ACL system
- a new authorization database model
- schema migrations

Prefer:

- reusable current-state predicates
- EXISTS/join-based query filtering
- pre-retrieval route authorization
- explicit response allowlists

Avoid loading sensitive records and merely hiding them in templates when practical.

==================================================
FRIEND-ONLY SURFACES
==================================================

Replace directed-row friendship authorization with the reciprocal-current rule everywhere friend-only information is exposed.

Audit and update all relevant paths, including:

- Friend Profile
- Wishlist
- Visited Mountains
- Friend trip surfaces
- Home social data
- Ideas
- Mountains
- availability-derived context
- invitation eligibility
- relevant APIs
- direct URL access

A stale one-sided Friend row must fail closed.

Do not use friendship history as a fallback.

==================================================
PUBLIC TRIP POLICY
==================================================

Preserve the approved meaning of "public":

Public does NOT mean globally public.

Current public trips are discoverable/viewable through friend-oriented surfaces only by CURRENT CONFIRMED FRIENDS, subject to the existing surface rules.

Unrelated authenticated users must not be able to open a public trip merely by guessing its URL.

Public → private:
remove friend-only discovery/access immediately.

Private → public:
grant confirmed-friend discovery only.

Do not make public trips globally accessible.

==================================================
PRIVATE TRIP POLICY
==================================================

Current private trip access remains available to:

- organizer
- current Going participant
- current Interested participant
- current Pending invitee for that specific trip

Friendship is not required for direct trip membership access.

Friendship alone does not grant private-trip access.

==================================================
TERMINAL TRIP POLICY
==================================================

Preserve BL-80 exactly.

Completed/cancelled trip detail remains available only to:

- organizer
- retained active Going/Interested participants

Read-only.

Do NOT grant terminal access based on:

- friendship
- pending invite
- declined invite
- removed participation
- trip history events

Do not reinterpret legacy `accepted` RSVP values in BL-133.

If legacy `accepted` rows are encountered, document them separately.

==================================================
ROSTER POLICY
==================================================

Approved policy:

Going and Interested identities:
visible to admitted trip viewers.

Pending and Declined identities:
ORGANIZER ONLY.

Removed participant identities:
not shown in normal user-facing rosters.

Important:

For non-organizers, exclude Pending/Declined roster records BEFORE their User records are hydrated or serialized where practical.

Do not merely hide them in the template after loading.

Preserve organizer invitation-management functionality.

==================================================
PROFILE / FIELD DISCLOSURE
==================================================

Confirmed friends may continue seeing the existing friend-profile data already approved, including current:

- wishlist
- visited mountains
- pass
- riding profile
- equipment fields

Do not expose these to:

- pending friends
- declined friends
- former friends
- stale one-sided Friend rows
- unrelated users

Email is NOT friend-visible information.

WISHLIST / PASS VISIBILITY

==================================================
AVAILABILITY POLICY
==================================================

Raw availability/open dates remain private.

Another user must not receive the full underlying date list.

Confirmed friends may receive only bounded derived overlap where the current product permits it.

Derived overlap must be based on:

- current reciprocal friendship
- current authoritative availability
- viewer-relevant eligible trip/date context

Do not expose raw availability through APIs or detail views.

Availability Ideas:

- current reciprocal friends only
- authoritative future availability
- expose overlap only, not raw date inventories

Trip Ideas:

- current visible public trips only
- active/legacy-current trip semantics as already approved
- participant-derived context requires current Going/Interested status
- terminal/private/removed/pending/declined records must not leak

History tables must not participate.
