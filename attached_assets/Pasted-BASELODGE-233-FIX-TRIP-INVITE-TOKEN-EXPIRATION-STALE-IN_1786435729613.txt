BASELODGE — #233 FIX TRIP INVITE TOKEN EXPIRATION & STALE INVITATION STATE

Implement ONLY the two correctness fixes confirmed by Audit #232:

1. Enforce TripInviteToken.expires_at when it has a value.
2. Reconcile an existing pending Invitation row when that same user accepts through a TripInviteToken.

DO NOT:
- change the open-share-link model
- bind tokens to specific users or emails
- change reusable-token behavior
- add token revocation UI
- re-enable the disabled TripInviteToken sharing UI
- change notifications
- migrate schema
- change invite preview content
- change friendship behavior

==================================================
BACKGROUND
==================================================

Audit #232 confirmed:

TripInviteToken is intentionally an OPEN, REUSABLE share link.

There is no intended recipient binding.

Multiple different users are allowed to accept the same token.

This behavior is correct and must remain unchanged.

However:

1. TripInviteToken.expires_at is currently ignored by both:
   GET /trip-invite/<token>
   POST /trip-invite/<token>/accept

2. Six existing tokens have expired expires_at values but remain active and acceptable.

3. If a user already has a direct Invitation row with status='pending'
   and then accepts the trip through a TripInviteToken,
   SkiTripParticipant becomes ACCEPTED but the Invitation row remains pending.

Fix ONLY these two inconsistencies.

==================================================
1. CENTRALIZE TOKEN VALIDITY CHECK
==================================================

Inspect:

trip_invite_token_landing()
trip_invite_token_accept()

Both currently validate:

- token exists
- tit.is_active

but not:

tit.expires_at

Avoid duplicating subtly different validity logic if a very small internal helper is appropriate.

Desired validity:

A token is valid if:

- token exists
- is_active == True
- AND either:
    expires_at is NULL
    OR expires_at is in the future

Important:

Current token creation intentionally sets:

expires_at = NULL

Those tokens remain valid indefinitely until deactivated.

DO NOT start assigning expiration dates to new tokens.

This task only enforces expiration where expires_at already has a value.

7. STALE Invitation RECONCILIATION
==================================================

Audit #232 confirmed that TripInviteToken and Invitation are parallel systems.

Scenario:

User has:
SkiTripParticipant status = INVITED

and/or a matching trip Invitation with:
status = pending

Then user accepts through TripInviteToken.

Current behavior:
participant becomes ACCEPTED
but matching Invitation may remain pending.

Fix this consistency issue.

When token acceptance succeeds, find ONLY Invitation rows that clearly correspond to:

- this same trip
- this current user
- pending/invited state

Use the actual Invitation model fields to determine the correct recipient relationship.

Do not broadly update invitations.

Do not touch:
- invitations for another user
- invitations for another trip
- friend invitations
- already declined/accepted historical rows unless existing model semantics clearly require it

For a matching pending trip Invitation:

update it to the project's canonical accepted status.

Do this inside the SAME transaction as participant acceptance.

==================================================
8. DO NOT CHANGE PARTICIPANT ACCEPTANCE LOGIC
==================================================

Preserve current behavior:

No participant:
→ create ACCEPTED guest row

Existing INVITED participant:
→ change to ACCEPTED

Existing DECLINED participant:
→ change to ACCEPTED

Existing ACCEPTED participant:
→ idempotent redirect, no write, no notification

Owner:
→ cannot join own trip via token

Do not alter these rules.
