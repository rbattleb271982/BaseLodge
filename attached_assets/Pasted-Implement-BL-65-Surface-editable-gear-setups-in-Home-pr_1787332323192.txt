Implement **BL-65 — Surface editable gear setups in Home profile summary** using the completed investigation.

This is an **implementation task**. Make the scoped web/backend changes and tests required to complete BL-65.

## Hard constraint

This must ship through the existing **web/backend architecture only**.

Do not modify:

* Native iOS project files
* Native Android project files
* Capacitor configuration
* Native plugins
* App permissions
* Entitlements
* Anything requiring a new Apple App Store or Google Play binary

The investigation confirmed BL-65 can be completed without native changes.

## Goal

Surface concise, editable gear information directly beneath the existing Home identity summary:

**Rider type · Skill level · Pass**

Users should see their relevant ski and/or snowboard setup at a glance and be able to tap it to open the existing Gear editor.

Do not create a second gear-management flow.

## Existing architecture

Home is rendered by `home()` in `app.py`.

The relevant Home header partials are:

* `templates/partials/home/_header.html`
* `templates/partials/home/_header_empty.html`

The existing Gear page is:

* Route: `/settings/equipment`
* Template: `templates/settings_equipment.html`

Gear is stored in `EquipmentSetup`.

Important current behavior:

* A user may have multiple saved setups.
* Setups have a discipline such as skier or snowboarder.
* BaseLodge currently has **one global primary setup per user**, not one primary setup per discipline.
* Do not change that model or behavior in BL-65.

## Required setup-selection logic

For each rider-relevant discipline:

1. If the user's current global primary setup matches that discipline, use it.
2. Otherwise use the oldest saved setup for that discipline.
3. Do not modify any existing setup records or primary flags.

Prepare one deterministic setup per relevant discipline for Home.

Do not use the legacy single `home_eq` value for this feature because it cannot correctly represent a user who skis and snowboards.

## Rider-discipline rules

Only render disciplines the user actually declares in their rider profile.

Examples:

### Skier

If a matching ski setup exists:

**Skis · Salomon QST 92**

If no matching ski setup exists:

**Add your gear**

### Snowboarder

If a matching snowboard setup exists:

**Snowboard · Burton Custom**

If no matching snowboard setup exists:

**Add your gear**

### Skier + snowboarder

If both exist:

**Skis · Salomon QST 92**

**Snowboard · Burton Custom**

If only skis exist:

**Skis · Salomon QST 92**

**Add your snowboard gear**

If only snowboard exists:

**Add your ski gear**

**Snowboard · Burton Custom**

## Mismatched saved data

Do not show equipment for a discipline the user does not currently declare.

Examples:

* A skier with only a saved snowboard setup must not see that snowboard shown as skis.
* A snowboarder with an old ski setup must not see that ski setup in the Home summary.
* A both-discipline user may see one matching setup plus an add-state for the missing discipline.

Do not silently relabel equipment.

## Blank-detail setups

If a valid saved setup exists but has no useful brand/model detail, do not treat it as missing.

Use a truthful concise fallback such as:

* **Skis setup**
* **Snowboard setup**

Use the existing label when appropriate if it is more useful and concise.

Do not surface boots, bindings, width, length, purchase year, or other detailed fields on Home.

## Rental users

Preserve the existing rental state.

If the user's relevant gear state indicates they rent equipment, show a clear **Rental gear** treatment rather than misleading them with an own-gear setup or “Add your gear” prompt.

Reuse existing rental semantics. Do not redesign rental behavior.

## Home presentation

Add the gear summary directly below the existing Rider / Level / Pass identity line in both:

* populated Home header
* empty Home header

Requirements:

* compact
* visually subordinate to the main identity line
* underlined/tappable
* consistent with existing BaseLodge typography and link styling
* no large new card or section
* no Home redesign

Each setup/add state should be independently tappable when there are two disciplines.

## Navigation

### Add-gear state

Link to the existing:

`/settings/equipment`

Do not create a new form or route.

### Existing saved setup

Deep-link to the selected setup on the existing Gear page.

Use the existing setup element ID pattern:

`#setup-<id>`

Extend the existing browser behavior in `templates/settings_equipment.html` so that when the page loads with a setup hash:

* find the corresponding saved setup
* reuse the existing edit-form behavior
* open that setup directly for editing

Do not create a new editing mechanism.

If the hash is absent, preserve the normal Gear-page behavior.

If the hash is invalid or refers to a setup the current user cannot edit, fail safely and leave the normal Gear page usable.
