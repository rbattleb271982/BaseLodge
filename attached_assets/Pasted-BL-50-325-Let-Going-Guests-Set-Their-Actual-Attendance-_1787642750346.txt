BL-50 / #325 — Let Going Guests Set Their Actual Attendance Dates
Implement BL-50 — Persist and validate participant-specific trip dates, using the BL-49 investigation and approved product decisions.
Goal
Allow a Going guest on a shared trip to set the dates they will actually attend within the organizer’s core trip dates.
Do not create separate trips for participant date differences.
Approved product rules
Only Going guests may set participant-specific attendance dates.
Interested, Pending, Declined, and Removed guests may not set or retain attendance dates.
The organizer’s own attendance continues to be represented by the trip’s core dates.
A participant may edit only their own attendance dates.
The organizer may not edit another guest’s participant-specific dates.
One contiguous inclusive range per participant per shared trip.
Both participant dates null = Full trip.
Participant dates must remain within the organizer’s core trip dates.
Same-day attendance is allowed.
For in-progress trips, Going guests may still edit their attendance dates, including dates earlier in the trip that have already passed, as long as the range remains within the trip’s core dates.
Organizer core-date changes
If the organizer tries to change the trip’s core dates in a way that would make any existing participant-specific attendance range invalid:
Block the organizer’s date change.
Do not clamp, clear, or rewrite the guest’s attendance dates automatically.
Return a clear validation message explaining that one or more participant attendance ranges would fall outside the proposed new trip dates.
Persistence
Reuse the existing nullable:
SkiTripParticipant.start_date
SkiTripParticipant.end_date
Do not add a new table or redesign the schema unless the current code makes that unavoidable.
Normalize existing participant creation behavior so a guest with no explicit attendance override uses:
start_date = NULL
end_date = NULL
rather than unnecessarily copying the organizer’s full trip dates.
This includes reconciling the current join-request path that materializes the parent range.
API / permissions
Add the smallest focused current-user endpoint needed for attendance-date updates.
It must:
require authenticated membership on the trip;
require guest Going status;
allow changing only the caller’s own participant row;
accept either:
a complete valid start_date + end_date, or
an explicit clear/full-trip action that sets both to null;
reject partial pairs;
reject malformed dates;
reject reversed ranges;
reject dates outside the organizer’s trip range.
Preserve existing RSVP and participant authorization behavior.
Minimal Trip Detail UI
For a Going guest, add a compact My dates control on Trip Detail.
Behavior:
No participant override → display Full trip
Override present → display the participant’s actual date range
Tapping/editing opens a simple date-selection surface bounded by the organizer’s trip dates
Include an explicit Full trip action that clears both participant dates
Do not redesign Trip Detail broadly.
Do not add this control for Interested, Pending, Declined, Removed, or organizer rows.
RSVP transitions
If a participant moves from Going to a state that is not eligible for attendance dates, clear both participant date fields so stale attendance overrides cannot remain.
Preserve existing RSVP semantics otherwise.
Validation for organizer date edits
Before committing a core trip date change, verify that every complete participant override would still fit inside the proposed new core range.
If any would not fit:
reject the organizer update;
leave the trip and participant dates unchanged;
return/display a clear validation message.
