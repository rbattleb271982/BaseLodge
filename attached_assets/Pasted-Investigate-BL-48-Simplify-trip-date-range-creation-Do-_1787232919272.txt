Investigate BL-48 — Simplify trip date-range creation.

Do not implement anything yet. Investigation and implementation plan only.

GOAL

Simplify trip creation by removing the unnecessary “Add this range” step.

The intended interaction is:

1. User selects a start date.
2. User selects an end date.
3. Once the range is complete, BaseLodge automatically adds that range to the trip.
4. The selected range appears below the calendar using the existing selected-range treatment and remove/X control.
5. If BaseLodge supports multiple date ranges for a trip, the user can immediately select another range.
6. User saves the trip normally when finished.

The purpose of this investigation is especially to verify the existing multi-range architecture before we change the interaction.

Do not assume multi-range trips can be removed or simplified.

APPROVED PRODUCT DIRECTION

Remove the explicit:
“Add this range”

button/step if the current architecture safely allows it.

A completed start/end selection should commit automatically.

Example:

User taps:
Jan 10
then
Jan 14

BaseLodge immediately shows:

Jan 10 – Jan 14    ×

The calendar is then ready for another selection if multiple ranges are currently supported.

IMPORTANT

This task changes the DATE-SELECTION INTERACTION only.

Do not change:
- the underlying meaning of trip dates
- trip visibility
- trip status
- trip invitations
- RSVP behavior
- participant-specific dates
- trip overlap logic
- mountain selection
- trip editing permissions
- notification behavior
- existing multi-range capability unless explicitly required

MULTI-RANGE INVESTIGATION

Before recommending implementation, determine exactly how multiple date ranges currently work.

Document:

- Whether a single trip can currently contain multiple date ranges
- How those ranges are stored
- Relevant models/tables
- How ranges are created
- How ranges are removed
- How ranges are edited
- Whether ranges can overlap
- Whether adjacent ranges are merged or remain separate
- How validation works
- Whether there is a maximum number of ranges
- How the trip's overall start/end dates are derived
- What happens when only one range exists
- How existing trips with multiple ranges are rendered

Then trace every important downstream consumer of trip ranges, including where relevant:

- Trips list
- Trip Detail
- Home
- Happening
- Ideas
- profiles
- friend profiles
- mountain pages
- overlap calculations
- invitations
- notifications
- calendar/date helpers

Do NOT redesign these downstream consumers. We only need to know whether changing the creation interaction could affect them.

CREATE VS EDIT

Investigate both:

1. Creating a new trip
2. Editing an existing trip

Determine whether both use the same calendar/date-range component and JavaScript.

The intended behavior should ideally be consistent:

Select start → select end → range commits automatically.

But if Edit Trip has architectural differences that make this unsafe, identify them before implementation.

CURRENT “ADD THIS RANGE” BEHAVIOR

Trace exactly what happens today when the user:

1. selects a start date
2. selects an end date
3. taps “Add this range”

Identify:

- client-side state before the button is tapped
- what the button actually commits
- DOM/state changes
- validation performed
- hidden fields/form serialization
- server-side parsing
- whether anything is persisted before final Save Trip
- how remove/X works afterward

We need to know whether auto-commit can safely invoke the same existing behavior immediately after a valid end-date selection rather than rewriting date logic.

EDGE CASES

Investigate current behavior for:

- tapping the same date twice
- single-day trips
- end date before start date
- selecting dates that overlap an already-added range
- selecting dates adjacent to an existing range
- removing a range
- removing the only range
- editing an existing range
- abandoning a partially selected range
- changing mountain/destination after selecting dates
- validation when Save Trip is tapped with no valid range
- mobile calendar behavior

Do not invent new behavior unless the current implementation requires a decision. Flag any unresolved product decisions.

EXPECTED IMPLEMENTATION PRINCIPLE

Prefer the smallest possible change.

If the existing “Add this range” handler already correctly:

- validates the range
- appends it to selected ranges
- updates hidden/form state
- renders the selected-range chip/row
- resets the calendar selection

then the likely implementation should reuse that logic automatically when the end date is selected and remove/hide the redundant button.

Do not duplicate that logic.
