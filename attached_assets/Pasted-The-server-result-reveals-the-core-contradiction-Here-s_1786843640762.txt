### The critical contradiction — device says `optedIn=true`, server says `enabled=False`

The OneSignal API right now shows subscription `f10dcf69` is **back to `enabled=False, notification_types=-30`**. The server-side state reverted between the previous log session (where `optIn()` flipped it to `enabled=True, notification_types=31`) and these sessions.

**What's happening on every launch, in order:**

1. `initialize()` + `login()` complete
2. `getOptedInAsync()` (from `[OSTrace]`) fires and reads the SDK's **local cache** → returns `true` (the `optIn()` from the previous session is still cached locally)
3. Simultaneously, `getPermissionInternal` fires → returns `not_determined` (because OneSignal's permission state machine never saw a grant through its own flow)
4. The SDK, seeing `not_determined`, **asynchronously pushes an opt-out to the server** → `f10dcf69` reverts to `enabled=False, notification_types=-30`
5. `[OSTrace]` logs `optedIn=true` because step 2 reads the local cache **before step 4's server sync completes**

So `optedIn=true` from `getOptedInAsync()` is not a reliable signal of server-side state — it's a local snapshot that gets overwritten by the permission-check cycle seconds later.

### Root cause is now fully confirmed

`OS permission status=not_determined` → SDK opts out the subscription on every launch. The fix is `OS.Notifications.requestPermission()` — the method exists (`Notifications=true` every session), but the init code never calls it because it checks `OS.requestPermission` (top-level, absent) instead of `OS.Notifications.requestPermission` (correct location).

Until that fix lands, the subscription will revert to opted-out within seconds of every cold launch, and pushes sent while it appears opted-in will race against the reversion. The `optedIn=true` local-cache read is not a reliable delivery guarantee.
