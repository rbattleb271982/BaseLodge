KNOWN PRODUCT / ARCHITECTURE DIRECTION
==================================================

Use the repository as the primary evidence source.

The following are established BaseLodge product boundaries that may not all be fully represented in the current code yet.

Use them only to evaluate whether the existing architecture can safely support documented future direction.

Do not invent additional roadmap features.

Core architecture:

- Home = what is happening now.
- Profile = who the user is plus personal BaseLodge configuration.
- Notifications = what happened.
- Needs You = what still requires attention.
- Seen/unseen and resolved/unresolved are separate concepts.
- Red badges represent unseen activity, not unresolved-work totals.
- Availability is canonical and private.
- Open to Ski is first-person presentation of Availability.
- Open to Ski overlap represents possibility, not commitment.
- Trips remain separate from Availability.
- Creating or joining an overlapping Trip may offer to remove overlapping Availability but must never silently mutate it.
- Buddy passes are personal inventory with selective social utility.
- Wishlist represents future interest, not unfinished work.
- Trip participant follow-up is coordination-first, not accountability or nagging.

Favorite Friends direction:

- Favorite Friends are private and one-way.
- No reciprocal state.
- No limit.
- Favorite state ends permanently if the friendship ends.
- Favorite prioritization stops at the direct friend and does not propagate through second-degree relationships.
- Favorites may sort first in people-oriented contexts.
- Favorites do not change Suggested Friends.
- Favorites do not create notification eligibility.
- Favorites do not alter push timing or delivery.
- Overlap summaries remain simple rather than exposing separate Favorite counts.

Attention architecture:

- Notifications contain relevant recent activity and answer "What happened?"
- Notifications are not the canonical pending-action destination.
- Needs You contains unresolved attention.
- Resolution actions live in appropriate context.
- Seen does not mean resolved.
- Resolving something elsewhere reconciles the corresponding attention state.
- Informational notifications age out.
- Deep links should go to the owning destination.
- Native badge should reflect unseen Notifications, not Needs You.

Native direction:

- Capacitor remains the current mobile architecture.
- Push taps should deep-link to current authorized state.
- Authentication should preserve intended push destination.
- Stale push payloads should recover safely.
- Foreground suppression should occur only when the exact owning context is already visible.
- Native badge should reconcile against server-authoritative unseen Notification state.

Messaging/email direction:

- Email infrastructure is being hardened before BaseLodge intentionally designs user-facing email programs.
- Do not assume currently named preference fields represent approved future email categories.

Performance direction:

- BaseLodge already has some intent-based route prefetching.
- Static assets use long-lived immutable caching.
- Privacy-sensitive projections remain server-authorized.
- Do not broaden speculative loading of private/mutable data merely for speed.
- Real-world measurement should precede major optimization.
- Capacitor cold/warm/resume/network behavior must be considered separately from ordinary web navigation.

Design/product philosophy:

BaseLodge should optimize for better real-world skiing, coordination, relationships, and memories.

It should not optimize for screen time, manufactured urgency, engagement for its own sake, FOMO, or social pressure.

This matters to the technical pre-mortem when architecture begins forcing product behavior in undesirable directions.

==================================================
EVIDENCE STANDARD
==================================================

This report must clearly distinguish:

KNOWN DEFECT
A problem directly demonstrated by current code, tests, configuration, schema, or reproducible behavior.

EVIDENCED RISK
Not necessarily broken today, but repository evidence shows a credible path to failure.

PLAUSIBLE RISK
Technically possible and relevant, but current evidence is insufficient to say it is likely.

UNKNOWN / UNPROVEN ASSUMPTION
Something important that cannot be determined from the repository or available environment.

NOT ACTUALLY A PROBLEM
An area investigated because it appeared risky, but the current architecture is appropriate or sufficiently protected.

Do not convert uncertainty into certainty.

If you do not know, say so.

For unknowns, explain exactly what measurement, load test, production telemetry, restore drill, security review, or other evidence would resolve the uncertainty.

==================================================
SEVERITY / STRATEGIC CLASSIFICATION
==================================================

Classify material findings as:

EXISTENTIAL
Could plausibly contribute to BaseLodge failing as a durable product, suffering a serious security/privacy incident, losing/corrupting important data, or requiring an emergency architectural migration.

STRUCTURAL
Not likely to kill BaseLodge immediately, but becomes increasingly dangerous or limiting as BaseLodge moves toward 10K/50K users and three more years of development.

MANAGEABLE DEBT
A legitimate engineering issue that should eventually be addressed but should not distract from larger risks.

NOT ACTUALLY A PROBLEM
Investigated and found to be acceptable.

Do not inflate severity.

A long list of "critical" findings is not useful.

INVESTIGATION METHOD
==================================================

Inspect the repository broadly before reaching conclusions.

Build an architectural map first.

Trace important user/data lifecycles rather than reviewing isolated files.

Examples:

- authentication -> session -> authorization -> protected request
- friendship creation -> social visibility -> friendship removal
- Availability -> overlap projection -> Trip creation/join -> reconciliation
- Trip creation -> participation -> modification -> deletion
- Notification creation -> unseen -> seen -> resolution -> retention
- Suggested Friend -> request -> withdrawal/acceptance -> cleanup
- account creation -> years of activity -> account deletion
- push generation -> delivery -> tap -> authorization -> destination
- schema migration -> deployment -> rollback/recovery
- app launch -> authentication -> Home -> subsequent navigation
- native cold launch -> warm launch -> resume
- failure -> detection -> diagnosis -> rollback/restore

Use code, tests, migrations, configuration, documentation, dependency manifests, workflows, and other repository evidence.

Where useful, inspect Git history for architectural context, but do not treat old/dead code as current behavior without verifying it.

Do not access or modify real user data.
