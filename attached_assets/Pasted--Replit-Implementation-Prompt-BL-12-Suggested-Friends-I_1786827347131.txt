## Core behavior

Connected BaseLodge users can privately suggest their own existing connections to another user they are already connected with.

Example:

Richard is connected to Jon.

Richard can privately suggest Jennifer to Jon.

Jon sees Jennifer under **Suggested Friends** with attribution such as:

`Suggested by Richard`

Jennifer receives **no notification** that Richard suggested her.

If Jon chooses Connect, Jennifer receives only the normal BaseLodge connection request.

## Authorization

Suggestions may only be created between users who are currently connected.

For both:

`GET /friends/<friend_id>/suggest`

and

`POST /friends/<friend_id>/suggest`

the friendship authorization check must happen before form parsing or suggestion eligibility logic.

A non-connected user attempting to access or submit directly should receive a non-disclosing response such as 404.

Do not trust client-side eligibility.

Revalidate every submitted suggested user ID on the server.

## Database / Models

Implement the finalized `FriendSuggestion` architecture.

Conceptual fields:

* `id`
* `suggester_id`
* `recipient_id`
* `suggested_user_id`
* `created_at`
* `expires_at`
* `dismissed_at`

Suggestions expire 30 days after creation.

Multiple different recommenders may independently suggest the same person to the same recipient.

### Active uniqueness requirement

Do **not** use a permanent:

`UNIQUE (suggester_id, recipient_id, suggested_user_id)`

constraint.

That would break valid re-suggestion after dismissal or expiration.

Instead use the finalized active-only uniqueness strategy:

* partial unique index on:
  `(suggester_id, recipient_id, suggested_user_id)`
* only where:
  `dismissed_at IS NULL`

This must work in both production PostgreSQL and SQLite tests.

Migration direction:

`op.create_index(
    'uix_friend_suggestion_active',
    'friend_suggestion',     ['suggester_id', 'recipient_id', 'suggested_user_id'],
    unique=True,
    postgresql_where=sa.text('dismissed_at IS NULL'),
    sqlite_where=sa.text('dismissed_at IS NULL')
)`

Before inserting a fresh suggestion for a tuple, lazily close any expired active row for that same tuple by setting:

`dismissed_at = NOW()`

where:

* same suggester
* same recipient
* same suggested user
* `dismissed_at IS NULL`
* `expires_at <= NOW()`

This allows the new row to get:

* fresh `created_at`
* fresh `expires_at`
* fresh 30-day window

### Critical transaction safety requirement

A concurrency collision for **one suggested user must not roll back or prevent the other valid suggestions in the same submitted batch**.

If `flush()` or insert hits `IntegrityError` because another request concurrently inserted the same active tuple, do **not** use a plain rollback pattern that wipes the whole batch transaction.

Use a safe approach such as:

* nested transaction / savepoint per insert
* conflict-safe insert strategy
* another SQLAlchemy pattern that isolates the individual collision

The result must be:

Richard submits 20 people.

One person collides because another concurrent request inserted the same active suggestion.

The other 19 valid suggestions must still commit successfully.

The collision should simply behave as an idempotent duplicate for that one person.

## Selector UX

Add a dedicated full-screen suggestion selector.

Entry points:

1. Permanent **Suggest connections** action on the connected friend's profile
2. One-time action inside the connection-accepted toast for the original request sender

The selector shows the suggester's own BaseLodge connections.

Requirements:

* searchable
* alphabetical by first name, then last name
* multi-select
* no explicit numerical selection limit
* no profile photos
* display format like:
  `Michael Smith, NY`
* checkbox-style row interaction
* sticky CTA:
  `Suggest 8 people`

## Selector eligibility

Load eligibility in batch. Avoid N+1 queries.

For Richard suggesting to Jon:

### Already connected to Jon

Hide entirely.

### Pending direct Invitation involving Jon

Show but disable:

`Request pending`

### Already actively suggested by Richard

Show but disable:

`Already suggested`

Only active means:

* `dismissed_at IS NULL`
* `expires_at > NOW()`

Expired prior suggestions should not disable the candidate.

### Suggested by someone else

Still selectable.

Multiple independent recommenders are allowed.

### Other validation

The server must also prevent:

* suggesting Jon to himself
* suggesting Richard to himself
* submitting a person who is not actually Richard's connection
* submitting someone already connected to Jon

Re-check state on POST because it may have changed after the selector loaded.

## Confirmation

* the suggested people will **not** be notified

After successful submission:

* return to Jon's profile
* show a brief success toast such as:
  `8 people suggested to Jon`

## Inbound pending request state — finalized behavior

This is now fully decided.

When Jennifer appears in Jon's Suggested Friends but Jennifer has already sent Jon a pending connection request:

show:

**Accept**

not:

**Connect**

Use one batch Invitation query when loading Suggested Friends:

* `receiver_id == current_user.id`
* `sender_id IN suggested_user_ids`
* direct invitation only
* pending status

Add to each display row:

* `has_inbound_request`
* `inbound_invitation_id`

If true, render **Accept**.

Tapping Accept must call the existing invitation acceptance flow using the invitation ID.

After successful acceptance, Jennifer disappears immediately from Suggested Friends.

If the request state changed between page load and action, handle the non-success response gracefully and refresh/reconcile the tab rather than producing a broken state.

Do not create a reverse outbound request when an inbound request already exists.

## Normal Connect behavior

If there is no inbound pending request:

show:

**Connect**

Tapping Connect uses the existing direct friend invitation flow.

On successful request creation:

* remove the person immediately from Suggested Friends
* existing BaseLodge pending-request UX owns the state afterward

Handle duplicate/race states gracefully. Do not allow Invitation `IntegrityError` to cause a 500.

## Dismiss behavior

Dismiss endpoint should accept a suggested user ID and operate only where:

`recipient_id == current_user.id`

Set `dismissed_at = NOW()` on all active rows for:

`(recipient=current_user, suggested_user=X)`

regardless of recommender.

Then remove the row client-side.

No one is notified:

* not the suggester
* not other recommenders
* not the suggested user

There is no additional suppression rule.

A later valid new suggestion may cause that person to reappear.

## Expiration

Suggestions expire after **30 days**.

No background cleanup job is required for V1.

Active queries should simply exclude:

`expires_at <= NOW()`

Historical expired rows may remain stored.

For multiple recommenders, the person remains visible as long as at least one active recommendation row remains.

## Normal disconnect

If Richard and Jon later disconnect normally:

do not retroactively remove Richard's previously valid suggestions.

They remain until:

* Connect / Accept
* dismiss
* expiration

## Push notification

`"{first_name} suggested some people you may know. See who."`

Example:

`Richard suggested some people you may know. See who.`

Use the suggester's first name dynamically.

One push per eligible batch, regardless of whether the batch contains 1 person or 25 people.

Payload:

`data={"url": "/friends?tab=suggested"}`

## Push cooldown

12-hour cooldown per:

`(suggester_id, recipient_id)`

Within the cooldown:

* valid new suggestions still insert immediately
* Suggested Friends updates normally
* Activity behavior follows the finalized plan
* only the push is suppressed

A push failure must not undo suggestion creation.

Do not let a transient push-provider error consume the cooldown unless that matches the existing push helper's defined success/skip semantics.

## Performance

Avoid N+1 queries throughout.

In particular:

* selector eligibility should use batch queries
* Suggested Friends should batch-load suggested users
* recommender users should be batch-loaded
* inbound pending Invitation states should be one batch query
* attribution should be assembled without per-row DB lookups

For PostgreSQL/SQLite compatibility, prefer a clean Python-level grouping approach if that avoids dialect-specific SQL such as `array_agg`.

Do not add dialect complexity unless it materially improves the implementation.
