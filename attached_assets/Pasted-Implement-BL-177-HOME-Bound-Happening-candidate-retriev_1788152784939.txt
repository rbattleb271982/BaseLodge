Goal:
Replace Home Happening’s reuse of the Ideas engine’s unbounded friend-trip population with a dedicated, bounded Happening retrieval path.

APPROVED ARCHITECTURE

Use a dedicated Happening retrieval query/helper.

Ordering:
1. activity timestamp descending
2. trip ID descending only when activity timestamps are equal

Activity timestamp must preserve the current rule:
- use updated_at
- fall back to created_at

Per-friend behavior:
- owner and participant occurrences compete together
- select exactly one winning occurrence per attendance user/friend
- winner is the newest qualifying occurrence under the approved ordering

Dismissal behavior:
- winner selection happens BEFORE dismissal
- if the winning trip for a friend has been dismissed by the current user, do NOT fall back to an older qualifying trip for that friend

Final result:
- return at most five final Happening candidates

This architecture is independent from BL-176.
Do not alter Ideas retrieval or ranking.

DEDICATED RETRIEVAL

Implement the safest bounded database-side approach.

Expected approach:
- combine owner and participant qualifying occurrences
- carry attendance user/friend identity
- carry trip identity
- carry effective attendance dates where needed
- compute activity timestamp using current updated_at/created_at behavior
- rank rows per friend
- select rank 1
- apply user-specific dismissal so dismissed winners disappear without exposing older rows
- order remaining winners by:
  - activity timestamp DESC
  - trip ID DESC
- limit final results to 5

Do not materialize the full qualifying friend-trip population in Python.

Do not use an arbitrary pre-ranking LIMIT.

Do not introduce a finite overfetch heuristic.
