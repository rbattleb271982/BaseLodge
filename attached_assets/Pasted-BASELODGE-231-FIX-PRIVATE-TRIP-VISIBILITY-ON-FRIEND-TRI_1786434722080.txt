BASELODGE — #231 FIX PRIVATE TRIP VISIBILITY ON FRIEND-TRIP ROUTE

Implement ONLY the privacy fix identified in Audit #228 for:

GET /friend-trip/<id>

Do not change unrelated trip permissions, invite behavior, notifications, schema, or frontend architecture.

==================================================
BACKGROUND
==================================================

Audit #228 found:

GET /friend-trip/<id>

currently verifies that the viewer is a friend of the trip owner, but does not consistently enforce:

SkiTrip.is_public

That means a friend may be able to open a trip marked private by navigating directly to the friend-trip URL.

Desired product behavior:

Private trip:
- visible to owner
- visible to ACCEPTED / authorized trip members through the normal trip-detail experience
- NOT visible to ordinary friends through /friend-trip/<id>

Public trip:
- friends may view it through /friend-trip/<id> according to the existing friend-view rules

This task should close only that privacy gap.

==================================================

GET /friend-trip/<id>

- login

- trip owner

- is_public
- participant membership
- redirects / 403 / 404 behavior

Do not change anything until the current behavior is understood.

==================================================
2. ENFORCE is_public
==================================================

For the friend-view route:

If the viewer is NOT the trip owner and is only accessing because they are a friend:

require:

trip.is_public == True

If trip.is_public == False:

deny access.

Use the application's existing privacy-denial convention.

Prefer the same 403/404 behavior already used for inaccessible trip data rather than inventing a new page.

Do not expose private trip details in the error response.

==================================================

Check whether accepted participants ever use /friend-trip/<id>.

Do not broaden access beyond current rules.
