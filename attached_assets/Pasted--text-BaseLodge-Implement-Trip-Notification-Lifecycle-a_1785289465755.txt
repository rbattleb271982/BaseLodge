BaseLodge — Implement Trip Notification Lifecycle and Fix Trip-Accept Success Wording

Use the completed Push Notification Audit as the source of truth.

This is an implementation task. First inspect every affected route and confirm the existing execution paths before editing. Then implement the approved notification behavior below.

- emit_messaging_event() orchestration
- EventSpec registry
- OneSignal delivery provider
- notification preference checks
- MessageEventLog records
- one-hour duplicate suppression
- existing trip deep-link pattern

IMPORTANT PRODUCT SEMANTICS

In BaseLodge, accepting a trip invitation does not necessarily mean the user is definitely traveling.

Trips can have:

- Planning status
- Going status

Notification and UI wording must not imply confirmed attendance unless the trip is actually in Going status.

PART 1 — Preserve existing notification wording

Do not change these existing push notifications.

1. Trip invitation sent

Trigger:
An existing BaseLodge friend is invited through the in-app Invite Friends flow.

Recipient:
Invited user.

Title:

{Inviter name} invited you to a trip

Body:

You've been invited to {resort}.

2. Trip invitation accepted — owner notification

Trigger:
An invited user accepts a trip invitation.

Recipient:
Trip owner.

Title:

{Name} accepted your invite

Body:

They're joining you for {resort}.

Keep this wording unchanged. “Joining” is sufficiently neutral for both Planning and Going trips.

3. Friend request accepted

Trigger:
A user accepts a friend request.

Recipient:
Original requester.

Title:

{Name} accepted your request

Body:

You're now connected on BaseLodge.

Do not change friend-request notification behavior.

Friend-request declines and friend removals must remain silent.

in trip-acceptance routes.

Before changing the text, verify whether Flask flash messages are currently visible in:

- the regular web application
- the Capacitor iOS app
- the Capacitor Android app

- the flash() call
- the redirect
- the destination template
- the layout or component that renders flashed messages

- an alert
- toast
- banner
- snackbar
- another component

- POST /trips/<trip_id>/respond
- POST /trip-invite/<token>/accept

Required wording:

If trip.trip_status == "going":

You're going!

Otherwise:

You're planning!

Use the trip status after the successful database commit.

Although the external TripInviteToken flow is currently hidden from the UI, keep both acceptance routes consistent.

Do not change:

- participant acceptance behavior
- database statuses
- acceptance push notification text
- notification recipients
- notification delivery infrastructure

If the flash message is not currently user-visible, do not create a new UI component as part of this task. Report why it is not visible and whether the text-only change would have any effect.

PART 3 — Notify the owner when an invitation is declined

Trigger:
An invited participant declines a trip invitation.

Recipient:
Trip owner only.

Title:

{Name} declined your invite

Body:

They won't be participating in the {resort} trip.

Requirements:

- Dispatch only after the decline is successfully committed.
- Do not notify the declining user.
- Do not notify other trip participants.
- Use the same trip deep link as the existing trip-acceptance notification.
- Use the existing preference, logging, and deduplication infrastructure.
- A repeated decline or repeated request must not create duplicate pushes.
- Confirm every route through which a trip invitation can be declined and make behavior consistent where appropriate.

PART 4 — Notify existing participants when an invitation is accepted

The trip owner already receives the existing personalized acceptance push:

{Name} accepted your invite
They're joining you for {resort}.

Keep that notification unchanged.

In addition, notify the other existing accepted participants when someone accepts an invitation.

Recipients:

- Existing accepted participants
- Exclude the person who just accepted
- Do not send the generic notification to the owner if the owner already receives the personalized owner notification
- Do not send duplicate notifications to any recipient

Generic participant notification:

Title:

Someone accepted an invitation

Body:

A new participant has been added to the {resort} trip.

This wording is intentionally generic because not every participant will necessarily be friends with or know the accepting person.

It also avoids implying that the accepting person is definitely going.

Requirements:

- Dispatch after the acceptance transaction commits.
- Only notify users who are already accepted participants at that point.
- Do not notify pending or declined invitees.
- Preserve the owner’s existing personalized acceptance notification.
- Use the existing trip deep link.
- Ensure both acceptance routes behave consistently.
- Use existing duplicate suppression.

PART 5 — Notify participants when someone leaves a trip

This applies when a participant who previously accepted voluntarily removes themselves or leaves the trip.

Recipients:

- Trip owner
- All remaining accepted participants
- Exclude the person who left
- Do not notify pending invitees
- Do not notify declined invitees

Title:

A participant left the trip

Body:

A participant has left the {resort} trip.

Requirements:

- Keep the wording generic.
- Dispatch only after the participant has successfully been removed or their status has been updated.
- Identify every current route that allows an accepted participant to leave.
- Do not confuse leaving after acceptance with declining a pending invitation.
- Prevent duplicate pushes if the leave action is repeated.
- Use the trip deep link and current notification infrastructure.

PART 6 — Notify a participant when the owner removes them

This applies when the trip owner removes a participant.

Recipient:

- Removed participant only

Do not notify:

- the owner
- remaining participants
- pending invitees unrelated to the action

Title:

You've been removed from the trip

Body:

You're no longer participating in the {resort} trip.

Requirements:

- Dispatch after the removal transaction commits.
- Confirm whether the same route can remove accepted and pending participants.
- If a pending invite is withdrawn through this route, determine whether this wording is still accurate. Do not guess. Report the state distinctions and use status-appropriate logic if necessary.
- Use the trip deep link only if the removed user can still open a meaningful destination.
- If the removed user will no longer have authorization to open the trip, use the safest existing destination, such as the Trips page, rather than deep-linking to an inaccessible page.
- Do not expose private information about other participants.
- Use existing preferences, logging, and deduplication.

PART 7 — Notify participants when a trip is cancelled or deleted

Trigger:
The trip owner cancels or deletes the entire trip.

Recipients:

- All accepted participants
- All currently invited participants
- Exclude the owner
- Exclude declined or previously removed users unless the current data model still treats them as active recipients

Title:

{Resort} trip cancelled

Body:

The trip has been cancelled by the organizer.

Requirements:

- Determine the actual deletion or cancellation routes.
- Determine whether the trip is hard-deleted, soft-deleted, archived, or status-updated.
- Notification recipient information must be captured before a hard delete removes the records needed to identify recipients.
- Pushes must not be sent before the database action is known to have succeeded.
- If the trip is hard-deleted, the notification must not deep-link to a now-missing trip page.
- Use an existing valid destination such as the Trips page when the original trip URL will no longer work.
- Prevent duplicate cancellation notifications.
- Do not notify the owner who performed the cancellation.

PART 8 — Notify participants when important trip details are updated

Trigger:
The trip owner makes a meaningful change to the trip.

Recipients:

- Accepted participants
- Invited participants
- Exclude the owner
- Exclude declined, removed, or otherwise inactive participants

Title:

Trip updated from {name}

Body:

The details of the {resort} trip have changed.

First identify all editable trip fields and the routes used to update them.

Classify which changes should trigger this notification.

At minimum investigate:

- resort or destination
- trip dates
- trip status, including Planning to Going
- lodging or accommodation information
- other fields shown as core trip details

Do not send this push for inconsequential technical changes such as:

- timestamps
- internal IDs
- analytics fields
- unrelated metadata
- updates that do not change a user-visible value

Requirements:

- Send one notification per completed update action, not one per changed field.
- Dispatch only after the update commits.
- Do not send a notification when the submitted values are unchanged.
- Avoid generating a notification from background or internal updates that were not performed by the trip owner.
- Use the trip deep link.
- Use existing preferences, logging, and duplicate suppression.
- Confirm that rapid legitimate updates will not be incorrectly lost because the existing one-hour deduplication key is too broad. If the current deduplication design would suppress distinct trip updates, report the issue and use an event/object strategy that prevents accidental duplicates without hiding separate valid updates.
