Implement BL-42 — Add friend availability overlap to mountain pages using the completed investigation.
This is an implementation task. Do not re-investigate the feature.
Goal
On a mountain detail page, show a compact friend-availability signal when the signed-in user has an upcoming or in-progress trip at that mountain and confirmed friends have explicitly marked themselves available during that trip.
Core rule
Only show availability when the signed-in user has an explicit qualifying trip at the current resort.
Do not infer mountain availability from:
general availability without an own trip
lack of another trip
Going or Interested RSVP
wishlist
Been Here
Own trip windows
Determine the signed-in user's effective upcoming/in-progress trip windows at the current resort.
For each:
If the signed-in user is a participant and has both participant-specific start_date and end_date, use those dates.
Otherwise use SkiTrip.start_date and SkiTrip.end_date.
Treat boundaries as inclusive.
Ignore past trips.
Coalesce identical effective windows.
Do not require the user's own trip to be public merely to calculate their own availability context.
Friend availability
Only direct confirmed friends can qualify.
Resolve explicit availability using existing BaseLodge semantics:
UserAvailability is authoritative when the friend has table-backed availability.
Otherwise fall back to legacy User.open_dates.
Use only explicit available dates.
A friend qualifies for a trip window if at least one available date intersects that window.
Partial overlap qualifies.
Do not require the friend to be available for every day.
Query efficiency
Do not call get_available_dates_for_user() separately for every friend if that creates an N+1 query pattern.
Implement/reuse a focused batch helper that:
takes the existing confirmed friend IDs
loads their UserAvailability records in one query
builds friend_id → available dates
uses already-loaded User.open_dates as fallback for friends without table rows
calculates overlap against the viewer's effective trip windows
Display
Add a compact availability summary to the existing mountain social section after current-intent groups and before recorded-visit/wishlist summaries.
Examples:
Alex is free during your Feb 6–8 trip
3 friends are free during your Feb 6–8 trip
Use during, not for, because a friend may overlap only part of the trip.
Do not display:
raw availability calendars
complete available-date lists
availability notes
availability source
If zero friends overlap, omit the group entirely.
Multiple trips
If the signed-in user has multiple distinct qualifying trip windows at the mountain:
create one compact summary per distinct effective window
deduplicate each friend within a window
the same friend may legitimately qualify for two different trip windows
identical windows should not produce duplicate summaries
Going / Interested overlap
Preserve Going This Winter and Interested as independent RSVP-based signals.
Availability counts should include all qualifying direct friends even if they are also Going or Interested.
For visible name previews, suppress friends already visibly represented in Going/Interested if that matches the existing BL-33/social-summary convention found in the codebase.
Do not change the underlying availability count when suppressing a duplicate visible name.
Privacy
Maintain the existing confirmed-friend boundary.
Never include:
pending invitations
removed friends
non-friends
friends of friends
Do not expose raw availability information.
This feature should expose only the derived, trip-scoped overlap signal.
Do not change availability privacy copy as part of BL-42. Flag the existing “Only you can see your availability” wording in the completion report so it can be handled separately.
