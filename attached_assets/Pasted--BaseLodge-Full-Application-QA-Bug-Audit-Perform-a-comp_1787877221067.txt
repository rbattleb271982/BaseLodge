# BaseLodge Full Application QA + Bug Audit

Perform a comprehensive **READ-ONLY bug audit of the entire BaseLodge application**.

## Mode

Use the strongest available application-testing and code-inspection capabilities.

This is an audit only.

Do **not** fix bugs, edit code, commit, push, publish, deploy, run migrations, change schema, change secrets, or mutate production data.

The purpose is to identify real defects, regressions, broken states, inconsistent behavior, privacy issues, and user-experience failures across the application.

---

# Primary objective

Test BaseLodge as a real user would use it and identify anything that:

* does not work
* behaves incorrectly
* contradicts another part of the product
* produces broken or misleading UI
* exposes data it should not
* hides data it should show
* fails in an empty or edge state
* breaks navigation
* produces a server error
* produces a browser console error
* produces an incorrect count
* produces stale or inconsistent state
* has a broken mobile interaction
* fails after refresh
* fails when a user has little or no data
* fails when a user has a lot of data
* appears to be implemented in code but is functionally broken

Do not spend the audit proposing new features. Focus on defects in existing behavior.

---

# Audit methodology

Use both:

## A. Application testing

Exercise the actual running BaseLodge application in the browser.

Test authenticated flows wherever test credentials / existing development users permit.

Use mobile-width testing as well as desktop-width testing.

Capture:

* UI failures
* navigation failures
* rendering issues
* console errors
* failed network requests
* server errors
* unexpected redirects
* state inconsistencies

## B. Code-level verification

For every bug or suspicious behavior found in the browser:

* trace it into the relevant route
* template
* helper
* model
* JavaScript
* service
* test coverage

Also inspect code for meaningful bugs that may be difficult to trigger manually.

Do not report theoretical style problems as bugs unless they have a plausible user-visible or data-integrity consequence.

# Bug severity

Classify findings:

## P0 — Critical

Examples:

* data corruption
* cross-user data exposure
* destructive action affecting wrong user/data
* widespread inability to use the app

## P1 — High

Examples:

* major core flow broken
* serious privacy/authorization issue
* incorrect trip/RSVP state
* major feature unusable

## P2 — Medium

Examples:

* incorrect counts
* broken secondary flow
* meaningful UI/state inconsistency
* persistent interaction failure

## P3 — Low

Examples:

* minor rendering bug
* copy mismatch that causes confusion
* small mobile layout problem
* edge-case UX defect

Do not inflate severity.

---

# Evidence required for every bug

For each confirmed bug include:

1. **Bug ID**
2. **Severity**
3. **Area**
4. **User scenario**
5. **Steps to reproduce**
6. **Expected behavior**
7. **Actual behavior**
8. **Evidence**

   * screenshot / browser observation
   * console/network/server output where available
9. **Likely root cause**
10. **Exact relevant files/functions**
11. **Existing test coverage**
12. **Recommended fix direction**
13. **Confidence**

* Confirmed
* High
* Medium
* Suspected

Do not call something a confirmed bug without reproducible evidence.

---

# Separate findings into four groups

## A. Confirmed bugs

Reproduced and supported by evidence.

## B. High-confidence code defects

Not fully reproducible in available test data but clearly wrong from code inspection.

## C. Test failures / technical debt

Broken or stale automated tests, warnings, dead code, inconsistent comments, or infrastructure issues.

## D. Product ambiguities

Behavior that may be intentional but appears inconsistent.

Do not classify product ambiguity as a bug.
