Verify the implementation of BL-518: Pending Request Withdrawal.

This is a read-only verification and regression audit. Do not modify code, database schema, fixtures, tests, or data unless explicitly asked after the audit.

## Scenario to verify

Use this exact behavior as the target:

1. Richard suggests Eric to Charles.
2. Charles sees the suggestion.
3. Charles sends Eric a connection request.
4. Eric has not accepted or declined.
5. Charles withdraws the request.
6. Charles and Eric should return to a non-pending, non-connected state.
7. Eric must no longer have an actionable request from Charles.
8. Eric must not be able to accept the withdrawn request from stale UI.
9. Canonical request/friendship history and suggestion attribution must remain intact.

## 4. Verify stale acceptance protection

This is critical.

Simulate or inspect the equivalent state transition:

1. Charles sends request.
2. Eric loads a UI showing the pending request.
3. Charles withdraws it.
4. Eric attempts to accept using the stale UI/request.

Confirm the server rejects the acceptance and does not create a friendship.

The persisted request state must win over stale client state.

Mark BL-518 as failing if stale acceptance can recreate the friendship.

## 5. Verify repeated withdrawal

Check:

1. Charles withdraws successfully.
2. Charles or a stale client submits the withdrawal again.

Confirm the result is safe and consistent with BaseLodge's existing idempotency/error conventions.

There must be no:

* duplicate history
* duplicate cancellation events
* broken friendship rows
* server error caused by inconsistent state

## 6. Verify authorization

Confirm:

* Charles can withdraw Charles → Eric.
* Eric cannot withdraw Charles → Eric as though Eric were the sender.
* Richard cannot withdraw the request merely because Richard created the original suggestion.
* another authenticated user cannot withdraw it.

Authorization must be enforced server-side, not only through UI visibility.

## 7. Verify acceptance and decline races

Inspect the authoritative outcomes for:

### Accept wins first

Eric successfully accepts before Charles's withdrawal is committed.

Expected:

* friendship is established
* Charles can no longer use pending-request withdrawal
* any later action must follow normal friendship-removal behavior

### Withdrawal wins first

Charles successfully withdraws before Eric's acceptance is committed.

Expected:

* Eric's acceptance fails
* no friendship is established

### Decline wins first

Eric declines before Charles withdraws.

Expected:

* withdrawal does not improperly mutate the already-terminal request
* final state remains internally consistent

Confirm these transitions are protected by server-side persisted state.
