TASK: BL-158 — Bound My Trips retrieval with pagination/progressive loading

INVESTIGATE AND DESIGN ONLY.
Do not implement yet.

==================================================
GOAL
==================================================

Determine how My Trips retrieval, Python processing, and rendered card volume scale as a user's trip history grows, then design the smallest safe pagination/progressive-loading approach.

BL-161 established that My Trips query shape is already reasonably bounded:

- warmed baseline: 14 SQL statements
- 2 User SELECTs

Therefore BL-158 is primarily a RESULT-VOLUME and RENDERING task, not a query-count cleanup.

Do not optimize SQL statement count for its own sake.

==================================================
1. FIND AUTHORITATIVE BL-158 REQUIREMENTS
==================================================

Locate any existing BL-158 task/backlog requirements.

Use them as authoritative if found.

Review related completed work only for boundaries:

- BL-80 terminal trip history
- BL-133 authenticated social visibility
- BL-155 Trip Detail query cleanup
- BL-161 authenticated-page query overhead
- BL-156 Home candidate bounding

Keep BL-159 Friends pagination separate.

==================================================
2. MAP CURRENT MY TRIPS PIPELINE
==================================================

Trace the complete authenticated:

/my-trips

request.

Document:

SOURCE RECORDS
→ SQL ELIGIBILITY
→ ORM MATERIALIZATION
→ PYTHON PROCESSING
→ GROUPING/SORTING

- trips organized by viewer
- trips where viewer is Going
- trips where viewer is Interested
- pending invitations/requests if applicable
- completed trips
- cancelled trips
- any other historical state currently displayed

Do not infer states that the current product does not show.

==================================================
3. DOCUMENT CURRENT PRODUCT SEMANTICS
==================================================

Establish exactly how My Trips currently separates and orders:

- upcoming/current trips
- historical trips
- completed trips
- cancelled trips

- participant trips

Document:

- section order
- within-section ordering

- empty states
- counts

BL-158 must preserve these semantics unless an existing authoritative requirement explicitly changes them.

==================================================
4. MEASURE CURRENT SCALING
==================================================

Use disposable fixtures only.

At minimum test eligible trip populations of:

- 10
- 50
- 100
- 500

Where practical distinguish:

A. all upcoming
B. all historical
C. mixed upcoming + historical
D. owned + participant mix

Measure:

- SQL statement count

- Python trip/card structures created
- rendered trip cards
- approximate response HTML size
- directional request time

Timing is diagnostic only.

Do not use timing as the acceptance budget.

==================================================
5. IDENTIFY THE ACTUAL VOLUME PROBLEM
==================================================

Determine whether My Trips currently retrieves and renders every qualifying trip.

Quantify patterns such as:

500 eligible trips
→ 500 Trip objects
→ 500 card models
→ 500 rendered cards

Do not assume this is the exact behavior before measuring it.

Identify separately:

- database retrieval volume
- ORM materialization
- Python processing
- template rendering volume
- response size

==================================================
6. UPCOMING VS HISTORY
==================================================

Determine whether upcoming/current and historical trips should have the same loading strategy.

Investigate whether a safe design should:

A. keep all upcoming trips immediately visible while paginating history

B. paginate both sections independently

C. use another existing product-compatible boundary

Base the recommendation on measured cardinality and current semantics.

Do not arbitrarily hide imminent trips.

==================================================
7. TERMINAL TRIP SEMANTICS
==================================================

BL-80 is authoritative for completed/cancelled trip history.

Verify:

- completed trips remain discoverable where currently intended
- cancelled trips remain discoverable where currently intended
- terminal trips remain read-only
- historical access rules remain unchanged
- terminal lifecycle events/history never authorize access

Pagination must not accidentally make retained historical trips inaccessible.

==================================================
8. PARTICIPANT ATTENDANCE
==================================================

Preserve current attendance semantics for participant trips.

Determine how My Trips eligibility uses:

- Going
- Interested
- Pending
- Declined
- Removed
- effective attendance dates

Do not broaden visibility.

Pending/Declined/Removed must retain current behavior.

==================================================
9. ORDERING AND PAGINATION CORRECTNESS
==================================================

Document the exact deterministic ordering required before designing pagination.

Identify all ordering keys, such as:

- effective attendance date
- trip start/end
- lifecycle state
- created ID or trip ID tie breaker
- owned vs participant behavior

Pagination must use a deterministic total ordering.

Do not use OFFSET/LIMIT on an incompletely ordered dataset.

==================================================
10. OFFSET VS CURSOR/KEYSET
==================================================

Evaluate the smallest appropriate mechanism.

Compare:

A. OFFSET/LIMIT
B. cursor/keyset pagination

Consider:

- expected trip counts
- implementation complexity
- deterministic ordering
- duplicate/missing cards if records change between requests
- compatibility with upcoming/history sections
- browser navigation
- existing BaseLodge architecture

Do not choose cursor pagination merely because it is theoretically more scalable.

Recommend the simplest mechanism that is safe for BaseLodge's expected scale.

==================================================
11. PAGE SIZE
==================================================

Recommend an initial card/page size based on:

- current mobile layout
- response/render cost
- typical trip volume
- usability
- implementation complexity

Evaluate reasonable sizes such as:

10
15
20

Do not invent an arbitrary size without explaining the tradeoff.

12. PROGRESSIVE LOADING UX
==================================================

Inspect existing BaseLodge frontend patterns.

Determine the least disruptive interaction:

- Load more button
- automatic progressive loading
- conventional pagination
- separate history expansion

Prefer an existing application pattern if one exists.

Do not redesign My Trips.

Preserve the current visual system.

15. COUNTS
==================================================

Identify every My Trips count displayed or used elsewhere.

Pagination must distinguish:

TOTAL ELIGIBLE TRIPS

from

CURRENTLY LOADED CARDS

Do not accidentally change a full trip count into page length.

If counts currently represent the complete dataset, preserve them.

==================================================
16. EAGER LOADING / RELATED DATA
==================================================

Determine what each visible card requires.

Examples:

- Resort
- organizer
- participant state
- attendance dates
- lifecycle state

Design page-scoped eager/batch loading so related data remains bounded with page size.

Avoid introducing a per-card N+1.

BL-161 query-shape expectations remain a regression boundary.

==================================================
17. PRIVACY / AUTHORIZATION
==================================================

BL-133 remains a hard boundary.

Pagination must happen AFTER authoritative eligibility is established or within an equivalent privacy-safe SQL query.

Do not:

- retrieve unauthorized trips and filter them client-side
- expose hidden participant identities
- broaden private-trip access
- use history as authorization

18. LARGE HISTORY BEHAVIOR
==================================================

Create representative fixtures for a user with:

- many completed trips
- many cancelled trips
- many past nonterminal/legacy trips if supported
- upcoming trips mixed with history

Determine how many records My Trips currently retrieves and how the proposed design bounds them.

==================================================

- a trip is created
- a trip is cancelled

- RSVP changes
- attendance dates change

==================================================
21. PERFORMANCE BUDGETS
==================================================

Recommend deterministic budgets.

Examples:

Initial request:
- <= page-size Trip/card materialization per paginated section
- bounded related-object loading
- bounded HTML/card rendering

Subsequent page:
- <= page size additional cards
- bounded SQL statements
- no N+1 growth

Preserve the equivalent BL-161 warmed baseline as a reference:

14 SQL statements

If pagination architecture requires a small stable change in query count, explain and justify it.
