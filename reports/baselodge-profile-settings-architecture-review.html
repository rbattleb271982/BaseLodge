BaseLodge Profile and Settings Product Architecture Review

Current ownership, navigation, future-state options, and product decisions required

Review type: Product architecture investigation only; no future-state option selected.
Evidence: Current source and tests, disposable SQLite fixtures, isolated browser checks at five viewports, and read-only task history.
Safety: No Development or Production access and no external effects.

1. Executive summary

BaseLodge does not currently have a coherent standalone Settings destination. /profile is the canonical personal hub; /settings redirects to it, while other Settings-named routes are specialist managers. Profile combines identity, ski résumé, statistics, history, navigation, privacy, notifications, security, logout, and deletion.

Most detailed editing happens on separate screens. This is technically functional but conceptually mixed: Profile displays information managed under Settings-named URLs, Settings-like controls remain inline on Profile, and identity/preferences have parallel write paths.

Confirmed findings: API name updates do not synchronize normalized search-name fields; the delete-account overlay lacks dialog/focus behavior; Profile lacks push status; account deletion has the known FK blocker in #77; Wishlist loads the active resort catalog; compatibility write paths remain for identity, passes, equipment, and wishlist.

No broad privacy or authorization failure was found. Four unranked architectures are presented.

2. Current Profile purpose

Profile is simultaneously:

  • Personal ski identity: name, discipline, ability, passes, primary equipment.
  • Ski résumé: trips, visited mountains, wishlist, Ski Days.
  • Dashboard: bounded counts and collection summaries.
  • Management hub: links to editors and specialist tools.
  • Account surface: discoverability, push, password, logout, deletion.
  • Navigation index: entry to destinations absent from bottom navigation.

The tension is that one page mixes public-facing identity, private settings, history, navigation, and destructive controls.

3. Current Settings purpose

Settings exists mainly as a route namespace. There is no visible Settings landing page. Current Settings-named managers include Equipment, Mountains Visited, Wishlist, Password, and a Profile redirect. Settings-like controls outside that namespace include Push, Edit Profile, Ski Days, Availability, Passes, Privacy, Logout, and Deletion.

Its strongest coherent jobs are specialist data management and security. Its ownership is ambiguous for identity, passes, push, privacy, history, Availability, and account deletion.

7. New/light account journey

A light account sees incomplete identity prompts, zero trips/visited/wishlist/Ski Days, no equipment, and the full Profile/History/Account architecture. Empty states provide direct paths, but the user encounters many management destinations before having meaningful data. Availability is reached through Home, a post-pass nudge, or its dedicated editor—not a normal Profile row.

9. Dense account journey

Dense Profile remains bounded by summarizing rather than rendering full collections. Verified state included multiple passes, primary equipment, nine upcoming trips, twelve visited mountains, fifteen wishlist mountains, three Ski Days, and friend activity. Specialist Equipment and Ski Day tools remain justified. The tension is Profile’s accumulation of identity, stats, collection navigation, privacy, security, and deletion.

10. Profile findings

Strengths

  • Clear identity and bounded summaries
  • Useful empty/populated states
  • Dedicated complex managers
  • Consistent row pattern
  • Query shape remains bounded

Confirmed problems

  1. Multiple conceptual domains share one page.
  2. Name/identity has multiple writers.
  3. API name changes omit normalized search-field updates.
  4. Push status is absent.
  5. Availability lacks a persistent row.
  6. Delete modal lacks accessible dialog behavior.
  7. Deletion has the known FK blocker.

11. Settings findings

Equipment, Wishlist, Visited Mountains, and Password work coherently as specialist managers. The architecture is incoherent because there is no Settings hub, Push/Ski Days/Edit Profile use different namespaces, Privacy and Deletion are inline on Profile, and compatibility routes remain beside canonical destinations. “Settings” currently describes implementation structure more than product structure.

14. Redundant workflows

Broad Edit Profile and Profile API overlap without identical secondary behavior. Passes can change through onboarding, Select Pass, and profile logic. Modern Equipment APIs coexist with legacy Profile equipment writers. Settings redirects preserve links but do not perform a current product job.

15. Useful contextual repetition

Primary equipment, wishlist count, visited count, trip count, Ski Day count, passes, Availability summaries, social overlap, and push status may appropriately appear in multiple places when one surface summarizes and another manages. These are not redundant if roles remain explicit.

18. Design consistency findings

Profile’s section-row pattern is clear. Dedicated managers provide visible back navigation, dense collections remain separate, Equipment communicates primary state, and Ski Days separates add/edit/remove. Inconsistencies include rows/buttons/switches/cards for similar actions, dense Edit Profile, inline-styled deletion modal, inconsistent top-bar/page headings, and truncated subtitles.

19. Responsive findings

Forty persona/page combinations were tested at 360, 390, 430, 768, and 1280 pixels across Profile, Edit Profile, Select Pass, Equipment, Push, Ski Days, Wishlist, and Availability.

  • No route failures
  • No horizontal overflow
  • No blocking clipping
  • Reachable controls and bottom navigation
  • Dense Profile remained bounded

Mobile Profile measured about 1,237–1,247 CSS pixels; Edit Profile about 1,370–1,449; dense Wishlist about 1,159–1,170. Wider screens remain readable but leave substantial unused horizontal space because managers retain mobile-oriented content columns.

20. Accessibility/navigation findings

Positive

  • Labeled back links on managers
  • Semantic Push switch state
  • Mostly native links/buttons
  • POST and CSRF for Logout/Delete

Confirmed delete-modal issues

  • No dialog role or aria-modal
  • No accessible heading relationship
  • No focus movement or trap
  • No Escape close
  • No demonstrated focus restoration
  • Email label lacks explicit for association

Async Equipment/Push busy and error announcements, custom discoverability behavior, post-save focus, and deep-link back behavior need explicit implementation criteria. This is not a WCAG certification.

21. Performance/query observations

Profile uses seven SQL statements with or without an owned trip, demonstrating bounded query shape. No Profile GET-time mutation was found. Wishlist loads the active resort catalog, a catalog-scaling risk without a demonstrated current latency defect. Friend Profile is query-heavy but no row-loop N+1 was proven. All 207 focused tests passed.

22. Privacy/authorization observations

Management routes require authentication; Equipment, Ski Days, and Wishlist mutations are owner-scoped; Friend Profile private context requires eligible reciprocal friendship; raw Availability remains private; derived overlap remains constrained; Logout/Delete are POST and CSRF protected; deletion requires confirmation and fresh auth/reauth. No broad leakage was demonstrated. Task #77 remains a concrete operational deletion blocker.

24. Potential screen consolidation/removal opportunities

  1. Settings redirect: build a real Settings destination or document it solely as an alias.
  2. Settings Profile: choose one canonical Edit Profile URL.
  3. Identity writers: share one write contract while preserving onboarding presentation.
  4. Pass editors: choose one later-management owner.
  5. Equipment endpoints: retain one service and deprecate compatibility callers after verification.
  6. Privacy/account: optionally move into coherent Settings while Profile summarizes.
  7. Availability: persistent Profile/Settings summary linking to the dedicated editor.
  8. Open to Ski: retain, de-emphasize, or relabel as Share Availability without duplicating data.

Equipment, Wishlist, Visited Mountains, Ski Days, and Availability perform substantial jobs; full inline absorption is not justified by code similarity alone.

25. Future-state Option A — Profile hub, Settings administration

Profile: identity and summary hub with rider/pass, primary equipment, history stats, persistent Availability, optional push status.

Settings: profile details, equipment, passes, notifications, privacy, password, legal, deletion.

Stays separate: specialist Equipment, Availability, Wishlist, Visited, Ski Days, Select Pass.

Navigation/design: existing four tabs; one clear Settings entry; row summaries.

Benefits: clear identity/configuration separation and discoverability. Tradeoff: Profile and Settings may both be broad.

Complexity: Medium. Migration: no data migration; route/copy/analytics work. Backlog: #66 Profile; #67/#77 Settings.

26. Future-state Option B — Read-only Profile, Settings personal-data center

Profile: read-only identity, résumé, and statistics.

Settings: canonical edit center for identity, passes, equipment, history, wishlist, Availability entry, push, privacy, password, deletion.

Stays separate: complex editors grouped behind Settings.

Benefits: clearest edit ownership and permissions boundary. Tradeoff: Profile is less actionable; Settings can become large; Availability may feel buried.

Complexity: Low–Medium. Migration: no data migration; deep-link regrouping.

27. Future-state Option C — Profile as “My Ski Life”

Profile: canonical index for identity, riding, passes, equipment, Availability, wishlist, visited mountains, Ski Days, and trips.

Settings: narrow system/account destination for push, privacy, password, legal, deletion, and app preferences.

Stays separate: complex editors linked from Profile.

Benefits: strong ski identity and clean account boundary. Tradeoff: Profile can become overloaded; Settings may feel sparse.

Complexity: Medium–High. Migration: no data migration; higher IA/deep-link work.

28. Future-state Option D — Planning-first, de-emphasized sharing

Profile: concise identity/stats with summaries.

Settings: edits and account controls.

Planning: Home, Ideas, Mountains, Trips, and Friend context become the primary value surfaces.

Open to Ski: secondary Share Availability action.

Benefits: fewest competing concepts and strongest planning connection. Tradeoff: less Profile action and lower sharing prominence.

Complexity: Medium. Migration: no data migration; Open to Ski route/copy/analytics policy.

29. Availability placement implications

All options preserve the locked direction: Availability is canonical; Open to Ski is presentation; trips remain separate; raw dates stay private; derived overlap remains eligible/contextual; mountain attachment is interest, not commitment; matching is date-first.

Supported placements include Profile summary, Settings link, Home summary, contextual projections, dedicated calendar, and separate Share Availability. Unsupported assumptions include embedding the full calendar in Profile, making Trips own Availability, automatic synchronization, a new bottom tab, or treating Open to Ski as separate data.

36. Final verdict

BaseLodge’s personal-data architecture is functionally capable but product ownership is fragmented. Profile carries too many roles to communicate one clear purpose, while Settings is not a coherent destination despite owning several URLs. Specialist managers remain justified; the key decision is how they should be owned, grouped, and reached.

Four coherent future architectures are available without immediate data migration. No option has been ranked or selected.
